#### 주제 1: HTTP 인증 방식
- HTTP는 어떻게 인증하는가?
  - - HTTP 몇 가지 특징
  - stateless ← 너가 누군지 모르겠다
      - 모든 요청마다 이전에 요청이나, 너가 누구였는지에 대해서 기억하고 있자 않는다
  - 보호되어야 하는 리소스
      - 내 프로필 정보
      - 결제 정보
      - 접근할 때마다 내가 누구인지 증명해야한다
  - 헤더를 통해서 인증하는 과정을 거친다
- Authorization
  - 클라이언트→서버한테 요청할 때 보내는 헤더
  - 신분증의 내용을 Authorization 헤더에 담는다
- HTTP 인증 헤더 방식 3가지
1. Basic Authentication
- 기본 인증
- 아이디+패스워드로 인증한다
    - 아이디:패스워드 → Base64인코딩한다
    - 인코딩= A→10, B→20 치환
    - 디코딩 10→A, 20→B라고 디코딩이 가능하다
    - 암호화된 통신이 아니고 인코딩된 평문
- Basic 인증 방식은 항상 HTTPS TLS 방식의 암호화된 통신에서만 사용한다
- 아이디 패스워드는 서버에서 검증해야한다
    - 데이터베이스에 들어있는 id, pwd
        - id, pwd 조회하고 입력값과 맞는지 확인하고
        - 이 계정이 하려고 하는 행위에 대한 권한이 있는지도 확인해야한다
    - 서버 자원에 부담이 된다
        - 중앙 집중식 서버에서 트래픽이 몰릴 때 인증이 Basic이라면 병목 현상의 지점이 될 수 있다
    - 장점
        - 구현이 간단하다
        - 토이 프로젝트, 내부용 API 콜할 때
            - 내부 ERD 시스템 사용하거나
2. Digest Authentication
- Basic 이증 ← 보안이 취약하다
    - 보안이 취약한 이유
        - 권한이 필요한 모든 요청마다 항상 “비밀번호”를 헤더에 담아서 보낸다
        - TIL 암호화되어있더라도 한번이라도 암호화가 풀린 구간에서 탈취당한다
    - 비밀번호를 직접 담아서 보내지말고 해시값을 구워서 보내자
- Nonce, Realm
    - Nonce → 서버가 클라이언트한테 딱 한 번쓰고 버리라고 주는 일회성 난수
    - Realm → 서버가 관리하는 보안 공간의 범위를 표기하는 문자열
        - users
        - posts
- 실행 과정
1. 클라이언트가 보호된 리소스를 요청
2. 서버: 여기는 보호되어 있어. 내가 너한테만 주는 일회성 번호(Nonce), 공간 이름(Realm)을 줄테니까 너의 비밀번호랑 섞어서 해시값으로 가져와(401응답)
3. 클라이언트: 비밀번호+Nonce, Realm을 해시 함수로 구워서 Authorization 헤더에 보낸다
- 그래도 문제가 있다
    - 비밀번호를 암호화시키고 보내서 보안성이 올라간다
    - 매번 요청마다 서버가 난수 만들고 그거 기억하고 요청오면 다시 해시화해서 확인해보고 이 과정은 그대로이다

3.Bearer Token

- 기존 방식의 문제점
    - Basic→ 비밀번호 매번 평문으로 보내기 + 매 요청마다 서버가 비번체크
    - Digest → 비밀번호 암호화 → 매 요청마다 서버가 체크하는 건 그대로

이 토큰을 소지한 요청은 “인증, 인가” 된 걸로 한다

- 마치 “무기명 콘서트 티켓”
- 왜 현대 웹에서 사용하냐?
    - 유저의 진짜 아이디 비번은 한 번만 전송된다
    1. 최초 로그인 시도
    2. 서버에서 인증과정을 수행
    3. 토큰을 발급
    4. 토큰을 클라이언트에게 준다
    5. 앞으로 클라이언트는 인증 인가 필요할 떄 이 토큰을 함께 보낸다
    - 이제부터 서버는 데이터베이스에 비밀번호 조회를 1번만 해도 된다

### 베어러 토큰이란?

- Bearer 의미 →소시자, 운반인
    - 토큰을 들고 있는 사람은 정당한 권한이 있는걸로 간주한다
    - 서버는 이 ㅌ큰을 내미는 사람이 진짜 철수인지 아닌지 상관하지 않는다 그냥 토큰에 “철수”라고 적혀 있으면, 다 철수로 생각
    - 티켓이 위조만 안되어 있으면 ok
- 영화관 티켓처럼
    - 아이디 비번 매번 인증하면 불편
        - 베어러 토큰 방식은
            - 키오스크에서 티켓 발급 받는다
            - 티켓을 검표하는 분에게 보여주기만 하면 영화관 들어간다

### 베어러 토큰의 장점

1. 유저의 비밀번호 보호된다
2. 범용성이 좋다
    1. 과거 인증 방식(세션+쿠키) → 브라우저에서는 잘 작동
    2. 모바일 앱에서는 동작하지 않는다
    3. 도메인이 달라지면, 쿠키가 따라 붙지 않는다. 인증 안됨
3. CSRF → 쿠키를 사용해서 취약점 생김

### 베어러 토큰의 단점

- 토큰의 무기명 티켓 → “찰리”라고 적혀 있으면 다 “찰리”인줄 안다
1. 토큰이 탈취되면 위험하다
    1. 토큰 탈취가 쉬움
    2. 토큰을 관리하는 주체는 클라이언트
    3. 토큰은 기본적으로 HTTPS에서 동작하는게 기본적인 원칙
        - 토큰은 유효기간을 짧게 설정하는게 일반적
2. 토큰은 보관하기가 까다롭다
    1. 브라우저→js storage← 직접 겁근할 수 있다
    2. 브라우저의 저장공간은 크게 2개
        1. Storage ← js 값을 가져올 수 있고
        2. Cookie ← 항상 모든 요청에 쿠키가 자동으로 붙음
    3. storage 보관 ←XSS 스크립트 해킹에 토큰 탈취
    4. 쿠키←CSRF 공격에 취약
        1. CSRF 방어하는 코딩을 하면 됨
 
#### 주제 2: JWT 이해하기
- ### JWT토큰이란?

- 마치 홀로그램 인쇄 티켓
    - 기존 토큰→ 아무 글자나 적힌 티켓 → 서버가 받으면, 아무 글자를 조회해서 맞는지 확인하는 과정을 거쳐야 했다.
    - jwt 토큰은
        - [이름: 찰리, 등급: VIP]
        - [영화관장의 친필 홀로그램 사인]이 서명되어있다
        - 서버는[사인]←이게 유효하다면 내부 값은 위조변조가 되지 않았겠구나

### JWT 구조 방식

- header, payload, signature

### 헤더의 영역

- 토큰의 타입, 서명에 사용된 알고리즘

### 페이로드 영역

- jwt 토큰에 담을 정보들이 있는 곳
- 여기는 평문 영역
- 노출되면 안되는 값은 넣으면 안된다

### 서명 영역

→ 이 토큰이 위조되었나? 를 검증하는 영역
- 인코딩 헤더(Base64) + 인코딩된 페이로드(Base64) + 서버만 알고 있는 비밀 키 값
    - 이걸 하나로 합쳐서 지정된 알고리즘으로 암호화한다
- JWT는 내부 내용이 보이니까 내부 내용을 수정할 수도 있는데
    - 해커가 페이로드 값을 변경하면 시그니처가 달라진다

## JWT 왜 써야함

1. 완전한 무상태성+확장성
    - 불편했던 것
    1. Basic, Digest 결국에 서버에서의 검증 로직
    2. 서버가 데이터를 관리하고 조회하는 자원을 써야했었다
    - JWT에서는 내가 필요했던 정보들 인증, 인가 필요한 정보가 이미 jwt토큰에 작성되어 있다
        - Base64 디코딩하면 그 안에 있는 내용만 보면 된다 → CPU 로 풀 수 있음
        - 암호화된 서명만 검증하면 된다
    - 세션 늘리려고 레디스같은 거 꼭 안써도 된다
    - 요청이 늘어나도 그냥 jwt 토큰 검증 시간만 든다
2. DB조회를 상당히 적게 한다
    1. 병목지점 → 왜냐하면 데이터베이스를 조회하기 때문
        1. 디비 조회가 왜 병목인가?
        2. 데이터베이스는 가장 느린 쓰기 장치에 기록된다
            1. HDD
        - API 호출할 때 인증인가 필요할 때 다른 인증들은 DB조회가 필요함

### 단점

1. 무효화가 어렵다
    1. jwt토큰을 발급되는 순간 어디에 있는지?
        1. 클라이언트가 들고 있다. 스토리지, 쿠키
    2. 해커가 jwt 토큰 탈취→만료시키고 싶은 이걸 못함
    3. 실무에서
        1. access Token, Refresh Token
        2. Access Token → 수명이 짧은 토큰
        3. Refresh Token → 토큰을 재발급하는 토큰
2. 네트워크 대역폭이 낭비된다
    1. 토큰은 내부 내용이 많을수록 길이가 길어진다
    2. 매번 API 요청할 때마다 수 Token을 매번 보내고 왔다 갔다하면 그만큼의 대역폭이 낭비된다

## Access Token 과 Refresh Token

→ 유저가 인증하는 건 액세스 토큰

→ 토큰을 재발급하는 건 리프레시 토큰

만약에 리프레시 토큰 탈취되면

- 액세스 토큰을 2주~1달 넘게 발급 받을 수 있다
- 서버는 리프레시 토큰의 주인이 누구인지 모름
- 이 문제를 해결하려고 하는 기술이 RTR

### RTR(Refresh Token Rotation)

1. 유저의 엑세스 토큰 만료
2. 유저가 리프레시 토큰을 서버에 보내면서 엑세스 토큰을 만드는 걸 요청
3. 서버는 본인의 저장소에 리프레시 토큰이 유효한지 확인. 리프레시 토큰 폐기
4. 서버는 유저한테 새로운 엑세스 토큰을 발급하고 새로운 리프레시 토큰 발급
5. 서버는 새로운 리프레시 토큰을 저장소에 저장한다
- 만약에 해커가 훔쳐도 상관없음
1. 해커가 훔친 리프레시 토큰으로 새 토큰 요청
2. 서버는 리프레시 토큰을 지움. 해커한테 새 토큰들을 준다
3. 새 리프레시 토큰을 저장소에 저장한다
4. 잠시 후에 진짜 유저가 자기가 들고 있던 기존 리프레시 토큰으로 재발급 요청
5. 저장소에서 기존 리프레시 토큰 검색 → 없네?
6. 기존 리프레시 토큰으로 발급된 유저는 비정상 유저다
    1. 해커가 쓴 거 아님?
    2. 서버는 해당 유저아이디 관련되 모든 리프레시 토큰을 다 만료시킨다→ 저장소에서 삭제시킴
7. 해커가 들고 있던 새 리프레시 토큰도 의미가 없어진다
