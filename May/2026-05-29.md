### 새로 배운 내용
#### 주제 1: 데이터베이스 동시성 제어
- 데이터베이스 동시성 제어: 여러 사용자가 동시에 데이터베이스에 접근할 때 발생할 수 있는 문제를 방지하고, 데이터의 일관성(consistency)과 무결성(integrity)을 유지하기 위한 기술
- 락킹 메커니즘(Locking Mechanism) (데이터를 안전하게 관리하고, 다중 사용자가 동시에 데이터에 접근할 때 발생할 수 있는 충돌을 방지하기 위한 기술)을 이용
  - 비관적 락
    - 충돌 가능성을 미리 가정하고 데이터를 사용할 때 락을 걸어 다른 사용자의 접근을 차단.
    - 주로 관계형 데이터베이스(RDBMS)에서 사용되며, 정확성과 일관성이 무엇보다 중요한 데이터에 적용.
    - | 장점 | 단점 |
      | :--- | :--- |
      | - 데이터 무결성과 일관성을 강하게 보장합니다.<br>- 충돌을 사전에 차단합니다.<br>- 정합성이 중요한 작업에 적합합니다. | - 동시성이 저하될 수 있습니다.<br>- 락 대기 및 데드락 발생 가능성이 있습니다.<br>- 트랜잭션 처리량이 감소할 수 있습니다. |
  - 낙관적 락
    -  충돌 가능성을 낮게 가정하고 데이터를 먼저 사용한 뒤, 최종적으로 업데이트 시 충돌 여부를 검사.
    - 충돌이 발생하면 UPDATE가 실패하며, 애플리케이션은 이를 감지해 재시도 또는 실패 처리로 대응.
    - | 장점 | 단점 |
      | :--- | :--- |
      | - 높은 동시성과 성능을 제공합니다.<br>- 락 대기가 없습니다.<br>- 읽기 위주의 환경에 적합합니다. | - 충돌 시 재시도 또는 실패 처리가 필요합니다.<br>- 충돌이 잦으면 비효율적입니다.<br>- 구현 로직이 필요합니다. |
- 데드락: 여러 트랜잭션이 서로가 가진 락을 기다리며 순환 대기(Circular Waiting) 상태에 빠질 때 발생합니다. 
  - 일반적인 원인은 서로 다른 자원을 서로 다른 순서로 잠그는 경우입니다. 대부분의 DBMS는 데드락을 자동으로 감지하고, 한 트랜잭션을 롤백하여 해소합니다.

#### 주제 2: Multi-Version Concurrency Control(MVCC)
- MVCC: 데이터베이스에서 동시성을 관리하기 위한 핵심 메커니즘 중 하나
  - 데이터의 여러 버전을 관리함으로써, 여러 트랜잭션이 동시에 데이터에 접근하더라도 서로 간섭하지 않도록 설계
  - MVCC를 사용하는 데이터베이스에서는 읽기 작업이 쓰기 작업을 직접 차단하지 않으며,
  - 각 트랜잭션은 자신이 시작된 시점 기준의 일관된 데이터 스냅샷을 읽게 됩니다.
  - 이로 인해 데이터베이스는 락(lock)에 과도하게 의존하지 않고도 일관된 읽기(Consistent Read)와 높은 동시성을 동시에 제공할 수 있습니다.
  - | 특징 | 내용 |
    | :--- | :--- |
    | **높은 동시성** | 읽기 작업이 쓰기 작업을 차단하지 않아, 다수의 트랜잭션이 동시에 처리될 수 있습니다. |
    | **데이터 정리 필요** | 여러 버전의 데이터가 생성되므로, 사용되지 않는 이전 버전을 정리하는 작업(예: PostgreSQL의 VACUUM, MySQL의 Undo Log 정리)이 필요합니다. |
    | **버전 충돌** | 트랜잭션은 최신 데이터가 아니라, 자신의 트랜잭션 시점에 유효한 버전을 읽습니다. |
- 락은 “막아서 기다리게 하는 방식”이고, MVCC는 “막지 않고 각자 볼 데이터를 분리하는 방식”
- Connection Pool: 데이터베이스 연결을 매 요청마다 새로 생성하지 않고, 미리 만들어 둔 연결을 재사용하는 방식
  - 애플리케이션이 DB 작업을 수행할 때마다 연결을 생성하고 종료하면, 네트워크 연결 수립, 인증, 세션 초기화 등의 비용이 반복적으로 발생합니다.
    Connection Pool은 이러한 반복 비용을 제거하기 위해 도입됩니다.
  - Connection Pool은 애플리케이션 시작 시 일정 개수의 커넥션을 미리 생성해 두고, 요청이 들어오면 풀에서 하나를 빌려 사용한 뒤 다시 반환하는 구조로 동작합니다.
    중요한 점은 커넥션을 “종료”하는 것이 아니라 “반환”한다는 것입니다.
- InnoDB Buffer Pool: 쿼리 결과를 캐싱하는 것이 아니라, 테이블의 데이터 페이지와 인덱스 페이지 자체를 메모리에 캐싱

#### 주제 3: OAuth
- OAuth: 사용자가 자신의 정보에 대한 접근 권한을 안전하게 타사 애플리케이션에 부여할 수 있게 하는 개방형 표준 프로토콜
- 사용자 비밀번호를 노출하지 않고도, 애플리케이션이 사용자의 데이터에 안전하게 접근할 수 있음
- OAuth	
1. 사용자 로그인 요청
2. 클라이언트가 인증 요청을 인증 서버로 전송
3. 로그인 페이지 제공
4. 사용자의 ID/PW 입력 및 제출
5. Authorization Code 발급
6. 클라이언트로의 리다이렉션
7. Authorization Code와 Access Token 교환
8. Access Token (및 필요시 Refresh Token) 발급
9. 로그인 성공
10. Access Token으로 리소스 서버에 리소스 요청
11. 리소스 서버의 토큰 검증
12. 리소스 제공
13. 클라이언트에서 데이터 활용
