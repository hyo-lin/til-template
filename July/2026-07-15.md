### 새로 배운 내용
#### 주제 1: Service
* **Service (서비스) 정의:** 파드(Pod) 집합에 대한 네트워크 엔드포인트를 생성하고, 클러스터 내부 또는 외부에서 해당 파드들에 안정적으로 접근할 수 있도록 지원하는 쿠버네티스 리소스입니다.
* **등장 배경:** 쿠버네티스 안에서 파드는 스케일링, 업데이트, 장애 복구 과정에서 언제든지 생성되고 삭제되며 IP 주소가 끊임없이 변경됩니다. 따라서 동적으로 변하는 파드의 개별 IP 대신, 애플리케이션들이 안정적으로 서로를 찾을 수 있는 **영구적인 고정 네트워크 주소**가 필요해졌습니다.

- ### 💡 Service를 사용해야 하는 진짜 이유 

쿠버네티스 환경에서 파드의 원활한 트래픽 제어와 프로덕션 환경의 고가용성을 확보하기 위해 서비스를 필수적으로 도입해야 하는 핵심 이유입니다.

| 이유 | 📝 상세 설명 | 🚀 현업 엔지니어의 Real-World Tip |
| :--- | :--- | :--- |
| **네트워크 안정성 보장** | 파드의 IP 주소는 수시로 변경되므로 고정된 가상 IP(Service)를 통해 언제나 안정적인 통신 엔드포인트를 확보합니다. | *주의:* 완전히 종료(Termination)되는 중인 파드와 이미 맺어져 있는 기존 TCP 연결은 끊어질 수 있으므로, 무중단 배포 시 Graceful Shutdown 설정이 동반되어야 합니다. |
| **관리 효율성 향상** | `Label Selector`를 기반으로 파드를 자동 탐지(Service Discovery)하므로, 인프라의 동적 스케일링에 유연하게 대응합니다. | **현업 빅테크 운영 환경에서도 파드의 개별 IP는 완벽히 무시하며 관리 영역에서 제외**합니다. 오직 서비스와 셀렉터 바인딩을 통해서만 통신 경로를 제어합니다. |
| **자동 트래픽 분산** | 서비스로 유입되는 트래픽을 백엔드 파드들로 자동 로드 밸런싱하여 특정 파드의 과부하를 방지합니다. | 서비스(Kube-Proxy)가 커널 레벨(IPVS/IPTables)에서 효율적으로 트래픽을 분산해 주므로 대규모 트래픽 하에서도 가용성과 빠른 응답 속도를 유지합니다. |
| **외부와의 유연한 연결** | `NodePort`, `LoadBalancer` 등의 타입을 사용하여 내부망 격리 수준을 조정하고 외부 네트워크 노출을 간편하게 제어합니다. | 서비스 설정을 통해 외부 로드 밸런서 프로비저닝부터 클러스터 내부의 파드 연결 통로까지 복잡한 네트워크 가상화 구성을 코드 한 줄로 자동 연동합니다. |

- ### 📊 Service 특징

| 특징 | 📝 상세 설명 | ⚙️ 주요 역할 및 이점 |
| :--- | :--- | :--- |
| **Pod 집합의 단일 엔드포인트** | 여러 개의 파드를 하나의 네트워크 그룹으로 묶어 단일 IP와 포트를 제공합니다. | 개별 Pod의 IP를 일일이 알 필요 없이, 서비스 엔드포인트만 바라보고 트래픽을 보낼 수 있습니다. |
| **안정적인 고정 IP 제공** | 파드가 죽고 새로 뜨면서 IP가 계속 바뀌더라도, 서비스는 고유한 고정 IP를 유지합니다. | Pod의 일시적인 생성/삭제에 영향을 받지 않고 영구적이고 안정적인 백엔드 연결을 유지합니다. |
| **내장 DNS 지원** | 서비스가 생성되면 쿠버네티스 내부 DNS 서버(CoreDNS)에 서비스 이름이 자동으로 등록됩니다. | 동일 클러스터 내에서는 IP가 아닌 서비스 이름(Domain) 기반으로 직접 라우팅 및 통신이 가능합니다. |
| **자동 트래픽 분산** | 서비스는 셀렉터(`selector`)로 매핑된 여러 대의 파드로 트래픽을 자동으로 분산(Load Balancing)합니다. | 특정 Pod에 트래픽이 몰리지 않도록 부하를 효율적으로 조율해 줍니다. |


- EndpointSlice: 서비스가 현재 연결할 수 잇는 실제 파드 IP 목록을 저장하는 리소스
- port: 클러스터 내부에서 “서비스”가 요청을 받을 때 사용하는 포트
- targetPort: 연결 대상 파드 컨테이너에서 사용하는 포트
```
[클라이언트] ────> [서비스 (port: 80)] ────> [실제 파드 (targetPort: 3000)]
```

- ### 🌐 ClusterIP 서비스 개요

| 구분 | 📝 핵심 내용 |
| :--- | :--- |
| **정의** | 클러스터 내부에서만 접근 가능한 가장 기본적인 서비스 유형입니다. 외부 네트워크에 노출되지 않으며, 쿠버네티스에서 Service를 생성할 때 지정하는 **기본값(Default)**입니다. |
| **사용 이유** | 클러스터 내부에 존재하는 다양한 애플리케이션 구성 요소들(마이크로서비스 파드, 데이터베이스 등)이 외부 노출 없이 안전하게 서로 내부 통신을 주고받기 위해 사용합니다. |
| **사용 방법** | 서비스 정의 YAML 파일의 `spec.type` 필드를 `ClusterIP`로 설정하면, 클러스터 내부에서만 유효한 가상 IP 주소(ClusterIP)가 자동으로 할당됩니다. |
| **사용 사례** | • **내부 데이터베이스:** 외부 접근이 차단되어야 하는 MySQL, PostgreSQL, Redis 등<br>• **내부 마이크로서비스:** 프론트엔드 파드에서만 호출하는 백엔드 API 서버<br>• **관리 도구:** 관리자만 내부망을 통해 접근해야 하는 Kubernetes Dashboard 등 |

- ### 🔌 NodePort 서비스 개요

| 구분 | 📝 핵심 내용 |
| :--- | :--- |
| **정의** | 클러스터 외부에서 내부 서비스에 직접 접근할 수 있도록, 모든 클러스터 노드(Node)의 특정 포트를 열어서 연결해 주는 서비스 유형입니다. |
| **사용 이유** | 로드 밸런서 같은 복잡한 외부 연동 장치 없이도, 클러스터 노드의 퍼블릭 IP와 할당된 포트 번호만을 이용해 간편하게 외부 트래픽을 내부 파드(Pod)로 유입시키기 위해 사용합니다. |
| **사용 방법** | • YAML 파일의 `spec.type`을 `NodePort`로 지정합니다.<br>• 쿠버네티스가 노드에 할당하는 포트 범위는 기본적으로 **`30000 ~ 32767`** 사이입니다. (원하는 포트를 `spec.ports[].nodePort`에 직접 명시할 수도 있습니다.) |
| **사용 사례** | • **테스트 및 개발 환경:** 별도의 클라우드 인프라 연동 없이 외부 브라우저에서 빠르게 동작을 테스트할 때<br>• **온프레미스/사내망:** 외부 트래픽이 직접 특정 서비스로 인입되도록 내부 네트워크 라우팅을 구성할 때 |

- ### ⚖️ LoadBalancer 서비스 개요

| 구분 | 📝 핵심 내용 |
| :--- | :--- |
| **정의** | 클라우드 제공업체(Cloud Provider)의 로드 밸런서를 연동하여 공인 IP(External IP)를 할당받고, 외부 네트워크에서 안정적으로 서비스에 접근할 수 있도록 경로를 열어주는 서비스 유형입니다. |
| **사용 이유** | 특정 노드의 IP에 종속되지 않고, 단일 진입점이 되는 공인 IP와 도메인을 통해 다수의 외부 사용자가 언제 어디서나 안정적으로 서비스에 접속할 수 있도록 설계해야 할 때 사용합니다. |
| **사용 방법** | • YAML 파일의 `spec.type`을 `LoadBalancer`로 설정합니다.<br>• 설정을 적용하면 AWS(ELB/ALB), GCP(Cloud Load Balancing), Azure 등에서 백하우스 시스템을 통해 인프라 수준의 외부 로드 밸런서가 자동으로 프로비저닝됩니다. |
| **사용 사례** | • **상용 서비스 배포:** 실제 일반 사용자가 접속하는 웹 서비스, 모바일 앱 백엔드 등을 안전하게 서비스할 때<br>• **외부 API 제공:** 사외 파트너사나 외부 클라이언트가 연동 및 호출할 수 있는 공인 API 게이트웨이 서버를 노출할 때 |

- ### ⚠️ 서비스가 하지 "않는" 일 (오개념 바로잡기)
  1. 서비스는 파드를 생성하지 않습니다.
  - 서비스는 오직 만들어진 파드 중 Selector에 맞는 녀석을 골라 트래픽을 전달할 뿐입니다. 파드가 죽었을 때 다시 띄우거나 개수를 유지하는 것은 ReplicaSet 이나 Deployment 같은 다른 리소스들의 몫입니다.
  2. 서비스는 URL 경로(Path-based)로 라우팅을 하지 못합니다.
  - 서비스는 L4 수준의 리소스입니다. IP와 Port, 프로토콜(TCP/UDP)만 바라보고 단순 전달만 수행할 뿐입니다.
  - 만약 /api/users는 A 서비스로, /api/auth는 B 서비스로 라우팅하는 식의 L7 수준(Application Layer)의 라우팅이 필요하다면 서비스가 아니라 Ingress나 API Gateway 리소스를 구현해야 합니다.

- #### 🛠️ 장애 해결을 위한 현업 실무 트러블슈팅 팁
  1. 서비스 통신 장애 발생 시 가장 먼저 엔드포인트부터 체크하기

  - 서비스가 안 돌면 대뜸 DNS 오류부터 의심하기 십상이지만, 실제 원인은 Selector 라벨 오타인 경우가 허다합니다. kubectl get endpointslices [서비스명]을 쳤을 때 타겟 IP 목록이 정상적으로 바인딩되어 있는지 반드시 교차 검증해 보세요.

  2. port와 targetPort 불일치 사태 예방

  - 서비스의 targetPort와 파드의 containerPort가 단 1의 오차 없이 서로 매핑되어 있는지 포트 값을 꼭 확인해야 합니다. 포트가 어긋나면 무한 행잉(Hanging) 및 Connection Refused 에러가 발생합니다.

  3. Selector 라벨 변경 시 트래픽 급감 주의

  - 서비스 Selector의 라벨 조건(예: version: v1 ➔ v2)을 갑자기 임의 변경하면, 아직 준비가 완료된 파드 수가 충분하지 않은 상태에서 변경된 타겟으로 트래픽이 한 번에 쏠려 서비스 레이턴시가 폭발하거나 일시적으로 처리가 중단되는 장애 상황이 발생할 수 있습니다.

  4. NodePort는 운영에서 절대 배제하기

  - 모든 노드에 포트 구멍을 뚫어야 하므로 보안 그룹 관리가 까다롭고, 포트 범위가 고도로 제한적이라 상용 환경에는 부적합합니다. 특수 목적을 제외한 운영 인프라는 무조건 Ingress 기반의 단일 엔드포인트 아키텍처를 지향해야 합니다.

#### 주제 2: Probe
- Probe: 컨테이너의 상태를 주기적으로 진단하는 메커니즘
  - 애플리케이션의 상태를 지속적으로 감지하여 안정성과 가용성을 보장하기 위해서
- ### 🔍 Kubernetes 3대 프로브(Probe)  요약

| 프로브 종류 | 📝 핵심 역할 | ⚙️ 동작 메커니즘 및 특징 |
| :--- | :--- | :--- |
| **Startup Probe**<br>(스타트업 프로브) | 애플리케이션의 **초기화 및 부팅 과정이 완료**되었는지 감지합니다. | • 무거운 애플리케이션(예: 초기 로딩이 긴 Spring Boot)의 안정적인 기동을 돕습니다.<br>• 이 프로브가 **성공하기 전까지는 아래의 Liveness/Readiness Probe 검사가 완전히 비활성화**됩니다.<br>• 실패 시: 컨테이너를 재시작합니다. |
| **Liveness Probe**<br>(활성 프로브) | 애플리케이션이 **정상 구동 중인지(살아있는지)** 지속해서 모니터터링합니다. | • 데드락(Deadlock)에 걸리거나 프로세스가 먹통(Hang)이 된 불완전 상태를 감지합니다.<br>• 컨테이너 자체가 정상 동작하지 않는다고 판단되면 **자동 복구(Self-Healing)를 트리거**합니다.<br>• 실패 시: 컨테이너를 강제로 즉시 재시작(Restart)합니다. |
| **Readiness Probe**<br>(준비성 프로브) | 애플리케이션이 **사용자의 실제 트래픽을 처리할 준비가 되었는지** 확인합니다. | • 대규모 데이터 로딩, 설정 캐싱 등이 끝나기 전까지 무분별하게 트래픽이 유입되어 에러가 발생하는 것을 방지합니다.<br>• 실패 시: 컨테이너를 죽이지 않고, 오직 **서비스의 Endpoint(EndpointSlice) 목록에서 해당 파드의 IP를 제외**하여 트래픽 인입만 차단합니다. |

- ### 🎯 Probe의 3대 핵심 역할 및 목적

쿠버네티스 컨테이너 자가 치유(Self-Healing)의 기반이 되는 프로브(Probe)의 본질적인 역할들입니다.

| 역할 | 📝 상세 설명 | ⚙️ 주요 동작 및 이점 |
| :--- | :--- | :--- |
| **실시간 상태 점검**<br>(State Monitoring) | 컨테이너 내 애플리케이션의 런타임 상태를 주기적으로 추적하여 정상 여부를 진단합니다. | 노드 내부의 `kubelet`이 지정된 프로브 방식(HTTP, TCP, Exec 등)으로 신호를 보내 상태 정보를 상시 수집합니다. |
| **지능형 트래픽 제어**<br>(Traffic Control) | 준비 과정이 끝나지 않았거나 내부 장애로 비정상 동작 중인 파드로 트래픽이 새어나가지 않도록 통제합니다. | 아직 부팅 중인 서버에 무리한 트래픽이 인입되어 사용자에게 에러 페이지(`502 Bad Gateway` 등)가 노출되는 대형 참사를 사전에 완벽히 차단합니다. |
| **자동 복구 수행**<br>(Self-Healing) | 애플리케이션이 데드락이나 메모리 누수 등으로 먹통이 되었을 때, 인프라 수준에서 스스로 대응합니다. | 사람이 개입하여 서버를 재부팅할 필요 없이, 시스템 장애를 스스로 감지하고 **컨테이너를 자동 재시작(Restart)**하여 순식간에 서비스를 정상화합니다. |

- ### LivenessProbe: 컨테이너의 Liveness(살아있는 상태)를 주기적으로 진단하는 메커니즘
  - 애플리케이션이 실행 중에 발생할 수 있는 비정상 상태를 자동으로 감지하고, 컨테이너를 재시작하여 복구하기 위해서
  - ### 🔄 Liveness Probe를 사용해야 하는 진짜 이유 (현업 관점)

애플리케이션이 먹통이 되는 시점을 인프라가 실시간으로 감지하고, 수동 개입 없이 스스로 치유(Self-Healing)하는 메커니즘을 구축하기 위해 필수적으로 도입해야 하는 이유입니다.

| 이유 | 📝 상세 설명 | 🚀 현업 엔지니어의 Real-World Tip |
| :--- | :--- | :--- |
| **비정상 상태 감지**<br>(Failure Detection) | 컨테이너 프로세스 자체는 살아있더라도 내부적인 문제(메모리 누수, 데드락, 스레드 잠금 등)로 인해 실제 요청 처리가 불가능한 불완전 상태를 정확히 짚어냅니다. | 단순히 프로세스 생존 여부만 보는 것이 아니라, 내부 헬스체크 API 엔드포인트(예: `/actuator/health`)를 찔러 내부 커넥션 풀 상태까지 종합 진단해야 합니다. |
| **자동화된 즉각 복구**<br>(Automated Recovery) | 비정상 상태가 감지되는 즉시 쿠버네티스가 해당 컨테이너를 스스로 재시작하여, 운영자의 별도 수동 개입 없이도 장애 상황을 신속하게 해결합니다. | **주의:** 어플리케이션 버그로 인한 무한 재시작 루프(`CrashLoopBackOff`)에 빠지지 않도록 적절한 임계치(Failure Threshold) 설정이 필수적입니다. |
| **트래픽 실패 차단**<br>(Preventing Traffic Failure) | 이미 망가진 상태의 컨테이너로 유저 트래픽이 계속 유입되어 에러가 발생하는 상황을 방지하고, 빠르게 컨테이너를 갈아 끼워 서비스 품질을 유지합니다. | 대규모 환경일수록 복구 골든타임을 확보하는 것이 중요하며, Liveness Probe가 일차적인 방어선 역할을 수행합니다. |
| **서비스 가용성 보장**<br>(High Availability) | 파드(Pod) 전체를 삭제하고 새로 스케줄링하는 무거운 작업 대신, **문제가 터진 컨테이너만 핀포인트로 재시작**하므로 파드 전체의 가용성을 안정적으로 유지합니다. | 멀티 컨테이너 파드 구조(예: 사이드카 패턴)에서 메인 컨테이너만 가볍게 살려내어 장애 확산을 조기에 차단할 수 있습니다. |
| **운영 효율성 극대화**<br>(Operational Efficiency) | 상태 점검(Health Check)과 1차 복구 절차를 완벽히 자동화함으로써 야간 장애 대응 등 운영진의 모니터링 부담을 획기적으로 줄여줍니다. | 수백, 수천 개의 파드가 돌아가는 대규모 마이크로서비스 아키텍처(MSA) 환경을 안정적으로 운영하기 위한 필수 기반 기술입니다. |
| **일관된 복구 정책**<br>(Consistent Policy) | 모든 마이크로서비스의 컨테이너에 동일한 점검 기준과 복구 규칙을 선언적으로 적용하여, 예측 불가능한 장애 상황에서도 일관되고 체계적인 대응을 보장합니다. | 인프라 엔지니어와 개발팀 간의 헬스체크 표준 규격을 맞추는 도구(IaC)로 활용하기 매우 좋습니다. |

### 1. 🔍 헬스 체크(Health Check) 메커니즘

Liveness Probe는 주기적으로 컨테이너 내부의 건강 상태를 점검하며, 가장 널리 쓰이는 방식은 **HTTP GET 요청**을 통한 웹 서버 엔드포인트 호출입니다.

* **정기적 호출:** 애플리케이션의 특정 헬스체크 경로(예: `/health`, `/actuator/health`)를 정기적으로 찌르거나, TCP 소켓 연결, 컨테이너 내부 명령어(`Exec`) 실행 등으로 상태를 확인합니다.
* **HTTP 응답 코드를 통한 판정:**
  * **`200 ≤ status < 400` (정상):** 애플리케이션이 건강하게 잘 살아서 요청을 처리할 수 있는 상태로 판정합니다.
  * **`status ≥ 400` 또는 타임아웃 (비정상):** 내부 스레드 데드락, DB 커넥션 유실 등으로 인해 애플리케이션이 먹통이 된 상태로 판정합니다.

### 2. 🎛️ 핵심 설정 요소 (Configuration)

YAML 파일에서 프로브의 정밀도를 제어하는 핵심 파라미터 4가지입니다.

| 설정 요소 | 📝 상세 설명 | ⚠️ 실무 고려사항 |
| :--- | :--- | :--- |
| **초기 지연 시간**<br>(`initialDelaySeconds`) | 컨테이너가 최초로 기동된 후, **첫 번째 헬스 체크를 수행하기 전까지 대기**하는 시간입니다. | 이 시간이 너무 짧으면, 애플리케이션 부팅이 완료되기도 전에 헬스 체크가 들어가서 컨테이너가 무한 재시작되는 루프에 빠질 수 있습니다. |
| **체크 주기**<br>(`periodSeconds`) | 상태 점검(Health Check)을 **얼마나 자주 수행할지** 결정하는 시간 간격입니다. | 너무 짧으면 서버에 헬스체크 트래픽 부하를 주고, 너무 길면 장애 감지와 복구 골든타임을 놓치게 됩니다. (기본값: 10초) |
| **타임아웃**<br>(`timeoutSeconds`) | 헬스 체크 요청을 보낸 후, **응답을 기다려주는 최대 제한 시간**입니다. | 지정한 시간 내에 응답이 오지 않으면 1회 실패로 간주합니다. 대개 1~3초 내외로 타임아웃을 짧게 가져갑니다. |
| **실패 임계값**<br>(`failureThreshold`) | 연속으로 **몇 번 이상 상태 점검에 실패해야** 컨테이너를 최종 비정상으로 판정하고 재시작할지 결정하는 횟수입니다. | 네트워크 일시 지연 등 일시적인 튐 현상으로 오작동하는 것을 막기 위해 보통 **3회 연속 실패** 시 복구를 트리거하도록 설정합니다. |

### 🚨 3. 장애 발생 시 자동 복구 프로세스

헬스 체크 도중 장애가 감지되었을 때, 쿠버네티스(Kubelet)가 컨테이너를 격리하고 자가 치유하는 단계별 흐름입니다.

```text
[정상 구동 중]
       │
       ▼
[특정 엔드포인트 호출 실패 (Status 500 or Timeout)]
       │
       ▼
[연속 실패 횟수 카운팅 시작]
       │
       ├─── 실패 횟수 < failureThreshold ───► 주기적인 재시도 대기 (계속 감시)
       │
       └─── 실패 횟수 ≥ failureThreshold (최종 장애 인식)
                               │
                               ▼
              [컨테이너 즉시 강제 재시작 (Self-Healing)]
 ```             
---
- ### ReadinessProbe: 컨테이너가 외부 요청을 처리할 수 있는지 상태를 주기적으로 진단하는 메커니즘
  - 준비되지 않은 컨테이너로 인해 발생할 수 있는 서비스 장애를 예방하여 안정적이고 신뢰성 높은 서비스를 보장하기 위해서
  - ### 🛡️ Readiness Probe를 사용해야 하는 진짜 이유 (현업 관점)

애플리케이션이 구동되자마자 트래픽이 인입되어 사용자에게 에러를 뱉는 참사를 막고, 실시간 동적 인프라 환경에서 완벽한 무중단 서비스를 제공하기 위해 도입해야 하는 핵심 이유입니다.

| 이유 | 📝 상세 설명 | 🚀 현업 엔지니어의 Real-World Tip |
| :--- | :--- | :--- |
| **준비되지 않은 상태의 장애 방지**<br>(Initialization Protection) | 애플리케이션 초기화 과정(DB 연결, 환경 변수 로드, 캐시 빌드 등)이 채 끝나기도 전에 외부 요청이 들어와 요청 처리에 실패하거나 SQL 에러를 뱉는 상황을 사전에 방지합니다. | 서버 프로세스가 떴다고 해서 바로 유저 요청을 처리할 수 있는 것은 아닙니다. 필수 외부 리소스(DB, Redis 등)와의 커넥션이 확실히 맺어진 후에 트래픽을 열어야 합니다. |
| **사용자 경험 완벽 보호**<br>(User Experience Protection) | 준비가 덜 된 컨테이너에 요청이 전달되면 심각한 응답 지연(Timeout)이 발생하거나 에러 페이지가 노출되어 서비스 신뢰도에 치명적인 타격을 줍니다. 이를 인프라단에서 원천 차단합니다. | 유저에게 노출되는 `502 Bad Gateway`나 `504 Gateway Timeout`의 상당수가 이 Readiness Probe가 없거나 설정이 꼬여서 발생합니다. |
| **동적 환경에서의 안정성 확보**<br>(Zero-Downtime Deployment) | 파드가 늘어나는 오토스케일링(HPA), 무중단 롤링 업데이트, 노드 장애 복구 등 파드가 급격히 재생성되는 과도기적 상황에서 안정성을 확보합니다. | 새 버전의 파드가 완전히 통신할 준비(`Ready`)가 될 때까지 트래픽 진입을 차단하고 기존 파드로만 서빙하여, 배포 중 트래픽 유실률을 **0%**로 만듭니다. |
| **서비스 전반의 신뢰성 향상**<br>(High Service Reliability) | 헬스 체크를 통과해 완벽하게 준비된 컨테이너만 실제 운영 트래픽 라인업에 올리기 때문에, 전체 애플리케이션의 동작 예측 가능성이 극대화됩니다. | 불량 파드를 걸러내고 검증된 파드로만 통신망을 구성하므로, 장애가 터지더라도 영향도를 최소화하고 유저에게 일관된 품질을 보장합니다. |
| **구체적인 프로덕션 사고 예방**<br>(Real-world Incident Prevention) | 데이터베이스 커넥션 풀(DBCP) 생성 지연 시, 연결이 완료될 때까지 엔드포인트에서 격리하여 SQL Connection Error를 예방합니다. | 롤링 배포 시 새로 뜨는 파드가 미처 기동이 끝나기 전에 기존 파드가 먼저 죽어버려 일시적으로 전체 서비스가 먹통이 되는 배포 사고를 완벽히 예방합니다. |


- ### 📊 Readiness Probe 핵심 특징

애플리케이션이 완전히 부팅되어 사용자의 실제 트래픽을 안전하게 처리할 수 있는 시점을 지능적으로 판단하기 위한 핵심 메커니즘입니다.

| 특징 | 📝 상세 설명 | ⚙️ 주요 역할 및 이점 |
| :--- | :--- | :--- |
| **주기적 실시간 점검** | 정의된 주기(`periodSeconds`)와 진단 방식에 따라 컨테이너가 살아있는 동안 상태를 멈추지 않고 상시 감시합니다. | 일시적인 과부하나 내부 리소스 장애로 인해 애플리케이션의 응답 능력이 상실되는 순간을 실시간으로 캐치합니다. |
| **지능형 준비 상태 제어** | 컨테이너가 아직 트래픽을 받을 준비가 안 되었다면, **파드의 IP를 서비스 엔드포인트(EndpointSlice) 목록에서 즉시 제외**합니다. | 준비되지 않은 파드로 트래픽이 유입되어 사용자에게 연결 실패(`Connection Refused`) 에러가 노출되는 대형 참사를 사전에 완벽히 차단합니다. |
| **다양한 점검 방식 지원** | 애플리케이션의 성격에 맞춰 **HTTP GET 요청, 내부 명령 실행(Exec), TCP 소켓 연결** 등 최적의 검사 필터를 유연하게 선택할 수 있습니다. | 일반 웹 서버뿐만 아니라 데이터베이스, 캐시 서버, 데몬 프로세스 등 다양한 형태의 컨테이너를 맞춤형으로 완벽하게 진단합니다. |

- ### 🚦 Readiness Probe가 구분하는 파드 상태 명세

Readiness Probe의 검사 결과에 따라 파드는 오직 다음 두 가지 상태로만 분류되며, 이에 따라 쿠버네티스 서비스(Service)의 트래픽 라우팅 대상 여부가 실시간으로 결정됩니다.

| 상태 | 📝 상세 설명 | ⚙️ 쿠버네티스 서비스(Service)의 처리 방식 |
| :--- | :--- | :--- |
| **Ready 상태**<br>(준비 완료) | 컨테이너 내부의 애플리케이션 초기화(DB 연결, 캐시 로딩 등)가 완벽히 끝나 **외부 요청을 안정적으로 처리할 수 있다고 판정된 상태**입니다. | 서비스의 실제 타겟 목록인 **`EndpointSlice`에 해당 파드의 IP가 즉시 추가**되며, 사용자의 실제 운영 트래픽이 정상적으로 분산 인입되기 시작합니다. |
| **NotReady 상태**<br>(준비 미완료) | 컨테이너가 막 기동 중이거나, 실행 중 일시적인 과부하·내부 장애가 발생하여 **외부 요청을 받아들일 준비가 되지 않았다고 판정된 상태**입니다. | 컨테이너를 강제로 죽이거나 재시작하지는 않습니다. 대신 **`EndpointSlice` 목록에서 해당 파드의 IP를 즉시 격리/제외**하여 준비가 끝날 때까지 트래픽 유입을 철저히 차단합니다. |

> **💡 핵심 요약**
> 컨테이너가 최초 기동된 후 **`Ready` 상태로 전환되기 전까지**, 쿠버네티스 서비스는 해당 파드를 절대 엔드포인트로 사용하지 않고 보호합니다. 이 덕분에 사용자는 배포 중에도 에러 없는 무중단 서비스를 경험할 수 있습니다.

- ### StartupProbe: 초기화 상태를 확인하기 위해 실행되는 점검 메커니즘
  - 초기화 시간이 오래 걸리는 애플리케이션의 안정성을 보장하기 위해서
  - ### 🚀 Startup Probe를 사용해야 하는 진짜 이유 (현업 관점)

초기 기동 시간(웜업)이 길거나 무거운 애플리케이션이 첫 부팅을 완전히 마칠 때까지 인프라 수준에서 안전하게 보호막을 씌워주기 위해 필수적으로 도입해야 하는 이유입니다.

| 이유 | 📝 상세 설명 | ⚙️ Liveness/Readiness Probe와의 연계 흐름 |
| :--- | :--- | :--- |
| **초기화 시간이 긴 애플리케이션 처리**<br>(Heavy App Warm-up) | 초기 로딩 및 환경 설정 등으로 부팅이 오래 걸리는 애플리케이션이 실제 트래픽을 받기 전, 충분한 시간적 여유를 가지고 안정적으로 기동할 수 있도록 든든한 대기 시간을 보장합니다. | 이 프로브가 활성화되어 검사를 수행하는 동안에는 **불필요하고 성급한 상태 점검(Liveness/Readiness)이 완전히 유예(Hold)**됩니다. |
| **초기화 중 문제 감지 및 자동 복구**<br>(Early Boot Failure Detection) | 부팅 과정에서 발생할 수 있는 OOM(메모리 부족), 필수 환경 변수 누락, 외부 DB 연결 실패 등의 기동 장애를 조기에 파악합니다. | 초기화가 끝나기도 전에 문제가 터졌다면, 쿠버네티스가 상황을 감지하고 컨테이너를 자동으로 재시작하여 스스로 복구 프로세스를 가동합니다. |
| **초기화 중 트래픽 완벽 차단**<br>(Zero Traffic During Boot) | 부팅 과정 중에 사용자 요청이 유입되어 에러가 발생하는 것을 막기 위해, Readiness Probe의 개입 자체를 뒤로 미루어 초기화 중인 컨테이너로의 트래픽 진입을 원천 봉쇄합니다. | 확실하게 기동(`Startup`)이 검증된 뒤에만 준비성(`Readiness`) 테스트 바통을 넘기기 때문에, 배포 시 단 한 건의 유실 트래픽도 생기지 않습니다. |
| **Liveness Probe의 오작동 방지**<br>(Preventing False-Positive Restarts) | 아직 서버가 열심히 부팅되는 중인데 Liveness Probe가 성급하게 "서버가 응답하지 않는다"며 멀쩡히 기동 중인 컨테이너를 강제로 죽이고 무한 재시작시키는 악순환을 완벽히 해결합니다. | **데스 루프(Death Loop) 방지:** 무거운 서버가 뜨다가 죽고, 다시 뜨다가 죽는 인프라 낭비를 확실하게 막아줍니다. |
| **초기화와 실행 상태의 명확한 분리**<br>(Lifecycle Separation) | 서버의 생애주기 중 '기동 단계'와 '상용 구동 단계'를 독립된 프로세스로 관리하여, 각각의 페이즈에 최적화된 유연한 헬스체크 기준을 부여합니다. | **자동 비활성화:** 일단 기동 성공이 최초 1회 확인되면 Startup Probe는 스스로 영구 비활성화되며, 이때부터 Liveness/Readiness Probe가 메인 감시를 인계받습니다. |

- ### 📊 Startup Probe(스타트업 프로브) 핵심 특징

애플리케이션이 런타임에 진입하기 전, 오직 '최초 부팅 완료' 시점만을 타겟팅하여 컨테이너를 안전하게 보호하고 검증하는 독특한 특징들을 가지고 있습니다.

| 특징 | 📝 상세 설명 | ⚙️ 주요 역할 및 이점 |
| :--- | :--- | :--- |
| **초기화 단계 한정 동작**<br>(Initialization Only) | 컨테이너가 최초로 실행되어 내부 애플리케이션의 기동이 완전히 끝날 때까지만 한시적으로 활성화되며, 목적을 달성하면 스스로 종료됩니다. | • 구동 환경이 완벽히 안정화된 이후에는 메인 감시단인 Liveness/Readiness Probe에게 바통을 확실히 넘겨줍니다.<br>• 생애주기별 역할 분담을 통해 초기화 단계와 일상 실행 단계를 철저히 독립적으로 격리 관리합니다. |
| **유연한 맞춤형 설정 제공**<br>(Flexible Tuning) | 구동 환경이나 앱 개발 환경(예: 무거운 레거시 프레임워크 vs 가벼운 마이크로서비스)에 맞추어 점검 주기, 타임아웃, 실패 임계치를 자유롭게 조율합니다. | • **실무 꿀팁:** 일반적으로 내 애플리케이션의 최대 기동 시간을 계산하여 `failureThreshold(실패 임계 횟수)`를 넉넉하게 확보하는 방식으로 인프라의 유연성을 극대화합니다. |
| **초기화 장애 조기 차단**<br>(Early Boot Failure Fix) | 애플리케이션이 첫 시동을 걸 때 발생하는 고유한 장애들(메모리 부족으로 인한 기동 실패, 설정 파일 바인딩 에러 등)을 핀포인트로 잡아내어 자가 치유를 시도합니다. | • 서버가 제대로 뜨지도 않은 좀비 상태로 방치되거나, 잘못 꼬인 설정 상태에서 유저 요청을 처리하려다 대형 에러를 터뜨리는 아키텍처적 문제를 원천 봉쇄합니다. |


#### 주제 3: QoS Classes
- QoS Classes: Pod의 리소스 관리와 스케줄링을 위한 분류체계
- 각 Pod는 설정된 리소스 요청(Request)과 제한(Limit)에 따라 QoS Class가 부여되며, 이를 통해 쿠버네티스는 노드의 자원을 효과적으로 할당하고, 리소스 부족 상황에서 안정적이고 예측 가능한 방식으로 Pod를 관리할 수 있습니다.
- ### 🎯 QoS Classes를 설정해야 하는 진짜 이유 (현업 관점)

한정된 클러스터 리소스 안에서 유저 서비스의 가용성을 완벽하게 방어하고, 인프라의 가성비와 안정성을 동시에 챙기기 위해 명시적인 QoS 설정을 도입해야 하는 핵심 이유입니다.

| 이유 | 📝 상세 설명 | 🚀 현업 엔지니어의 Real-World Tip |
| :--- | :--- | :--- |
| **안정적인 서비스 제공**<br>(Guaranteed Availability) | 메모리 누수나 갑작스러운 트래픽 폭증으로 노드 리소스가 바닥나는 비상 상황에서도, 결제나 API 관문 같은 핵심 서비스가 중단 없이 가용성과 신뢰성을 유지할 수 있도록 철저히 보호합니다. | 프로덕션 환경에서 가장 중요한 핵심 마이크로서비스는 무조건 `requests`와 `limits`를 1:1로 일치시켜 Guaranteed 등급을 확보해야 안전합니다. |
| **중요도 기반 우선순위 관리**<br>(Business-aligned Priority) | 모든 애플리케이션의 가치가 같을 수 없습니다. 사용자가 체감하는 실시간 API 서비스는 내부 데이터 배치 가공 작업보다 무조건 중요하므로, 비즈니스 가치에 맞는 제거 우선순위를 인프라에 주입합니다. | 배치 처리용 파드나 개발계 서버는 일부러 Burstable이나 BestEffort로 낮춰 설정함으로써, 유사시 핵심 서비스에 자원을 양보하도록 설계하는 것이 표준 아키텍처입니다. |
| **자동화된 지능형 자원 관리**<br>(Automated Resource Allocation) | 운영자가 장애 상황마다 어떤 파드를 죽이고 살릴지 수동으로 긴급 개입할 필요 없이, 쿠버네티스가 미리 정해둔 규칙대로 알아서 메모리를 회수하고 유연하게 자원을 배분합니다. | 인프라 운영자가 매번 새벽에 일어나 OOM 장애를 직접 복구하던 수고를 획기적으로 덜어주는 선언적 인프라(IaC)의 핵심 축입니다. |
| **전체 클러스터 안정성 보장**<br>(Cluster Level Stability) | 리소스 한계 임박 시 덜 중요한 파드부터 순차적으로 퇴출(Eviction) 및 격리하여, 노드 전체가 통째로 다운되거나 커널이 뻗어 모든 서비스가 한 번에 죽는 최악의 참사를 방지합니다. | 개별 파드 몇 개가 일시적으로 종료되는 것이 노드 전체가 마비되어 백여 개 파드가 전멸하는 것보다 백배 낫기 때문에 타협할 수 없는 보험과 같습니다. |
| **유연한 리소스 활용 극대화**<br>(Resource Efficiency) | `Burstable`이나 `BestEffort` 같은 유연한 등급 설정을 활용해 평소에는 남는 자원을 서로 나누어 쓰게 함으로써, 오버프로비저닝(자원 낭비)을 줄이고 클러스터 가성비를 극대화합니다. | 24시간 풀 가동되지 않는 캐시나 유틸리티 성격의 서버들은 Burstable로 묶어 두면, 평소에는 자원을 최소한만 점유하며 클러스터 효율을 크게 높여줍니다. |

- ### 🚦 QoS 3대 클래스 상세 분석

| QoS Class | ⚙️ 결정 조건 (리소스 설정 방식) | 📝 클래스 특징 및 영속성 | 💡 YAML 설정 예시 |
| :--- | :--- | :--- | :--- |
| **Guaranteed**<br>(최상위 보장) | • 파드 내 **모든 컨테이너**의 CPU, Memory에 `requests`와 `limits`가 **모두 설정**되어야 합니다.<br>• **`requests` 값과 `limits` 값이 완벽히 동일**해야 합니다. | • 자원 안정성과 신뢰성이 가장 높은 등급입니다.<br>• 노드가 자원 고갈 상태에 빠지더라도 **가장 마지막까지 보호**받으며 퇴출을 유예합니다. | ```yaml\nresources:\n  requests:\n    memory: "500Mi"\n    cpu: "500m"\n  limits:\n    memory: "500Mi"\n    cpu: "500m"\n``` |
| **Burstable**<br>(유연한 대처) | • `requests`나 `limits` 중 하나라도 설정되었으나 **Guaranteed 조건을 만족하지 못하는 경우**입니다.<br>• 일부 컨테이너만 설정되었거나, **`requests` < `limits`** 인 상황입니다. | • 최소 보장 자원(`requests`)은 확보하되, 필요 시 상한선(`limits`)까지 유연하게 자원을 더 끌어다 씁니다.<br>• 자원 고갈 시 **OOM 스코어(사용률)**에 따라 퇴출될 수 있습니다. | ```yaml\nresources:\n  requests:\n    memory: "256Mi"\n    cpu: "250m"\n  limits:\n    memory: "500Mi"\n    cpu: "500m"\n``` |
| **BestEffort**<br>(최선 공유) | • 파드 내 **어떤 컨테이너에도** `requests`와 `limits` 설정을 **단 하나도 하지 않은 경우**입니다. | • 사전에 보장받는 자원이 전혀 없습니다.<br>• 평소에는 노드의 남는 자원을 제한 없이 자유롭게 쓰지만, **자원이 조금만 부족해져도 가장 먼저 1순위로 강제 퇴출**됩니다. | ```yaml\nresources: {}\n``` |

> **❓ OOM (Out Of Memory) 이란?**
> 시스템에서 사용 가능한 물리 메모리가 완전히 바닥났을 때 발생하는 비상 상태입니다. 운영체제(OS) 커널이나 쿠버네티스는 시스템 붕괴를 막기 위해 **더 이상 메모리를 할당해 줄 수 없는 한계점**에서 특정 프로세스(컨테이너)를 강제로 즉시 종료(Kill)시키며, 이를 **OOM-Killed**라고 부릅니다.

### 📊 QoS Class별 리소스 관리 및 동작 구조

자원 가용성 수준에 따라 쿠버네티스가 각 등급의 파드를 어떻게 대우하고 관리하는지 정의한 명세입니다.

| 구분 | ⚖️ 평상시 자원 활용 방식 | 🚨 자원 부족(노드 압박) 발생 시 동작 방식 |
| :--- | :--- | :--- |
| **Guaranteed** | 지정된 자원 크기만큼 노드 내에 확실한 물리 영역을 예약받아 독점 사용합니다. | 노드 자원이 극도로 고갈되어도 시스템 데몬을 제외하고는 가장 마지막까지 안전하게 보존됩니다. |
| **Burstable** | 기본적으로 `requests`만큼은 보장받으며, 노드에 여유 자원이 있을 때에만 `limits` 범위까지 추가 확장하여 사용합니다. | 요청량(`requests`)을 초과하여 자원을 오버클록해 쓰고 있던 파드들이 우선적으로 퇴출 가시권에 들어옵니다. |
| **BestEffort** | 설정값 제한이 없으므로 노드 내 유휴 자원이 풍부할 때는 아무런 제약 없이 최대 성능을 낼 수 있습니다. | 노드에 조금이라도 자원 병목이 시작되면 유예기간 없이 **가장 먼저 즉각적인 퇴출(Eviction) 대상**이 됩니다. |

### 🚨 자원 부족 상황에서의 파드 제거(Eviction) 우선순위

노드 메모리나 CPU가 고갈될 때, 쿠버네티스가 자원 확보를 위해 파드를 종료시키는 순위표입니다.

```text
[자원 고갈 발생!] ───► 1순위 퇴출: BestEffort (설정 없는 파드 전멸)
                             │
                             ▼
                        2순위 퇴출: Burstable (OOM 스코어가 높은 녀석부터 순차 제거)
                             │
                             ▼
                        3순위 퇴출: Guaranteed (끝까지 생존, 최후의 보루)
```
#### 파드 퇴출 (Pod Eviction) 메커니즘

* **파드 퇴출(Eviction) 정의:** 워커 노드(Worker Node)의 핵심 물리 자원이 한계치에 다다랐을 때, 노드 전체가 뻗는 최악의 참사를 막기 위해 노드 감시 장치인 **`kubelet`이 특정 파드를 강제로 종료하고 쫓아내는 자가 방어 프로세스**입니다.
* **본질적인 목적:** 시스템 과부하로 노드 전체의 모든 파드가 전멸하기 전에, 중요도가 낮은 자원을 선제적으로 정리하여 **인프라 전체의 안정성을 확보**하는 데 있습니다.

---

### 🔍 어떤 자원이 부족할 때 퇴출(Eviction)이 발생할까?

쿠버네티스는 노드별로 할당 가능한 물리적 한계선이 정해져 있으며, 아래 **3가지 임계치**를 넘어서면 즉시 퇴출 작전에 돌입합니다.

| 부족 자원 종류 | 📝 상세 원인 및 발생 시나리오 | 🚨 인프라에 미치는 영향 및 결과 |
| :--- | :--- | :--- |
| **물리 메모리**<br>(Memory) | 애플리케이션의 메모리 누수(Memory Leak)나 갑작스러운 트래픽 폭증으로 노드의 가용 RAM이 바닥날 때 발생합니다. | 시스템이 먹통이 되기 전, QoS 클래스 등급이 낮은 파드부터 순차적으로 사형 선고를 내립니다. |
| **디스크 공간**<br>(Disk Space) | • **노드 파일 시스템:** 애플리케이션 로그(`stdout/stderr`)가 무분별하게 쌓여 디스크를 채울 때<br>• **이미지 파일 시스템:** 안 쓰는 컨테이너 이미지들이 노드 하드디스크를 가득 채울 때 | 디스크 쓰기 권한이 막혀 노드 전체가 무력화되는 것을 막기 위해 임시 파일과 파드를 정리합니다. |
| **프로세스 ID**<br>(PID Limits) | 애플리케이션 소스 코드 내에서 스레드나 자식 프로세스를 무한정 생성하여 **노드에 할당된 최대 PID 개수**를 초과할 때 발생합니다. | 리눅스 커널 수준에서 더 이상 새로운 프로세스를 띄울 수 없는 프로세스 고갈 상태를 방지하기 위해 해당 파드를 격리합니다. |
