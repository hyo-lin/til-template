# ☸️ Kubernetes HPA (Horizontal Pod Autoscaler) 

> **💡 HPA란?**
> 애플리케이션의 부하(CPU, 메모리, 사용자 정의 메트릭 등)를 실시간 모니터링하여 Deployment와 같은 워크로드의 **Pod 개수를 자동으로 수평 확장(Scale-out)하거나 축소(Scale-in)**하는 쿠버네티스 컨트롤러입니다.

---

## 1. HPA가 해결하는 문제 & 도입 이유

### ❌ 고정된 Pod 수의 한계 (HPA 미사용 시)

* **트래픽 증가:** Pod이 처리할 수 있는 범위를 초과하여 응답 지연 및 장애 발생
* **트래픽 감소:** 사용하지 않는 Pod이 계속 실행되어 CPU·메모리 및 인프라 비용 낭비
* **갑작스러운 변화:** 엔지니어가 직접 `kubectl scale`로 수정하기 전까지 대응 불가능
* **반복적인 운영 비용:** 엔지니어가 24시간 모니터링하며 수동으로 개수를 조절해야 함

### ⭕ HPA 도입의 핵심 목적

1. **부하 대응 자동화:** 이벤트, 쿠폰 발급, 타임 세일 등 트래픽이 몰릴 때 자동으로 스케일 아웃
2. **운영 안정성 및 여유 자원 확보:** 트래픽 감소 시 Pod을 줄여 클러스터 내 여유 리소스 확보
3. **대규모 클러스터 운영 자동화:** 수백 개의 노드와 수천 개의 Pod 환경에서 제어 루프(Control Loop)를 통해 수동 개입 최소화

---

## 2. HPA 동작 원리 및 구성 요소

### 🔄 HPA 제어 루프 (Control Loop)

```text
현재 상태 측정 ➔ 목표 상태와 비교 ➔ 필요 Pod 수 계산 ➔ Deployment replicas 변경 ➔ 새로운 상태 재측정

```

HPA는 **Pod을 직접 생성하거나 삭제하지 않습니다.** Deployment의 `replicas` 값만 수정하며, 실제 Pod 관리는 Deployment와 ReplicaSet이 담당합니다.

### 🏗️ 주요 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| **HPA 리소스** | 필요 Pod 개수를 계산하고 대상 워크로드의 `replicas` 변경 |
| **Deployment** | 애플리케이션 배포 상태 및 ReplicaSet 관리 |
| **ReplicaSet** | HPA가 변경한 `replicas` 수치에 맞게 실제 Pod 생성/삭제 유지 |
| **Metrics Server** | Node와 Pod의 CPU/메모리 사용량을 수집하여 Metrics API 제공 |
| **Resource requests** | **HPA가 CPU·메모리 사용률(%)을 계산할 때 기준이 되는 핵심 값** |

---

## 3. Metrics Server vs Prometheus (PLG Stack)

### 📊 Metrics Server란?

* `kube-system` 네임스페이스에 Deployment 형태로 설치되는 별도의 인메모리 수집 앱
* Kubelet에서 수집한 메트릭을 `metrics.k8s.io` API 형태로 제공 (`kubectl top`, 기본 HPA/VPA 활용)
* **장기 저장 기능이 없으며, 현재 시점의 실시간 계기판 역할** 수행

### ⚔️ Metrics Server vs Prometheus 비교

| 구분 | Metrics Server | Prometheus |
| --- | --- | --- |
| **주요 목적** | HPA·VPA 스케일링 및 `kubectl top` 지원 | 모니터링, 데이터 분석, 장애 알림 |
| **수집 데이터** | Node / Pod의 기본 CPU, Memory | CPU, Memory, HTTP 요청 수, Latency 등 전체 |
| **데이터 저장** | 장기 저장 안 함 (인메모리) | 시계열 데이터베이스(TSDB) 장기 저장 |
| **시각화** | 없음 | Grafana 연동 시각화 |
| **HPA 연동 방식** | 기본 CPU/Memory HPA에서 바로 사용 | 별도의 **Prometheus Adapter** 필요 (`custom.metrics.k8s.io`) |

## 4. 리소스 계산 방식 및 계산 공식

### ⚠️ 핵심: CPU 사용률의 기준은 `limit`이 아니라 `request`!!

HPA에서 설정하는 `averageUtilization: 60`은 **노드 전체**나 **`limits`** 기준이 아니라, **`requests` 대비 실제 사용량 비율**입니다.

$$\text{CPU 사용률(\%)} = \left( \frac{\text{실제 CPU 사용량}}{\text{CPU request}} \right) \times 100$$

### 📐 HPA 필요 Pod 수 계산 공식

$$\text{필요한 Pod 수} = \left\lceil \text{현재 Pod 수} \times \left( \frac{\text{현재 평균 메트릭 값}}{\text{목표 메트릭 값}} \right) \right\rceil$$


*(※ 계산 결과는 무조건 올림 처리)*

* **계산 예시:**
* 현재 Pod 수: `2개`, 현재 평균 CPU 사용률: `90%`, 목표 사용률: `60%`
* $\text{필요 Pod 수} = \text{올림}\left( \frac{2 \times 90}{60} \right) = \text{올림}(3.0) = \mathbf{3\text{개}}$

## 5. HPA & Deployment YAML 예시

### 📄 Deployment 정의 (`deployment.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
spec:
  # replicas: 2 (HPA 사용 시 주석 처리 권장)
  selector:
    matchLabels:
      app: web-api
  template:
    metadata:
      labels:
        app: web-api
    spec:
      containers:
        - name: web-api
          image: example/web-api:1.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi

```

### 📄 HPA 정의 (`hpa.yaml`)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  behavior: # 잦은 스케일링(Flapping) 방지 설정
    scaleUp:
      stabilizationWindowSeconds: 0 # 부하 발생 시 즉시 확장
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60 # 60초당 최대 4개씩 확장
    scaleDown:
      stabilizationWindowSeconds: 300 # 축소 시 5분간 지연 관찰
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60 # 60초당 최대 25%씩 축소

```


---

### ⚡ HPA 스케일링 속도 제어 (`behavior`)

#### 1. 플래핑(Flapping) 문제란?

부하 변화에 따라 HPA가 Pod 수를 너무 즉각적으로 조정할 때 발생하는 **시스템 불안정 현상**입니다.

```text
부하 급증 ➔ Pod 빠르게 확장 ➔ 부하 일시적 감소 ➔ Pod 즉시 축소 ➔ 다시 부하 급증 ➔ Pod 재확장 (무한 반복)

```

* **발생 원인:** Pod은 노드 스케줄링, Affinity, 컨테이너 생성 및 Initialization, Readiness Probe 통과 등 실제 트래픽을 받기까지 **초기화 시간**이 필요합니다.
* **문제점:** 준비 시간이 필요한 Pod이 채 자리 잡기도 전에 줄어들었다가 다시 늘어나기를 반복하면 **서비스 안정성이 심각하게 저하**됩니다.

---

#### 2. `behavior` 필드를 통한 스케일링 정책 제어

Kubernetes 1.18+ (`autoscaling/v2`)부터 제공되는 `behavior` 설정을 통해 **스케일 아웃(Scale-Up)은 빠르게, 스케일 인(Scale-Down)은 신중하게** 제어할 수 있습니다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60

  # 스케일링 속도 및 안정화 정책
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0    # 확장은 대기 시간 없이 즉시 판단
      policies:
        - type: Pods
          value: 4                     # 60초 동안 최대 4개까지만 증가
          periodSeconds: 60

    scaleDown:
      stabilizationWindowSeconds: 300  # 축소 전 최근 5분(300초)간의 최대 부하 상태 고려
      policies:
        - type: Percent
          value: 25                    # 60초 동안 현재 Pod 수의 최대 25%까지만 감소
          periodSeconds: 60

```

---

#### 3. 주요 설정 항목 및 의미

| 설정 필드 | 주요 의미 | 상세 설명 |
| --- | --- | --- |
| **`scaleUp.stabilizationWindowSeconds: 0`** | **즉시 확장** | 부하 발생 시 별도의 안정화 대기 시간 없이 즉시 Pod 확장을 시작합니다. |
| **`scaleUp.policies`** | **확장 폭 제한** | `type: Pods, value: 4, periodSeconds: 60` ➔ 60초 동안 최대 4개의 Pod까지만 늘립니다. (급격한 클러스터 리소스 고갈 방지) |
| **`scaleDown.stabilizationWindowSeconds: 300`** | **축소 유예 시간** | 축소 판단 시 바로 줄이지 않고 **최근 5분(300초) 동안의 계산값 중 가장 높았던 추천치**를 고려하여 일시적 부하 감소 시의 잦은 스케일 인을 방지합니다. |
| **`scaleDown.policies`** | **축소 폭 제한** | `type: Percent, value: 25, periodSeconds: 60` ➔ 60초 동안 현재 전체 Pod 수의 최대 25%까지만 단계적으로 줄입니다. |

## 6. ArgoCD(GitOps) 사용 시 충돌 해결 방법

### 💥 문제 상황 (Controller Race Condition)

1. HPA가 부하를 감지해 `replicas`를 `2 ➔ 5`로 변경
2. ArgoCD가 클러스터를 감시하다 Git 저장소(`replicas: 2`)와 다름을 감지하고 `5 ➔ 2`로 원복
3. HPA와 ArgoCD 간 무한 복구 충돌 발생

### 🛠️ 실무 해결 표준

#### 방법 1: Deployment YAML에서 `spec.replicas` 필드 아예 제거 (가장 권장)

* Git에는 배포 스펙(이미지, 환경변수 등)만 선언하고, 복제본 수(`replicas`) 관리는 완전히 HPA에게 위임합니다.

#### 방법 2: ArgoCD 설정에 `ignoreDifferences` + `RespectIgnoreDifferences` 적용

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      name: web-api
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true # 최초 배포 이후 Sync 시에도 replicas 차이를 무시

```

## 7. HPA 핵심 요약 

1. HPA는 Pod의 단일 성능을 높이는 게 아니라 Pod의 개수를 조절(수평 확장)한다.
2. HPA는 Pod을 직접 건드리지 않고 대상 워크로드의 `replicas`를 수정한다.
3. CPU Utilization 계산의 분모는 `limit`이 아닌 `request`다.
4. 기본 CPU/메모리 HPA를 구동하려면 **Metrics Server**가 필수다.
5. HPA가 Pod 수를 늘려도 **노드에 남은 리소스(CPU/Memory)가 없으면 Pod은 `Pending` 상태**에 빠진다.
6. 새 Pod이 뜬다고 즉시 트래픽을 받는 것은 아니며, Node 스케줄링 및 **Readiness Probe 검사 시간**이 소요된다.
7. 급격한 스케일 인으로 인한 성능 저하를 막기 위해 **`behavior` 정책**을 활용한다.
8. HPA는 **Stateless(상태가 없는) 애플리케이션**에서 가장 효과적이다.
9. HPA는 앱 내부의 코드 버그나 **DB 병목 현상을 해결해 주지 않는다.**
10. 실무 구축 시 **`requests` 명시, `min/maxReplicas` 설정, Readiness Probe**를 반드시 함께 설계해야 한다.

#### 주제 2: VPA

# ☸️ VPA (Vertical Pod Autoscaler) 

> **💡 VPA 핵심 요약**
> Pod의 **실제 CPU·메모리 사용 이력을 분석**하여 컨테이너의 적절한 **Resource Requests(요청량) 및 Limits(제한량)**를 자동으로 계산하고 맞춰주는 **쿠버네티스 수직 오토스케일링 애드온**입니다.

---

## 1. VPA가 필요한 이유 (Right-Sizing)

개발자가 처음 Pod을 작성할 때 CPU/메모리를 얼마로 설정해야 할지 정확히 알기 어렵습니다.

* **Requests를 너무 낮게 잡은 경우:**
* Node 스케줄러는 `requests` 기준으로 Pod을 배치하므로, 실제 부하 시 CPU Throttling이 발생하거나 OOMKilled(Out Of Memory)로 Pod이 강제 종료됩니다.


* **Requests를 너무 높게 잡은 경우:**
* 실제 사용량은 적은데 노드 자원을 크게 예약해버려 **클러스터 자원 낭비 및 인프라 비용 비효율**이 발생합니다.



👉 **VPA는 이 `requests` 수치를 실제 애플리케이션 사용 패턴에 맞춰 가장 적절한 크기로 맞춰줍니다.**

---

## 2. VPA의 3가지 핵심 내부 컴포넌트

VPA는 3개의 독립된 컨트롤러 파드가 협력하여 동작합니다.

```text
       [ Metrics Server / Prometheus ]
                     │
                     ▼ (사용량 데이터 수집)
             ┌───────────────┐
             │  Recommender  │ ➔ 적절한 권장값 계산 (status.recommendation에 저장)
             └───────┬───────┘
                     │
         ┌───────────┴───────────┐
         ▼                       ▼
  ┌─────────────┐     ┌──────────────────────┐
  │   Updater   │     │ Admission Controller │
  └──────┬──────┘     └──────────┬───────────┘
         │ (기존 Pod 제거)        │ (신규 Pod에 권장값 주입)
         ▼                       ▼
  [ Pod Eviction ]      [ K8s API Server / Pod Creation ]

```

1. **Recommender (추천기):**
* Pod의 현재/과거 CPU 및 메모리 사용량, OOM 발생 이력을 계속 수집 및 분석합니다.
* 계산된 추천 리소스 값을 VPA Custom Resource의 `status.recommendation` 필드에 기록합니다.


2. **Updater (갱신기):**
* 현재 실행 중인 Pod의 `requests`와 Recommender의 추천값을 비교합니다.
* 차이가 크면 기존 Pod을 Eviction(제거)하여 Deployment가 새 Pod을 다시 띄우도록 만듭니다.


3. **Admission Controller (승인 컨트롤러):**
* API Server로 전달되는 신규 Pod 생성 요청을 가로채 **Recommender가 계산한 권장 리소스 값을 Pod 스펙에 주입**합니다.



---

## 3. VPA Recommender의 추천 수치 읽는 법

VPA를 생성하고 `kubectl get vpa <vpa-name> -o yaml`을 조회하면 아래와 같은 `recommendation` 정보가 출력됩니다.

```yaml
status:
  recommendation:
    containerRecommendations:
      - containerName: app
        target:          # 🎯 가장 권장하는 설정값 (가장 중요)
          cpu: 250m
          memory: 300Mi
        lowerBound:      # 🔽 최소 권장 범위 (이보다 낮으면 스케일 업 필요)
          cpu: 100m
          memory: 128Mi
        upperBound:      # 🔼 최대 권장 범위 (이보다 높으면 스케일 다운 필요)
          cpu: 500m
          memory: 512Mi
        uncappedTarget:  # 🔓 minAllowed/maxAllowed 제약 조건을 적용하기 전 순수 계산값
          cpu: 250m
          memory: 300Mi

```

## 4. VPA `updatePolicy` (업데이트 모드) 4가지

`spec.updatePolicy.updateMode` 설정을 통해 VPA가 추천된 리소스 값을 Pod에 어떻게 반영할지 제어합니다.

| updateMode | 동작 방식 | 설명 및 특징 |
| --- | --- | --- |
| **`Off`** | **추천만 함 (적용 X)** | **[실무 최선선호]** Pod에 아무런 영향을 주지 않고 추천치 데이터만 계산합니다. 모니터링 후 사람이 수동 반영할 때 사용합니다. |
| **`Initial`** | **최초 생성 시만 적용** | Pod이 **처음 뜰 때만** Admission Controller가 권장값을 주입합니다. 실행 중인 Pod은 절대 건드리지 않아 재시작 위험이 없습니다. |
| **`Recreate`** | **재시작을 통한 적용** | **[기존 디폴트]** 실행 중인 Pod의 `requests`와 추천치 차이가 크면 **Pod을 강제로 Eviction(제거) 후 재생성**하여 적용합니다. |
| **`InPlace`** | **무재시작 실시간 적용** | *(K8s 1.33+ / InPlacePodVerticalScaling 기능)* **Pod을 재시작하지 않고** CPU/Memory 수치를 실시간으로 변경합니다. (노드 자원 부족 시 Eviction으로 전환) |

---

## 5. VPA 실무 배포 YAML 스펙 (`vpa.yaml`)

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: express-vpa
  namespace: default
spec:
  # VPA를 적용할 워크로드 대상 지정
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: express-app

  # 업데이트 정책 설정 (안전하게 Off 모드로 수집 후 검토 권장)
  updatePolicy:
    updateMode: "Off"

  # 리소스 최소/최대 안전 제약 조건 설정 (필수!)
  resourcePolicy:
    containerPolicies:
      - containerName: express
        minAllowed:
          cpu: 50m
          memory: 64Mi
        maxAllowed:
          cpu: "2"
          memory: 2Gi
        controlledResources:
          - cpu
          - memory

```

---

## 6. VPA 실무 운영 시 주의사항 및 팁

1. **`minAllowed` / `maxAllowed`는 반드시 설정할 것**
* VPA가 순간적인 메모리 튐 현상 때문에 추천값을 무한정 높여버리면, 해당 Pod이 노드 스펙보다 커져 스케줄링 실패(`Pending`)에 빠집니다.


2. **`replicas: 1`인 단일 Pod 서비스에 `Recreate` 모드 적용 금지**
* `Recreate` 모드는 기존 Pod을 지우고 다시 띄우므로, 파드가 1개뿐이라면 **재생성되는 동안 서비스 다운타임**이 발생합니다.


3. **StatefulSet(DB 등) 환경에서의 주의**
* DB나 캐시 서버 등은 재시작 시간이 길기 때문에, VPA에 의해 Pod이 Eviction되면 클러스터 장애로 이어질 수 있으므로 `Off` 또는 `Initial` 모드 사용이 안전합니다.


4. **VPA가 Pod을 키운다고 Node가 저절로 늘어나는 것은 아님**
* VPA는 Pod 스펙을 변경할 뿐이며, 변경된 Pod을 수용할 노드 자원이 부족하면 Cluster Autoscaler(CA)가 별도로 노드를 늘려주어야 합니다.

---
#### 주제 3: CA

# ☸️ Kubernetes CA (Cluster Autoscaler)

> **💡 CA란?**
> Pod을 배치할 노드 공간이 부족할 때 **Worker Node를 늘리고(Scale-Out)**, 리소스가 낭비되는 불필요한 노드가 생기면 **줄이는(Scale-In)** 노드 단위의 인프라 자동 확장 도구입니다.

---

## 1. CA가 해결하는 문제 & 핵심 원리

### ❌ HPA / VPA 만으로 해결할 수 없는 한계

* HPA와 VPA는 Pod의 개수나 스펙을 늘려줍니다.
* 하지만 클러스터 내 모든 노드의 물리적 리소스(CPU/메모리)가 이미 꽉 차 있다면, 신규 Pod은 노드에 배치되지 못하고 **`Pending` / `Unschedulable` 상태**로 대기하게 됩니다.

### ⭕ CA의 핵심 판단 기준 (Resource Usage가 아닌 Scheduling 가능 여부!)

* HPA/VPA처럼 **"현재 노드의 실제 CPU/메모리 사용량 %"를 보지 않습니다.**
* **"현재 `Pending` 상태인 Pod이 존재하는가?"** 및 "해당 Pod의 Resource Requests를 수용할 노드가 클러스터 내에 있는가?"를 기준으로 동작합니다.

```text
Pod 생성 ➔ kube-scheduler가 배치 가능한 노드 검색 ➔ 배치 실패 (Pending / Unschedulable) ➔ CA가 노드 증설 필요성 검토

```

---

## 2. 노드 증설(Scale-Out) & 축소(Scale-In) 동작 방식

### 📈 노드 증설 (Scale-Out)

* CA는 노드를 **"직접"** 생성하지 않습니다.
* AWS의 **Auto Scaling Group (ASG)** 등 클라우드 인프라 제공자의 인스턴스 그룹을 감시하며, 노드가 더 필요하다고 판단되면 ASG의 `Desired Capacity` 수치만 증가(예: 2 ➔ 3)시킵니다.
* 실제 EC2 인스턴스 생성 및 스케일링은 AWS ASG가 수행합니다.
* *(참고: 최근에는 ASG의 한계 및 속도를 극복하기 위해 EC2 템플릿을 직접 제어하여 훨씬 빠르고 유연하게 노드를 구동하는 **Karpenter(카펜더)** 도구를 EKS 환경에서 많이 활용합니다.)*



### 📉 노드 축소 (Scale-In)

* 노드 이용률이 낮다고 바로 삭제하지 않으며, 아래 조건을 모두 만족하여 **안전하게 퇴거 가능할 때만 노드를 제거**합니다.

| 확인 항목 | 설명 및 제약 조건 |
| --- | --- |
| **다른 노드 이동 가능 여부** | 해당 노드에서 실행 중인 Pod들을 다른 노드로 이사시킬 수 있어야 합니다. |
| **타 노드 리소스 여유** | 이동시킬 대상 노드들에 CPU·메모리 공간이 충분해야 합니다. |
| **스케줄링 조건 만족** | `nodeSelector`, `Affinity`, `Taint/Toleration` 등 제약 조건을 타 노드가 만족해야 합니다. |
| **안전 퇴거 정책** | `PodDisruptionBudget (PDB)` 등의 최소 가용성 정책을 위반하지 않아야 합니다. |
| **로컬 데이터 종속성** | 노드에 종속된 Local Volume 데이터나 `hostPath` 등이 지정된 Pod이 없어야 합니다. |

---

## 3. HPA vs VPA vs CA 삼총사 비교

| 구분 | HPA (Horizontal) | VPA (Vertical) | CA (Cluster Autoscaler) |
| --- | --- | --- | --- |
| **확장 대상** | Pod 개수 | Pod의 CPU / Memory `requests` | **Worker Node 개수** |
| **확장 방향** | 수평 확장 | 수직 확장 | **클러스터 수평 확장** |
| **주요 판단 기준** | CPU, 메모리, Custom Metric | 과거/현재 CPU, 메모리 사용 이력 | **스케줄링 불가능한(`Pending`) Pod 유무** |
| **변경 결과** | `replicas` 수치 변경 | `requests` 수치 변경 | **노드 그룹 크기(`Desired Capacity`) 변경** |
| **인프라 연동** | 불필요 | 불필요 | **AWS ASG 등 클라우드 인프라 연동 필수** |

---

## 4. 자체 구축(kubeadm) vs EKS에서의 CA 구성 차이

EKS와 같은 관리형 서비스가 아닌 `kubeadm` 기반 자체 구축 클러스터에서 CA를 적용하려면 노드가 클러스터에 자동으로 가입(`join`)할 수 있는 프로비저닝 구조가 수동으로 설계되어야 합니다.

### 🛠️ `kubeadm` + CA 연동을 위한 4가지 필수 요소

1. **Worker Node 전용 Custom AMI 구축:**
* 새 EC2가 생성되자마자 즉시 구동될 수 있도록 `containerd`, `kubelet`, `kubeadm`, CNI 패키지, 커널 설정 등을 미리 구워둔 **골든 이미지(AMI)** 준비


2. **`User Data`를 통한 자동 Join 처리:**
* EC2 인스턴스 부팅 시 실행될 Shell Script로 `kubeadm join <Master-IP>:6443 --token ...` 자동 수행


3. **AWS Auto Scaling Group (ASG) 설정:**
* 최소(Min), 최대(Max), 희망(Desired) 인스턴스 개수 범위를 정의한 ASG 구성


4. **CA 전용 IAM 권한 부여:**
* Master Node / CA Controller가 AWS API를 호출하여 ASG 조회, 인스턴스 생성/종료 요청, Desired Capacity 수치를 변경할 수 있는 IAM Policy 부여



### 🏢 현실적인 실무 인프라 구성 패턴

1. **`kubeadm` + 수동 노드 관리 (CA 미사용):** 소규모 환경이나 베어메탈 서버 환경
2. **`kubeadm` + ASG + CA:** 인프라 설정 난이도가 매우 높고 관리가 까다로움
3. **EKS + CA / Karpenter (가장 일반적):** AWS 관리형 K8s 서비스와 Karpenter 결합으로 완벽한 자동화 달성

---

## 💡 Autoscaler 종합 최종 요약

* **HPA:** 애플리케이션 트래픽 변화에 맞춰 **Pod의 개수**를 늘리거나 줄인다.
* **VPA:** 애플리케이션의 리소스 사용 이력을 보고 **Pod 1개의 CPU/Memory Requests 스펙**을 맞춘다.
* **CA:** Pod을 배치할 노드가 모자라 **`Pending`이 발생하면 Node를 추가**하고, 남으면 **Node를 제거**한다.
