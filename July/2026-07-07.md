### 새로 배운 내용
#### 주제 1: 무중단 배포
- Zero-downtime deployment: 사용자의 입장에서 서비스 중단 없이 애플리케이션을 업데이트하거나 배포하는 방식
  - 서비스 이용자에게 중단 없이 안정적인 기능 업데이트를 제공하기 위해서
- 다운타임: 서버스가 요청을 처리하지 못하는 시간
- 새 버전을 먼저 준비하고 준비가 완료된 뒤 트래픽을 전환한다. 그리고 정상 작동하면, 기존 버전을 종료한다.
- Connection Draining or Graceful Shutdown: 이미 처리 중인 요청을 마무리할 시간을 주는 방식
- 무중단 배포 시 고려사항
  - 애플리케이션은 가능하면 Stateless하게 설계
  - 데이터베이스 변경은 무중단이어도 문제가 많이 발생
  - 롤백은 “배포 실패 시”가 아니라 “지표가 불안정”할 때
- ### ⚙️ 점진적 배포의 핵심 구성 요소 및 역할

| 구성 요소 | 📋 역할 |
| --- | --- |
| **다중 인스턴스 또는 다중 컨테이너** | 기존 버전과 새 버전을 동시에 실행하여 중단 없는 환경을 구성합니다. |
| **로드밸런서 / 리버스 프록시** | 사용자 요청을 정상 서버로 분산하고, 버전 간 트래픽 흐름을 제어합니다. |
| **헬스 체크** | 새 버전이 실제 요청을 받을 준비가 되었는지(런타임 정합성) 확인합니다. |
| **트래픽 전환 정책** | 기존 버전과 새 버전 사이의 요청 비율을 설정된 규칙에 따라 조절합니다. |
| **롤백 전략** | 새 버전에 문제가 생기면 이전 버전의 안정적인 상태로 즉시 복귀합니다. |
| **모니터링** | 배포 후 오류율 · 응답 시간 · 리소스 상태를 실시간으로 확인합니다. |
| **CI/CD 파이프라인** | 빌드 · 테스트 · 배포 과정을 완전히 자동화하여 일관된 절차를 보장합니다. | 

#### 주제 2: Blue/Green Deployment
- Blue/Green Deployment: 두 개의 독립된 환경(블루, 그린)을 운영하며, 트래픽을 새로운 버전으로 전환해 서비스 중단 없이 배포와 롤백이 가능한 배포 방식
  - 두 개의 완전 분리된 환경에서 새 버전을 검증한 뒤 트래픽 스위치만으로 즉시 롤아웃·롤백할 수 있어 무중단 배포 과정을 단순화하여 배포할 수 있기 때문에
    - **롤아웃:** 소프트웨어의 **새로운 버전을 실제 운영 환경에 단계적으로 적용해 나가는 과정 전체**
    - **롤백:**  운영 환경에 배포된 새 버전에서 문제가 발생했을 때, 즉시 이전 안정적인 버전으로 되돌리는 작업

- ### 🚀 무중단 배포: Blue-Green 배포 구성 요소

| 구성 요소 | 📋 설명 |
| --- | --- |
| **Blue 환경** | 현재 서비스 중인 운영 환경으로, 사용자가 실제로 접근하고 있는 버전입니다. |
| **Green 환경** | 새로운 애플리케이션 버전이 배포되는 대기 중인 환경이며, 전환 준비가 완료되면 서비스 대상이 됩니다. |
| **트래픽 전환 도구** | Nginx, AWS ALB, 로드 밸런서 등, Blue에서 Green으로 사용자의 요청을 즉시 전환할 수 있도록 설정을 변경하는 구성 요소입니다. |
| **헬스 체크 및 모니터링** | Green 환경이 정상적으로 동작하는지 사전 검증하는 절차로, 전환 후에도 안정성을 확보할 수 있습니다. |
| **롤백 메커니즘** | Green 전환 이후 문제가 생겼을 때, 빠르게 Blue로 복귀할 수 있도록 설계된 자동 혹은 수동 복원 절차입니다. |

- ### 🔄 무중단 배포: Blue-Green 배포 프로세스 흐름 (Deployment Flow)

| 단계 | 프로세스명 | 설명 |
| --- | --- | --- |
| **1** | **안정 서비스 유지 (Blue)** | 현재 운영 중인 버전(Blue)이 안정적으로 사용자에게 서비스를 제공 중인 상태입니다. |
| **2** | **신규 버전 준비 (Green)** | 새로운 버전(Green)을 Blue와 동일한 환경에 미리 배포하고 구동을 준비합니다. |
| **3** | **안정성 검증 및 트래픽 전환** | 헬스 체크 또는 QA 등을 통해 Green의 안정성이 검증되면, 로드 밸런서 설정을 변경하여 사용자의 트래픽을 Green으로 즉시 전환합니다. |
| **4** | **모니터링 및 사후 조치** | 전환 후 시스템에 문제가 없으면 기존 Blue 환경을 종료하거나 다음 배포를 위해 대기 상태로 유지합니다. |
| **5** | **즉시 복구 (Rollback)** | 만약 트래픽 전환 후 예상치 못한 문제가 발생할 경우, 트래픽을 다시 기존 Blue 환경으로 즉시 되돌려(롤백) 장애를 방지합니다. |



#### 주제 3: Rolling Deployment
- Rolling Deployment: 기존 인스턴스를 하나씩 새로운 버전으로 순차 교체하며 전체 서비스를 점진적으로 업데이트하는 배포 방식
  - 서버를 일정 단위로 순차 교체해 전체 서비스를 중단 없이 새 버전을 점진 배포하고, 문제가 생겨도 영향을 받은 인스턴스만 교체해 영향을 최소화할 수 있기 때문
- ### 📊 배포 전략 비교: In-place 방식 vs Side-by-side 방식

| 항목 | 🔄 In-place (교체 실행 방식) | ⇄ Side-by-side (동시 실행 방식) |
| --- | --- | --- |
| **기본 개념** | 기존 인스턴스를 하나씩 종료하고 그 자리에 새 버전을 실행 | 기존 인스턴스를 유지한 채 새 버전을 병렬로 실행 |
| **리소스 사용량** | 추가 리소스 없이 기존 인스턴스만 사용 | 배포 중 인스턴스 수 증가 ➡️ 일시적인 리소스 추가 필요 |
| **무중단 여부** | 무중단 가능하나 처리량이 일시적으로 감소할 수 있음 | 무중단에 가깝고, 전체 처리량을 유지 가능 |
| **배포 속도** | 순차 교체 ➡️ 상대적으로 느림 | 병렬 배포 ➡️ 상대적으로 빠름 |
| **안정성** | 한 인스턴스 단위로 교체하므로 영향이 제한적 | 병렬 환경에서 헬스체크를 통해 안정성 확보 용이 |
| **운영 복잡도** | 비교적 단순 (기존 자원 내 교체) | 트래픽 전환, 인스턴스 중복 관리 필요 |
| **장애 발생 시 대응** | 즉시 중단 가능하나 복구는 수동적 | 기존 인스턴스를 유지하므로 롤백이 빠르고 유연함 |
| **적합한 환경** | 리소스가 제한된 환경, 단순한 구조 | 오케스트레이션 기반 환경(K8s, ECS 등), 고가용성 요구 서비스 |

- ### 🔄 In-place 배포 진행 프로세스 (교체 실행 방식)

| 단계 | 프로세스명 | 설명 |
| --- | --- | --- |
| **0** | **초기 상태 (v1)** | 모든 인스턴스는 v1 버전으로 실행되고 있으며, 로드 밸런서는 모든 인스턴스에 트래픽을 분산하고 있는 안정적인 서비스 상태입니다. |
| **1** | **1차 교체 - 기존 인스턴스 종료** | 첫 번째 v1 인스턴스를 로드 밸런서에서 제외한 후 종료합니다. 로드 밸런서는 남은 인스턴스들에게만 트래픽을 분산하기 시작합니다. |
| **2** | **v2 인스턴스 실행** | 방금 비운 자리에 새로운 v2 버전 인스턴스를 실행합니다. 이후 해당 인스턴스를 로드 밸런서에 다시 등록하여 트래픽 분산에 포함시킵니다. |
| **3** | **2차 교체 반복** | 남아 있는 v1 인스턴스를 하나씩 제거하고, 그 자리에 v2 인스턴스를 실행하는 작업을 차례대로 반복합니다. (v1 인스턴스는 점차 줄고, v2 인스턴스가 늘어남) |
| **4** | **최종 전환 완료 (v2)** | 모든 v1 인스턴스가 v2로 대체되었으며, 로드 밸런서는 이제 모든 v2 인스턴스에만 트래픽을 분산합니다. 서비스는 무중단으로 새로운 버전으로 완전히 전환된 상태입니다. |
| **⚠️** | **롤백 (Rollback)** | 만약 중간이나 최종 배포 후 문제가 발생하여 롤백을 진행할 경우, 위의 과정을 **정반대 순서**로 진행하여 v1 버전으로 복구하게 됩니다. |

- ### 🔄 Side-by-side (동시 실행 방식)

| 단계 | 프로세스명 | 설명 |
| --- | --- | --- |
| **0** | **초기 상태 (v1)** | 시스템은 기존 버전인 v1 인스턴스 3개로 구성되어 있으며, 로드 밸런서는 모든 인스턴스에 균등하게 트래픽을 분산하고 있는 안정적인 상태입니다. |
| **1** | **1차 배포: v2 인스턴스 추가** | 기존 v1 인스턴스를 종료하지 않고, 새로운 v2 인스턴스를 병렬로 하나 추가 실행합니다. 로드 밸런서는 새로 추가된 v2를 포함한 모든 인스턴스에 트래픽을 분산합니다. |
| **2** | **1차 교체: v1 인스턴스 종료** | 새로운 v2 인스턴스가 안정적으로 구동되면, 기존 v1 인스턴스 중 하나를 종료하여 점진적으로 버전을 교체해 나갑니다. 트래픽은 여전히 실행 중인 남은 인스턴스들로 분산됩니다. |
| **3** | **2차 교체 반복** | v2 인스턴스를 하나씩 더 추가하고, 그에 맞춰 남아 있는 v1을 하나씩 제거하는 과정을 차례대로 반복합니다. 이 과정 동안 v1은 줄고 v2는 늘어나며, 서비스는 지속되지만 **리소스를 일시적으로 더 사용**하게 됩니다. |
| **4** | **최종 전환 완료 (v2)** | 모든 v1 인스턴스가 v2로 안전하게 교체되면, 로드 밸런서는 v2 인스턴스들만을 대상으로 트래픽을 분산합니다. 서비스 중단 없이 새 버전으로의 전체 시스템 전환이 완료됩니다. |
| **⚠️** | **즉시 복구 (Rollback)** | 만약 중간 단계나 최종 배포 직후 런타임 장애가 발생하여 롤백을 진행할 경우, 위의 과정을 **정반대 순서**로 진행하여 v1 버전으로 안전하게 복구합니다. |

#### 주제 4: Canary Deployment
- Canary Deployment: 새 버전을 전체에 적용하기 전에 일부 사용자나 트래픽에만 점진적으로 배포하여 안정성을 검증한 후 전면 배포하는 방식
  - 새 버전의 안정성을 실사용 환경에서 미리 검증하여 전체 배포로 인한 장애를 사전에 방지하기 위해서
- ### 🦆 카나리(Canary) 배포 진행 프로세스 (Deployment Flow)

| 단계 | 프로세스명 | 트래픽 비율 (v1 : v2) | 설명 |
| --- | --- | --- | --- |
| **0** | **초기 상태 (v1)** | **100% : 0%** | 전체 트래픽이 기존 버전인 v1 인스턴스로만 전달되고 있습니다. 아직 신규 버전(v2)은 배포되지 않은 상태이며, 사용자는 안정된 환경에서 서비스 중입니다. |
| **1** | **첫 번째 카나리 릴리스** | **90% : 10%** | 새 버전(v2) 인스턴스 하나를 추가로 실행합니다. 로드 밸런서는 전체 트래픽 중 약 10% 정도만 v2로 전달하고, 나머지 90%는 기존 v1으로 유지하며 실사용 검증을 시작합니다. |
| **2** | **점진적 확장** | **70% : 30%** | 모니터링 중 이상 징후가 없다면, v2로의 트래픽 비중을 30%로 확장합니다. 이때도 v1이 유지되며 두 버전이 병행 운영됩니다. |
| **3** | **지속 확장** | **30% : 70%** | v2의 안정성이 추가로 확인되면 트래픽의 대부분을 v2에 할당합니다. 보수적인 이동을 위해 여전히 30%는 v1로 남겨둡니다. |
| **4** | **전면 전환 직전** | **10% : 90%** | 최종적인 안정성 검토를 위해 대부분의 사용자(90%)가 v2를 사용하도록 조정합니다. 극소수의 트래픽이 v1에 남아 있어 언제든 롤백할 가능성을 열어둡니다. |
| **5** | **전체 전환 (v2 완료)** | **0% : 100%** | 모든 트래픽을 v2로 완전히 전환합니다. 기존 v1 인스턴스는 종료하거나 망에서 분리되며 카나리 배포가 최종 완료됩니다. |

- ### 📊 배포 전략 비교: Side-by-side 롤링 배포 vs 카나리 배포

| 구분 | ⇄ Side-by-side 롤링 배포 | 🦆 카나리 배포 |
| --- | --- | --- |
| **교체 방식** | 새 버전(v2) 인스턴스를 미리 띄운 뒤, 기존(v1)을 순차적으로 하나씩 교체 | 전체 중 극히 일부(예: 5~10%) 인스턴스에만 먼저 v2를 배포 |
| **트래픽 전환 규모** | 항상 v1·v2가 섞여 운용되며, 순차적으로 최종 100% v2로 전환 | 초기 소수 트래픽만 v2로 전달하고, 검증 완료 시 단계적으로 비율을 늘려 100%로 전환 |
| **위험 관리** | 교체 시점마다 방금 교체된 인스턴스만 롤백하여 영향을 국소화 | 카나리 그룹에서만 문제를 감지하므로, 전체 서비스 리스크가 더 작음 |
| **사용 시점** | 전체 풀 교체를 예측 가능하고 안정적으로 수행해야 할 때 | 새 버전에 대한 세밀한 모니터링과 최소 영향 검증이 필요할 때 |

- ### 📊 배포 전략 종합 비교: Blue/Green vs Rolling vs Canary

| 구분 | 🟢 Blue/Green 배포 | ⇄ Rolling 배포 | 🦆 Canary 배포 |
| --- | --- | --- | --- |
| **기본 개념** | 기존 버전(Blue)과 새 버전(Green)을 완전히 분리된 환경에 배포하고, 트래픽 전환을 통해 한 번에 교체 | 기존 인스턴스를 하나씩 교체하여 새 버전을 점진적으로 전체에 적용 | 일부 사용자 또는 트래픽에만 새 버전을 우선 적용하여 실시간 반응을 기반으로 점진 확산 |
| **트래픽 처리 방식** | 전환 시점에 전체 트래픽을 한번에 Green으로 이동 | 배포 단위마다 순차적으로 트래픽 전환 | 트래픽을 비율 단위로 점진적으로 늘려가며 분산 |
| **리소스 요구** | Blue, Green 모두 동시에 실행되므로 **2배의 자원 필요** | 기존 인프라 내에서 진행 가능. 필요 시 일시적 리소스 증가 가능 | 새 버전 인스턴스 + 트래픽 조절 인프라 ➡️ 상황에 따라 유동적 자원 필요 |
| **롤백 방식** | 트래픽을 다시 Blue로 전환하면 즉시 롤백 가능 **(매우 빠름)** | 새 버전 교체 중단 후, 기존 버전 인스턴스를 다시 배포 | 트래픽 비율을 줄이고, 기존 버전 트래픽을 다시 늘리는 방식으로 롤백 |
| **배포 속도** | **매우 빠름** (환경만 준비되면 전환은 즉시 가능) | **느림** (순차적으로 교체되기 때문에 전체 완료까지 시간 소요) | **중간** (단계적 조절 속도에 따라 유동적) |
| **안정성 확보** | Green을 독립적으로 사전 테스트할 수 있어 안정성 확보가 용이 | 실시간으로 인스턴스를 교체하기 때문에 변경 중 문제가 생길 위험 존재 | 실제 사용자로부터 직접 피드백을 받아 안정성 검증 가능 |
| **운영 복잡도** | 중간 (환경 2개 운영 + 트래픽 전환 필요) | **가장 단순** (순차 교체, 자동화 쉬움) | **가장 복잡** (트래픽 비율 조절, 모니터링 및 조건 기반 확산 로직 필요) |
| **적합한 환경** | 리소스 여유가 있고, 빠르고 반복적인 배포가 필요한 서비스 | 정적인 구조, 리소스 제약이 있는 환경 | 대규모 사용자 기반, 민감한 기능 배포, A/B 테스트 등 |
