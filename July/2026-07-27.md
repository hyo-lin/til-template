#### 주제 1: RBAC, ServiceAccount
## RBAC
## 1. RBAC 개요 및 필요성

> **RBAC (역할 기반 접근 제어)**
> "누가(Subject), 어떤 쿠버네티스 리소스에(Resource), 어떤 작업(Verb)을 할 수 있는지" 역할을 기준으로 제어하는 인가(Authorization) 메커니즘입니다.

### 왜 RBAC가 필요한가?

1. **최소 권한 원칙 적용**: 모든 사용자나 파드에 관리자(Admin) 권한이 남발되는 것을 방지합니다.
2. **네임스페이스 격리 실효성 확보**: 개발팀/네임스페이스 간 무단 접근(예: FE 개발자가 BE Secret 수정)을 방지합니다.
3. **클러스터 내 애플리케이션 권한 제한**: Prometheus, Ingress Controller, CI/CD 툴 등 파드 내부 앱이 필요한 API 요청만 수행하도록 통제합니다.
4. **대규모 사용자 관리**: 개인별 권한 부여 대신 '역할(Role)' 단위로 묶어 매핑함으로써 효율적인 관리가 가능합니다.

---

## 2. 인증(Authentication) vs 인가(Authorization)

| 구분 | 인증 (Authentication) | 인가 (Authorization) |
| --- | --- | --- |
| **개념** | **"당신이 누구인가?"** (신원 확인) | **"당신이 이 행동을 할 권한이 있는가?"** (권한 검증) |
| **수단** | SSL Client Cert (pem), Token, OIDC, Kubeconfig | RBAC (Role, ClusterRole, Binding) |
| **순서** | **1단계** (API Server 요청 진입 시 신원 확인) | **2단계** (인증 완료된 요청에 대해 권한 확인) |

---

## 3. RBAC 핵심 리소스 구성 요소

| 구성 요소 | 설명 | Scope (범위) |
| --- | --- | --- |
| **Role** | 특정 네임스페이스 범위에서 리소스에 대한 권한을 정의합니다. | Namespace |
| **RoleBinding** | 특정 네임스페이스에서 Role 또는 ClusterRole을 주체에게 부여합니다. | Namespace |
| **ClusterRole** | 클러스터 전체 범위에서 사용하거나 여러 NS에서 재사용할 권한을 정의합니다. | Cluster |
| **ClusterRoleBinding** | ClusterRole을 클러스터 전체 범위로 주체에게 부여합니다. | Cluster |

---

## 4. Role 및 RoleBinding 상세 요소

### ① Role 세부 요류

| 요소 | 설명 | 예시 |
| --- | --- | --- |
| **API 그룹 (APIGroups)** | 리소스가 속한 API 그룹을 정의합니다. | `""` (Core API: Pod, Service 등), `"apps"` (Deployment 등) |
| **리소스 (Resources)** | 접근을 제어할 대상 리소스를 지정합니다. | `"pods"`, `"services"`, `"deployments"` |
| **작업 (Verbs)** | 대상 리소스에 대해 허용할 동작을 명시합니다. | `"get"`, `"list"`, `"watch"`, `"create"`, `"update"`, `"delete"` |

> **주요 Verbs(작업) 모음**
> * **조회:** `get` (단일 조회), `list` (목록 조회), `watch` (실시간 상태 변화 감시)
> * **생성/수정:** `create` (생성), `update` (전체 교체), `patch` (일부 수정)
> * **삭제:** `delete` (단일 삭제), `deletecollection` (일괄 삭제)
>
>

### ② RoleBinding 세부 요소

| 요소 | 설명 | 예시 |
| --- | --- | --- |
| **RoleRef** | 바인딩할 Role 또는 ClusterRole 정보를 지정합니다. | `kind: Role`, `name: pod-reader` |
| **주체 (Subjects)** | 권한을 부여받을 대상(사용자, 그룹, 서비스계정)을 명시합니다. | `User`, `Group`, `ServiceAccount` |
| **네임스페이스 (Namespace)** | RoleBinding이 동작할 특정 네임스페이스를 지정합니다. | `namespace: backend` |

---

## 5. Role vs ClusterRole 비교

| 구분 | Role | ClusterRole |
| --- | --- | --- |
| **적용 범위** | 특정 **Namespace** 내부 | **Cluster 전체** |
| **Namespace 지정** | 필수 지정 | 지정하지 않음 |
| **대상 리소스** | Pod, Service, Deployment 등 (NS에 속함) | Node, PV, StorageClass, Namespace 등 (NS에 안 속함) |
| **재사용성** | 해당 NS 내에서만 유효 | 하나 정의 후 여러 NS에서 RoleBinding으로 재사용 가능 |

---

## 6. 실무 활용 패턴

1. **팀별 네임스페이스 격리**: `frontend` 개발자는 `frontend` NS의 Pod 조회 및 Deployment 수정만 가능하도록 제한.
2. **개발자 vs 운영자 권한 분리**:
* **개발자**: 워크로드 조회, 로그 확인(`get`, `list`, `logs`), 제한된 수정 권한.
* **운영자**: 클러스터 전체 리소스 관리, NS 생성/삭제, RBAC 제어 권한.


3. **애플리케이션 전용 Service Account (SA) 부여**:
* ArgoCD, Prometheus, Ingress Controller 등 앱마다 전용 SA를 생성하고 필요한 최소 권한만 RoleBinding하여 부여.



---

## 7. 핵심 특징 요약

* **권한의 합집합(Union) 처리**: 한 주체에게 여러 Role이 부여되면 권한이 합쳐집니다. (명시적인 Deny 규정이 없으며 Allow 규칙들의 합으로 동작)
* **선언적 권한 정의**: Role은 '권한의 정의'일 뿐이며, 주체에게 실제 권한이 부여되는 시점은 **RoleBinding이 생성될 때**입니다.

# 🔑 Kubernetes 계정 관리 (ServiceAccount & User Account)

## 1. 개요 및 계정 유형 비교

쿠버네티스에는 클러스터에 접근하는 주체에 따라 User Account(사람)와 ServiceAccount(애플리케이션)라는 두 가지 형태의 신원(Identity)이 존재합니다.

### User Account vs ServiceAccount

| 구분 | User Account (사람) | ServiceAccount (앱/프로그램) |
| --- | --- | --- |
| **주요 대상** | 개발자, 클러스터 관리자, 운영자 | Pod, 애플리케이션, Prometheus, ArgoCD 등 |
| **사용 목적** | 사람의 클러스터 조작 및 관리 (`kubectl`) | 애플리케이션의 Kubernetes API 호출 |
| **k8s 리소스 여부** | ❌ **없음** (외부 인증 시스템 활용) | ⭕ **존재함** (`kind: ServiceAccount`) |
| **생성 및 관리** | OIDC, IAM, 클라이언트 인증서(X.509) | Kubernetes API로 직접 생성 및 관리 |
| **적용 범위 (Scope)** | 클러스터 전체 (인증 체계에 따라 분리) | 특정 **Namespace**에 속함 |
| **주요 인증 정보** | Client Cert, Token, OIDC, IAM Role | **Projected Short-lived Token** |

---

## 2. ServiceAccount (SA) 상세

> **ServiceAccount**
> Pod와 같은 애플리케이션 워크로드가 클러스터 내부 리소스에 접근하거나 쿠버네티스 API와 상호작용할 수 있도록 권한을 제공하는 계정입니다.

### ① ServiceAccount 구성 요소

| 요소 | 설명 | 예시 |
| --- | --- | --- |
| **네임스페이스 (Namespace)** | ServiceAccount가 속한 네임스페이스를 정의합니다. | `namespace: production` |
| **토큰 (Token)** | Kubernetes API 서버와 상호작용하기 위해 사용되는 인증 토큰입니다. | `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…` |
| **시크릿 (Secret)** | Token과 클러스터 인증서(CA 정보)가 포함된 Secret 리소스입니다. | `secretName: api-access-token-abc123` |
| **RBAC Role / Binding** | ServiceAccount가 접근할 수 있는 리소스와 권한을 정의합니다. | `RoleBinding: sa-reader-binding` |

### ② ServiceAccount 주요 특징

* **Pod와 연결**: Pod 생성 시 `serviceAccountName`을 별도로 지정하지 않으면 해당 네임스페이스의 `default` ServiceAccount가 자동으로 연결됩니다.
* **Token 기반 인증**: Pod 실행 시 보안용 단기(short-lived) 토큰이 자동 생성되어 Pod 내부 디렉터리에 마운트됩니다.
* **네임스페이스 단위 관리**: SA는 특정 네임스페이스에 속하므로, 클러스터 수준 리소스에 접근하려면 `ClusterRole` 및 `ClusterRoleBinding` 조회가 필요합니다.
* **RBAC과의 연계**: SA 자체는 신원일 뿐이며, 실제 권한은 `RoleBinding` 또는 `ClusterRoleBinding`을 통해 부여받습니다.

### ③ ServiceAccount 동작 방식

```
Pod 생성 (SA 연동) ➔ 단기 토큰 생성 및 Volume 마운트 ➔ API 서버 요청 (Token 전달) ➔ RBAC 권한 검증 ➔ 요청 허용/거부

```

| 순서 | 동작 | 내용 |
| --- | --- | --- |
| **1** | **ServiceAccount 생성** | 네임스페이스 안에 ServiceAccount가 존재하며, 미지정 시 Pod는 자동으로 `default` SA를 사용합니다. |
| **2** | **Pod와 연결** | Pod가 생성되면 지정된 ServiceAccount가 Pod의 실행 환경에 연결됩니다. |
| **3** | **단기 토큰 생성 & Volume 마운트** | Pod 실행 시 SA용 단기(short-lived) 토큰을 자동 생성하고, Projected Volume 형태로 Pod 내부에 마운트합니다. |
| **4** | **API 서버 인증** | Pod 내부 앱은 마운트된 projected token을 읽어 Control Plane의 API 서버로 인증 요청을 보냅니다. |
| **5** | **RBAC로 접근 권한 결정** | `Role/RoleBinding` 또는 `ClusterRole/ClusterRoleBinding`을 통해 SA의 API 접근 권한이 최종 결정됩니다. |

## 3. User Account 관리 실무 (EKS vs Self-Hosted)

### ① AWS EKS 환경 (EKS Access Entry)

AWS EKS에서는 IAM을 통한 신원 인증과 쿠버네티스 RBAC 권한을 **EKS Access Entry** 기능으로 바인딩합니다.

```
IAM Identity Center / IAM Role
       ↓
EKS Access Entry (인증 매핑)
       ↓
Kubernetes Group (EKS Access Policy 또는 ClusterRoleBinding)
       ↓
실제 Kubernetes 권한 부여

```

* **주요 EKS Access Policy**:
* `AmazonEKSClusterAdminPolicy`: 클러스터 전체 관리자
* `AmazonEKSAdminPolicy`: 관리자 수준 권한
* `AmazonEKSEditPolicy`: 워크로드 생성 및 수정 권한
* `AmazonEKSViewPolicy`: 읽기 전용 권한



### ② Self-Hosted (kubeadm) 환경

쿠버네티스 내부에는 User Account 리소스가 없으므로, **X.509 클라이언트 인증서** 또는 외부 인증 서비스(Keycloak, Okta 등 OIDC)를 연동합니다.

* **인증서 주체(Subject) 항목을 통한 식별**:
* `CN (Common Name)` ➔ **Username** (예: `CN=charlie`)
* `O (Organization)` ➔ **Group** (예: `O=developers`)

## 4. ServiceAccount 보안 모범 사례 (Best Practices)

1. **애플리케이션별 전용 SA 생성**: `frontend-sa`, `backend-sa`, `prometheus-sa` 등 용도별로 최소 권한을 가진 전용 SA를 분리해 적용합니다.
2. **`default` ServiceAccount 권한 부여 금지**: 기본 SA에 권한을 주면 SA를 명시하지 않은 네임스페이스 내 모든 Pod가 위험한 권한을 남용할 수 있습니다.
3. **최소 권한 원칙 (Least Privilege) 적용**: `Pods delete`, `Secrets get`, `Namespaces create` 등 파괴적이거나 민감한 권한은 필요한 경우에만 제한적으로 부여합니다.
4. **생성(Create) 권한 오남용 유의**: 삭제 권한만큼이나 **생성(Create) 권한 과도 부여가 위험**합니다. (잘못된 자원 생성으로 노드 OOM, IP 고갈 등 발생 가능)

#### 주제 2: Helm (Kubernetes 패키지 매니저)
## ☸️ Helm
## 1. 개요 및 등장 배경

> **Helm**
> 쿠버네티스 애플리케이션을 구성하는 여러 YAML 리소스(Deployment, Service, ConfigMap 등)를 하나의 설치 패키지인 **Chart**로 묶어, 설정값만 바꿔 반복 설치·업데이트·롤백할 수 있게 해주는 **쿠버네티스 전용 패키지 매니저**입니다.

### 기존 YAML 배포 방식의 문제점

* **관리할 YAML 파일 급증**: 단일 앱 배포에도 최소 3개(Deployment, Service, ConfigMap), 복잡한 서비스는 10개 이상의 YAML 관리가 필요함
* **환경별 중복 파일 발생**: Dev, Staging, Prod 등 환경마다 `replicas`, `image tag`, `domain` 등 설정값만 약간씩 다른 YAML이 중복 생성되어 관리가 파편화됨
* **배포 및 롤백의 어려움**: 여러 리소스를 하나씩 `kubectl apply` 해야 하며, 문제 발생 시 시스템 전체를 특정 시점으로 한 번에 롤백하기 힘듦

---

## 2. Helm 핵심 구성 요소

### ① 핵심 개념 구분 (Chart vs Release)

| 구분 | **Chart (설계도)** | **Release (실제 설치 결과)** |
| --- | --- | --- |
| **개념** | 리소스 템플릿과 설정(`values`)을 하나로 묶은 **설치 패키지** | 특정 Chart를 클러스터에 실제로 **설치(배포)한 인스턴스** |
| **비유** | 클래스 (Class), Docker Image | 객체 (Instance), Container |
| **특징** | 로컬 디렉터리 또는 원격 차트 저장소(Repository)에 존재 | 버전 이력(Revision)이 남으며 **독립적인 롤백(Rollback)** 가능 |
| **예시** | `express-chart/` 패키지 자체 | `express-dev`, `express-prod` 등 배포된 결과 |

### ② 차트 구조 (Directory Structure)

```text
express-chart/
├── Chart.yaml          # 차트의 메타데이터 (차트 이름, 버전 등)
├── values.yaml         # 템플릿에 주입할 기본 설정값 (Default Values)
├── charts/             # 의존성 차트 파일 저장 디렉터리
└── templates/          # Go 템플릿 문법이 들어간 k8s YAML 파일들
    ├── deployment.yaml
    ├── service.yaml
    └── configmap.yaml

```

| 파일/디렉터리 | 역할 및 설명 |
| --- | --- |
| **`Chart.yaml`** | 차트 이름(`name`), 버전(`version`), 앱 버전(`appVersion`) 등을 정의하는 파일 |
| **`values.yaml`** | 이미지 태그, 복제본 수 등 템플릿 변수에 들어갈 **기본 설정값**을 모아둔 파일 |
| **`templates/`** | `{{ .Values.replicaCount }}`와 같이 변수(Go Template)가 포함된 YAML 템플릿 위치 |
| **`charts/`** | 해당 차트가 의존하는 외부 차트들이 저장되는 위치 |

## 3. Helm 동작 원리 및 문법 예시

### ① 템플릿 바인딩 과정

```text
  [ templates/deployment.yaml ]         [ values.yaml ]
  spec:                                 replicaCount: 2
    replicas: {{ .Values.replicaCount }}  image:
    image: {{ .Values.image.tag }}          tag: "v1.0.0"
                    │                        │
                    └───────────┬────────────┘
                                ▼
                       [ Helm 렌더링 엔진 ]
                                ▼
                  [ 최종 완성된 Kubernetes YAML ]
                  spec:
                    replicas: 2
                    image: "v1.0.0"
                                ▼
                   [ Kubernetes API Server 전달 ]

```

### ② 동작 단계

| 순서 | 단계 | 동작 내용 |
| --- | --- | --- |
| **1** | **설정값 선택** | 사용자가 사용할 Chart와 환경별 `values.yaml` (예: `values-prod.yaml`) 선택 |
| **2** | **템플릿 렌더링** | Helm CLI가 `templates/` 내부의 Go 템플릿 변수에 `values` 값을 결합해 순수 YAML 생성 |
| **3** | **API 전달** | 렌더링된 최종 YAML을 `kube-apiserver`로 전달하여 리소스 생성/업데이트 요청 |
| **4** | **릴리스 저장** | 배포 이력(Revision)을 클러스터 내 Secret/ConfigMap 형태로 저장해 롤백 및 추적 지원 |

## 4. `kubectl` vs `Helm` 비교

| 구분 | **kubectl** | **Helm** |
| --- | --- | --- |

#### 주제 3: Ingress
## 🌐 Ingress

## 1. 개요 및 등장 배경

> **Ingress**
> 클러스터 외부의 HTTP/HTTPS 요청을 도메인(`Host`)과 URL 경로(`Path`)에 따라 클러스터 내부의 **Service**로 연결해 주는 **L7 애플리케이션 라우팅 규칙(선언 리소스)**입니다.

### NodePort 방식의 한계와 Ingress 도입 이유

* **기존 NodePort의 한계**:
* **보안 위험 증가**: 서비스마다 비표준 포트(30000~32767)를 열어야 하므로 노드 방화벽/보안 그룹 규칙이 비대해지고 외부 공격 지점(Attack Surface)이 확대됨
* **사용자 경험(UX) 저하**: `example.com:30080`, `example.com:30081`과 같이 도메인 뒤에 포트를 명시해야 하므로 실제 상용 서비스에 불합리함
* **TLS(SSL) 인증서 관리 파편화**: 서비스마다 SSL/TLS 인증서를 각각 적용하고 갱신해야 하는 번거로움 발생


* **Ingress의 해결책**:
* 표준 포트(80/443) 단일 진입점 제공
* 도메인 및 경로 기반의 L7 라우팅 지원
* TLS Termination(SSL 종료)을 Ingress Controller에서 중앙 집중식으로 일괄 처리



---

## 2. Ingress vs Ingress Controller (핵심 구조)

Ingress 리소스 자체는 단순한 '설계도(규칙 명세서)'일 뿐이며, 실제로 트래픽을 받고 프록싱하는 주체는 **Ingress Controller**입니다.

| 구분 | **Ingress (선언)** | **Ingress Controller (실행)** |
| --- | --- | --- |
| **개념** | 외부 트래픽 라우팅 규칙을 정의한 **YAML 리소스** | Ingress 규칙을 감시하고 **실제 L7 프록시를 제어하는 실행체** |
| **비유** | 건축 설계도 | 건물을 시공하고 운영하는 주체 |
| **특징** | 리소스만 생성 시 아무 일도 일어나지 않음 | 클러스터 내 Pod 형태로 동작하며 실제 트래픽 분배 담당 |
| **종류** | `kind: Ingress` | NGINX Ingress, Traefik, AWS Load Balancer Controller 등 |

---

## 3. Ingress 주요 기능 및 라우팅 방식

### ① 핵심 제공 기능

| 기능 | 설명 |
| --- | --- |
| **트래픽 중앙 관리** | 외부에서 들어오는 트래픽을 단일 진입점에서 관리하고 내부 Service로 분배 |
| **네임 기반 가상 호스팅** | 하나의 Ingress에서 `example.com`, `api.example.com` 등 여러 도메인을 서로 다른 Service로 전달 |
| **TLS Termination** | Ingress Controller 단에서 SSL/TLS 암호화를 복호화하여 백엔드 Pod로는 HTTP로 가볍게 전달 |
| **Path 기반 라우팅** | URL 경로(`/app1`, `/app2`)에 따라 서로 다른 내부 Service로 라우팅 |

### ② 라우팅 방식 예시 (`YAML` 기준)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
  namespace: ingress-app
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx # 처리할 Ingress Controller 지정
  rules:
    - host: app.local # [호스트 기반 라우팅]
      http:
        paths:
          - path: /app1 # [경로 기반 라우팅]
            pathType: Prefix
            backend:
              service:
                name: service-app1
                port:
                  number: 80

```

## 4. Ingress 트래픽 흐름 (동작 방식)

```text
[ External Client ]
        │ (1) HTTP / HTTPS (80, 443)
        ▼
[ Ingress Controller Pod ] ◄── (Ingress 규칙 및 TLS Secret 감시)
        │ (2) L7 Host/Path 매칭 및 SSL Termination
        ▼
[ ClusterIP Service ]
        │ (3) L4 Pod 로드 밸런싱
        ▼
[ Target Pod (App) ]

```

| 순서 | 단계 | 설명 |
| --- | --- | --- |
| **1** | **클라이언트 요청 수신** | 외부 클라이언트가 도메인(`app.local/app1`)으로 요청을 보내면 Ingress Controller가 단일 진입점으로 수신 |
| **2** | **Ingress 규칙 매칭** | Controller가 Ingress 리소스에 정의된 Host 및 Path 조건 확인 (HTTPS 요청 시 SSL 복호화 수행) |
| **3** | **서비스 전달** | 매칭된 내부 Service(ClusterIP)로 트래픽 전달 |
| **4** | **Pod 처리 및 응답** | Service가 가용한 Pod로 로드 밸런싱하여 요청 처리 후 응답 반환 *(Pod → Service → Ingress Controller → Client)* |

---

## 5. 실무 아키텍처 패턴 & 베어메탈(kubeadm) 한계 극복

### ① Cloud(EKS) vs 베어메탈(kubeadm) 환경 차이

* **Cloud (EKS)**: Ingress 생성 시 AWS ALB(Application Load Balancer)가 자동 생성되어 고정 퍼블릭 IP/DNS 제공
* **베어메탈 / EC2 (kubeadm)**: 관리형 로드 밸런서가 없으므로 Ingress Controller Pod가 노드 이동 시 퍼블릭 IP가 변경되는 문제가 발생함

### ② EC2 Native NGINX + Ingress Controller 리버스 프록시 패턴 (실무 표준)

베어메탈/EC2+kubeadm 환경에서 고정 퍼블릭 IP와 안정적인 HTTPS(TLS)를 확보하기 위해 EC2 OS 단에 **Native NGINX**를 앞단 프록시로 배치하는 구조를 사용합니다.

```text
[ 인터넷 사용자 ]
       │ HTTPS (443)
       ▼ (A 레코드 고정 IP)
[ EC2 OS Native NGINX ] ── (Certbot / SSL 인증서 관리)
       │ HTTP proxy_pass (localhost:32080)
       ▼
[ Kubernetes Ingress Controller (NodePort 32080) ]
       │ L7 Host / Path 라우팅
       ▼
[ 내부 Service & Pod (App, Grafana, Prometheus) ]

```

* **장점**:
1. Ingress Controller Pod가 다른 노드로 재스케줄링되어도 **외부 접속 IP가 항상 고정**됨
2. Let's Encrypt(`certbot`) 인증서 관리를 EC2 OS 단에서 직관적이고 안전하게 일괄 수행 가능
3. 쿠버네티스 내부 노드 파손 시에도 단일 장애점(SPOF) 완화 구조 형성

## 6. 서비스(Service) vs Ingress 역할 비교

| 구분 | **Service** | **Ingress** |
| --- | --- | --- |
| **주요 역할** | 클러스터 **내부** Pod들을 그룹화하고 L4 엔드포인트 제공 | 클러스터 **외부** 트래픽을 내부 Service로 라우팅 (L7) |
| **트래픽 범위** | 주로 클러스터 내부 통신 (ClusterIP) | 외부 ➔ 내부 진입 트래픽 (Inbound) |
| **주요 기능** | L4 로드 밸런싱, Pod IP 추적 | 도메인/Path 라우팅, SSL/TLS Termination, Host 헤더 변경 |
| **차세대 표준** | - | **Gateway API** (Ingress의 표현력 한계를 극복하기 위해 등장한 차세대 표준) |


---

### 🌐 Ingress의 프로토콜 제약과 TCP/UDP 트래픽 처리 대안

#### 1. Ingress의 프로토콜 제약 (L7 전용)

* **지원 프로토콜**: **`HTTP`**, **`HTTPS`**
* **미지원 프로토콜**: **`TCP`**, **`UDP`**
* **특징**: Ingress는 기본적으로 L7(애플리케이션 계층) 리소스이므로 **Host(도메인) 및 Path(URL 경로) 기반의 HTTP/HTTPS 프록싱만 처리**할 수 있습니다. 따라서 데이터베이스(MySQL, Redis 등) 연결, 게임 서버, DNS 서비스처럼 순수 **TCP/UDP 통신이 필요한 환경에는 Ingress를 적용할 수 없습니다.**

---

#### 2. TCP / UDP 트래픽 처리를 위한 대안

| 구분 | **NodePort / LoadBalancer Service** | **Gateway API (현업 표준화 트렌드)** |
| --- | --- | --- |
| **계층 (Layer)** | **L4 (전송 계층)** | **L4 + L7 (통합 컨트롤)** |
| **특징** | TCP/UDP 포트를 직접 노출하여 백엔드 Pod로 바로 전달 | Ingress의 한계를 극복하기 위해 등장한 **차세대 쿠버네티스 표준 API** |
| **장점** | 구조가 단순하며 모든 TCP/UDP 트래픽 수용 가능 | HTTP/HTTPS뿐만 아니라 **TCP, UDP, gRPC 등 다양한 프로토콜**을 하나의 표준화된 규칙으로 프록싱 가능 |
| **단점** | L7 도메인/경로 기반 세부 라우팅 및 SSL 종료 불가 | 컨트롤러 구현체에 따라 지원 범위 확인 필요 |

---

#### 💡 한줄 요약

> **HTTP/HTTPS 웹 트래픽**은 기존 **Ingress**로 처리할 수 있지만, **TCP/UDP 트래픽**이 필요할 경우 traditional **NodePort/LoadBalancer Service**를 사용하거나, 최근 현업에서 L4/L7 통합 라우팅 표준으로 자리 잡고 있는 **Gateway API**를 도입하는 것이 권장됩니다.

## 🔍 추가 보완: `kube-proxy` 및 `Host/Local` 라우팅 원리

### 1. `kube-proxy`는 Ingress 트래픽 흐름에서 무슨 일을 할까?

> **Ingress Controller도 결국 쿠버네티스 안에서는 하나의 "Pod"이자 "Service(NodePort)"입니다.**

외부 트래픽이 노드에 도달했을 때 Ingress Controller Pod까지 찾아가는 실제 L4 패킷 전달은 `kube-proxy`가 담당합니다.

```text
[ 외부 요청 ] ──(32080 포트)──> [ 노드 (IP: 172.31.x.x) ]
                                        │
                                 [ kube-proxy ] (iptables/IPVS 규칙 적용)
                                        │
          ┌─────────────────────────────┴─────────────────────────────┐
          ▼                                                           ▼
[ Ingress Controller Pod (노드 A) ]                 [ Ingress Controller Pod (노드 B) ]

```

* **NodePort 포워딩**: Ingress Controller를 노출하기 위해 생성한 NodePort(예: `32080`)로 요청이 들어오면, 각 노드의 `kube-proxy`가 이를 감지하여 실제 Ingress Controller Pod가 떠 있는 노드/IP로 패킷을 포워딩해 줍니다.
* **`externalTrafficPolicy` 영향**:
* **`Cluster` (기본값)**: Ingress Controller Pod가 없는 노드의 32080 포트로 요청이 들어와도, `kube-proxy`가 다른 노드에 있는 Controller Pod로 트래픽을 대신 넘겨주어 정상 작동합니다.
* **`Local`**: Controller Pod가 **실제 존재하는 노드**로 들어온 요청만 처리하고, 없는 노드로 들어온 요청은 바로 드롭하여 불필요한 네트워크 홉(Hop)을 줄입니다.



---

### 2. `app.local`과 `localhost` 도메인 라우팅의 원리

#### ① 왜 EC2 IP가 아닌 `app.local`로 접속해야 할까? (Host Header)

Ingress Controller는 **HTTP Header의 `Host` 값**을 보고 어떤 서비스로 보낼지 결정합니다.

* **잘못된 접속 (`[http://13.125.](http://13.125.)x.x:31874`)**:
* HTTP Request Header ➔ `Host: 13.125.x.x`
* Ingress 규칙에는 `host: app.local`만 정의되어 있으므로 매칭되는 규칙이 없어 **`404 Not Found`** 반환.


* **올바른 접속 (`[http://app.local:31874](http://app.local:31874)`)**:
* `/etc/hosts` 설정에 의해 `app.local`이 EC2 IP로 변환되어 노드에 도달함.
* HTTP Request Header ➔ `Host: app.local`
* Ingress 규칙의 `host: app.local`과 일치하므로 **내부 Service로 정상 라우팅**.



#### ② Native NGINX의 `proxy_pass http://localhost:32080` 원리

EC2 OS 단에 설치한 Native NGINX 설정에서 `proxy_pass http://localhost:32080;`을 사용하는 이유는 **NodePort의 특징** 때문입니다.

* NodePort는 쿠버네티스 클러스터의 모든 노드의 `localhost` 포트(32080)에 포트를 개방합니다.
* 따라서 Native NGINX가 EC2 내부의 `localhost:32080`으로 찌르면, 그 노드의 `kube-proxy`가 트래픽을 받아 Ingress Controller Pod로 전달하게 됩니다.

---

### 💡 요약 맵핑

| 구성 요소 | 핵심 역할 |
| --- | --- |
| **`kube-proxy`** | NodePort(32080)로 들어온 L4 트래픽을 실제 Ingress Controller Pod로 전달 |
| **`app.local`** | Ingress가 라우팅 대상을 식별하기 위한 HTTP **`Host` 헤더 기준값** |
| **`localhost:32080`** | EC2 Native NGINX가 k8s 노드의 NodePort로 트래픽을 넘겨주는 내부 통로 |


---

#### ❓ Q. Ingress Controller Pod가 없는 노드(Node B)로 외부 트래픽이 들어오면 어떻게 처리되나요?

> **상황**: 클러스터 내 Node A, C에는 Ingress Controller(I.C) Pod가 실행 중이지만, **Node B에는 I.C Pod가 없는 상태**입니다. 이때 외부 NLB가 Node B의 NodePort로 요청을 보낸 경우 트래픽은 어떻게 동작할까요?

---

#### 💡 정답

쿠버네티스 Ingress Controller 서비스의 **`externalTrafficPolicy`** 설정(`Cluster` vs `Local`)에 따라 트래픽 처리 방식이 전혀 달라집니다.

---

#### 📝 상세 해설

##### ① `externalTrafficPolicy: Cluster` (기본값 설정일 때)

* **동작 방식**:
1. 외부 NLB가 I.C Pod가 없는 **Node B**의 NodePort로 요청을 전달합니다.
2. Node B의 `kube-proxy`가 클러스터 전체의 Endpoint 정보를 확인합니다.
3. Node B에 I.C Pod가 없으므로, 내부 네트워크 홉(Network Hop)을 거쳐 **I.C Pod가 살아있는 Node A 또는 Node C로 트래픽을 대신 포워딩**합니다.
4. 전달받은 Node A/C의 I.C Pod가 L7 규칙(Host/Path)을 해석하여 최종 애플리케이션 Pod(WAS)로 요청을 넘겨줍니다.


* **핵심 특징**:
* I.C Pod가 없는 노드로 들어와도 **정상 통신이 가능**합니다.


---

##### ② `externalTrafficPolicy: Local` (성능/IP 보존 설정일 때)

* **동작 방식**:
1. 외부 NLB가 I.C Pod가 없는 **Node B**의 NodePort로 요청을 전달합니다.
2. Node B의 `kube-proxy`가 *"내 노드(Local)에는 I.C Pod가 없다"*고 판단합니다.
3. 다른 노드로 트래픽을 넘겨주지 않고 **그 자리에서 요청을 즉시 차단(Drop) / 실패 처리**합니다.


* **핵심 특징**:
* 다만 I.C Pod가 없는 노드로 직접 들어온 요청은 바로 에러가 나므로, 실무에서는 NLB가 Health Check를 통해 I.C Pod가 떠 있는 노드로만 요청을 보내도록 유도합니다.
