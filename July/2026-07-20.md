### 새로 배운 내용
#### 주제 1: Namespace
- Namespace: 리소스를 논리적으로 분리하기 위한 고유 이름을 가진 공간
- | 특징 | 내용 |
  | --- | --- |
  | **리소스 분리** | 네임스페이스는 클러스터 리소스를 논리적으로 분리합니다. 동일한 클러스터 내에서도 네임스페이스에 따라 리소스가 구분되므로, 각 네임스페이스는 독립적인 환경처럼 작동할 수 있습니다. |
  | **리소스 격리** | 네임스페이스는 특정 리소스들(예: 파드, 서비스, 컨트롤러 등)에 대해 독립적인 격리 계층을 제공합니다. 이를 통해 한 네임스페이스의 리소스 상태가 다른 네임스페이스에 영향을 미치지 않도록 보장합니다. |
  | **이름 충돌 방지** | 네임스페이스는 동일한 이름의 리소스가 클러스터 내에서 서로 충돌하지 않도록 합니다. 예를 들어, 동일한 이름을 가진 두 개의 파드가 다른 네임스페이스에 존재할 수 있습니다. |
  | **정책 적용의 단위** | 네임스페이스는 `ResourceQuota` 및 `LimitRange`와 같은 정책을 설정할 수 있는 단위입니다. 이를 통해 자원의 할당 및 제한 정책을 정의하여 클러스터 자원을 적절하게 사용할 수 있습니다. |
  | **다양한 오브젝트에 대한 적용 가능성** | 네임스페이스는 파드, 서비스, 컨트롤러와 같은 리소스에 적용되고, 다양한 정책을 추가하여 보안을 강화할 수 있습니다. |
  | **스코프 관리** | 네임스페이스는 사용자나 팀별로 리소스를 분리하여 관리할 수 있는 스코프를 제공합니다. 이는 권한을 네임스페이스 단위로 세분화하여 적용할 수 있게 합니다. |
- #### Namespace 사용 이유
- | 이유 | 설명 |
  | --- | --- |
  | **환경 간 논리적 분리** | 네임스페이스는 개발, 테스트, 운영 등 다양한 환경을 분리하여 관리할 수 있도록 합니다. 이를 통해 환경 간 영향을 최소화하고, 동일 이름의 리소스 충돌을 방지합니다. |
  | **정책 및 규칙의 적용 단위** | 네임스페이스를 기준으로 네트워크 정책, 리소스 제한 정책 등을 설정할 수 있습니다. 네임스페이스를 사용하면 세밀한 설정을 할 수 있어 각 환경에 맞는 조건을 적용할 수 있습니다. |
  | **확장성과 운영의 유연성** | 네임스페이스를 통해 단일 클러스터에서도 여러 환경을 동시에 운영할 수 있으며, 클러스터 확장 없이 다양한 요구사항을 수용할 수 있습니다. |
  | **테스트 및 배포** | 개발 및 테스트 환경을 운영 환경과 독립적으로 유지할 수 있어, 새로운 애플리케이션 배포나 테스트 시 운영 환경에 영향을 미치지 않습니다. |

#### 주제 2: ResourceQuota, LimitRange
- ResourceQuota: 특정 네임스페이스에 할당할 수 있는 리소스의 최대값을 제한하는 메커니즘
- #### ResourceQuota의 핵심 개념
- | 개념 | 설명 |
  | :--- | :--- |
  | **네임스페이스별로 동작** | ResourceQuota는 특정 네임스페이스에 적용되어 해당 네임스페이스에서 사용할 수 있는 리소스를 제한합니다. 각 네임스페이스는 설정된 리소스 범위 내에서 독립적으로 동작하며, 하나의 네임스페이스가 과도한 리소스를 사용하는 경우에도 다른 네임스페이스에 영향을 주지 않도록 보장합니다. |
  | **리소스 제한의 범위** | ResourceQuota는 CPU, 메모리와 같은 물리적 리소스뿐만 아니라 파드, 서비스 등 네임스페이스 내에서 생성할 수 있는 쿠버네티스 오브젝트의 개수까지 제한할 수 있습니다. |
  | **할당 가능한 리소스의 상한선 설정** | ResourceQuota는 네임스페이스에서 생성할 수 있는 리소스의 총량을 상한선으로 설정합니다. 이 상한선을 초과하려는 리소스 요청은 자동으로 거부되며, 이를 통해 네임스페이스 내 리소스 사용을 체계적으로 관리할 수 있습니다. |
  | **리소스 관리 및 공정성 확보** | ResourceQuota는 클러스터의 리소스를 공정하게 분배하여 특정 네임스페이스가 리소스를 독점하지 않도록 합니다. 이를 통해 리소스 부족으로 인한 파드 생성 실패나 네임스페이스 간 충돌을 방지하고, 클러스터의 안정성을 유지할 수 있습니다. |
- #### ResourceQuota 사용 이유
- | 이유 | 설명 |
  | :--- | :--- |
  | **제한적인 클러스터 리소스** | 쿠버네티스 클러스터에서 사용할 수 있는 CPU, 메모리, 스토리지 등 물리적 리소스는 한정적입니다. 제한 없이 사용하면 특정 네임스페이스가 과도한 리소스를 점유해 다른 네임스페이스가 자원을 사용할 수 없는 상황이 발생할 수 있습니다. |
  | **네임스페이스 간 리소스 충돌 방지** | 클러스터 내 여러 네임스페이스가 동작하며, 각 네임스페이스는 동일한 리소스를 공유합니다. ResourceQuota는 네임스페이스별로 리소스의 상한선을 설정하여 특정 네임스페이스가 과도한 리소스를 사용하지 못하도록 하여 충돌을 방지합니다. |
  | **클러스터 안정성 확보** | ResourceQuota는 리소스를 예측 가능하게 사용하도록 강제함으로써, 자원 부족으로 인한 파드 실패나 서비스 중단 같은 클러스터 내 불안정한 상황을 방지합니다. 이는 클러스터의 안정성을 유지하는 데 필수적입니다. |
  | **리소스의 공정한 분배** | ResourceQuota는 모든 네임스페이스에 대해 자원을 공정하게 분배합니다. 팀 간, 프로젝트 간, 워크로드 간 리소스 사용의 균형을 보장하여 특정 네임스페이스의 독점적 사용을 방지합니다. |
  | **운영 효율성 및 문제 예방** | ResourceQuota를 설정하면 리소스 사용량을 체계적으로 관리하고 모니터링할 수 있습니다. 설정된 한도를 초과하려는 요청은 자동으로 거부되므로, 리소스 부족으로 인한 성능 저하나 장애를 사전에 예방할 수 있습니다. |

- LimitRange: 네임스페이스에서 컨테이너나 Pod가 허용된 자원 범위 내에서만 리소스를 사용할 수 있도록 강제하는 메커니즘
- #### LimitRange의 핵심 개념
- | 항목 | 설명 |
  | :--- | :--- |
  | **네임스페이스별 설정** | LimitRange는 특정 네임스페이스 내에서만 적용됩니다. 각 네임스페이스는 독립적인 LimitRange 설정을 가질 수 있습니다. |
  | **개별 오브젝트 적용** | LimitRange는 네임스페이스 내에서 생성되는 개별 Pod, 컨테이너 등의 리소스 사용량을 제한합니다. |
  | **리소스 관리 단위** | CPU, 메모리와 같은 물리적 리소스뿐만 아니라 서비스와 같은 리소스의 제한도 설정 가능합니다. |
  | **동적 검증** | LimitRange는 오브젝트 생성 시점에서 리소스 요청 및 제한 설정이 정의된 범위 내에 있는지를 동적으로 검증하여 규칙에 어긋나는 요청을 거부합니다. |
- #### LimitRange 사용 이유
- | 이유 | 설명 |
  | :--- | :--- |
  | **과도한 리소스 사용 방지** | 특정 오브젝트가 리소스를 과도하게 요청하거나 사용하면 다른 오브젝트가 필요한 리소스를 확보하지 못할 수 있습니다. LimitRange는 오브젝트별 최대 리소스 한도(max)를 설정하여 리소스 독점을 방지하고, 클러스터의 안정성을 유지합니다. |
  | **리소스 부족 상황 예방** | 너무 적은 리소스를 요청한 오브젝트는 실행 도중 자원 부족으로 인해 비정상적으로 작동하거나 실패할 수 있습니다. LimitRange의 최소값(min) 설정을 통해 충분한 리소스를 확보하도록 강제하여 이러한 상황을 방지합니다. |
  | **리퀘스트-리미트 비율 제어** | 리소스 요청(request)과 사용(limit) 간 비율을 제한하여 예측 가능한 리소스 사용 환경을 제공합니다. 비정상적으로 높은 limit 설정은 리소스 사용량의 불균형을 초래할 수 있기 때문에, maxLimitRequestRatio로 방지합니다. |
  | **네임스페이스 간 리소스 균형** | 네임스페이스가 클러스터 자원을 공유하기 때문에 특정 네임스페이스의 과도한 리소스 사용은 다른 네임스페이스에 영향을 줄 수 있습니다. LimitRange는 개별 오브젝트의 리소스를 제한하여 네임스페이스 간 공정한 리소스 사용을 보장합니다. |
- #### LimitRange 동작 방식
- | 동작 방식 | 설명 |
  | :--- | :--- |
  | **요청 시 검증** | 사용자가 Pod 또는 컨테이너를 생성할 때, 해당 리소스 요청(request)과 제한(limit)이 LimitRange에서 설정한 규칙을 만족하는지 확인합니다.<br>  - *예시 1*: min보다 낮은 요청 ➔ 거부<br>  - *예시 2*: max를 초과한 요청 ➔ 거부<br>  - *예시 3*: maxLimitRequestRatio를 초과하는 비율 설정 ➔ 거부 |
  | **기본값 적용** | 사용자가 리소스 요청(request) 및 제한(limit)을 명시하지 않을 경우 LimitRange에서 정의한 default와 defaultRequest 값을 자동으로 할당합니다. 이를 통해 사용자는 모든 리소스를 명시적으로 설정하지 않아도 클러스터의 정책에 맞는 리소스 사용이 가능합니다. |
  | **네임스페이스 수준 리소스 관리와의 차별성** | LimitRange는 개별 오브젝트에 초점을 맞춘 리소스 제한을 제공합니다. 이는 네임스페이스 전체 리소스를 관리하는 ResourceQuota와 상호보완적으로 작동합니다. |

#### 주제 3: ConfigMap, Secret
- ConfigMap: 애플리케이션이 필요한 구성 데이터를 키-값 형태로 저장하여, 이를 Pod에 동적으로 주입하거나 환경 변수로 전달하는 쿠버네티스의 리소스
- #### ConfigMap의 특징 및 주요 개념
- | 개념 | 설명 |
  | :--- | :--- |
  | **구성 데이터의 키-값 저장** | ConfigMap은 문자열 데이터의 키-값 쌍을 저장하는데 최적화되어 있습니다. 저장된 값은 단순 문자열뿐만 아니라, YAML과 같은 형식으로도 포함될 수 있습니다. |
  | **Pod와 독립적인 구성 관리** | ConfigMap은 Pod와 독립적으로 관리됩니다. Pod 정의와 분리하여 구성 데이터를 변경하더라도, 새로운 ConfigMap을 Pod에 연결하거나 기존 값을 참조하도록 설정하면 됩니다. |
  | **다양한 주입 방식** | ConfigMap의 데이터는 Pod에 다음과 같은 방식으로 주입될 수 있습니다.<br>- **환경 변수**: 애플리케이션의 실행 환경 설정을 위한 변수로 사용<br>- **커맨드라인 인수**: 실행 시 인수로 전달<br>- **볼륨 마운트**: 파일 시스템의 파일로 주입하여 애플리케이션이 읽을 수 있도록 제공 |
  | **파일 마운트와 환경 변수의 차이점** | - **환경 변수 방식**: ConfigMap의 값이 Pod 시작 시점에만 로드되며, 이후 ConfigMap의 변경 사항은 Pod가 재시작되기 전까지 반영되지 않습니다.<br>- **파일 마운트 방식**: ConfigMap 값이 Pod 내에 파일로 마운트되며, ConfigMap 데이터가 변경되면 즉시 마운트된 파일에도 반영됩니다. |
- #### ConfigMap 사용 이유
- | 이유 | 설명 |
  | :--- | :--- |
  | **구성 데이터의 환경 독립성 유지** | ConfigMap은 애플리케이션의 구성 데이터를 코드에서 분리하여 관리합니다. 이를 통해 동일한 애플리케이션 이미지를 개발, 테스트, 운영 환경에서 재사용할 수 있습니다. 개발과 배포가 분리되므로 운영 효율성이 크게 향상됩니다. |
  | **중앙 집중적 구성 관리** | ConfigMap은 Kubernetes 리소스로 구성 데이터를 중앙에서 관리합니다. 구성 변경 시 Pod 정의를 수정하거나 애플리케이션 이미지를 재생성할 필요 없이 ConfigMap만 업데이트하면 됩니다. |
  | **구성 데이터 변경의 유연성 제공** | ConfigMap은 애플리케이션 실행 중에도 데이터를 동적으로 변경할 수 있는 옵션(파일 마운트 방식)을 제공합니다. 이를 통해 변경된 설정이 즉시 반영될 수 있습니다. 환경 변수 방식의 경우에도 구성 변경 시 Pod를 재시작하여 반영할 수 있습니다. |
  | **구성 관리와 보안 분리** | 민감하지 않은 구성 데이터를 관리하는 ConfigMap은 Kubernetes Secret과 역할이 분리되어, 보안 필요성이 낮은 일반적인 데이터를 효율적으로 관리할 수 있습니다. |
  | **애플리케이션 설정 복잡성 감소** | ConfigMap을 활용하면 복잡한 설정 파일이나 스크립트를 관리할 필요 없이, 단순한 키-값 형태로 데이터를 저장하고 애플리케이션에 주입할 수 있습니다. |
  | **운영 중단 없이 구성 데이터 유지** | ConfigMap은 코드 변경 없이 구성을 업데이트할 수 있으므로, 운영 중단 없이 애플리케이션 동작을 조정할 수 있습니다. 특히, 파일 마운트 방식을 사용하면 동적 데이터 변경이 가능합니다. |
  | **👨‍💻 현업 빅테크 클라우드 엔지니어 코멘트** | ConfigMap은 코드 변경 없이 구성을 업데이트할 수 있지만, 운영 중단 없이 적용하려면 애플리케이션이 설정 reload 방식을 지원해야 합니다. |

---
- Secret: 민감한 데이터를 안전하게 저장하고 Pod에 전달하기 위해 설계된 키-값 쌍 기반의 리소스
- #### Secret의 주요 특징
- | 특징 | 설명 |
  | :--- | :--- |
  | **보안 중심 설계** | Secret은 민감한 정보를 외부에 노출하지 않도록 설계되었습니다. 이를 통해 민감 데이터가 Pod 명령어, 로그, 환경 변수로 무분별하게 노출되는 것을 방지할 수 있습니다. 단, Secret 자체는 쿠버네티스 관리 권한에 따라 접근이 가능하므로, 철저한 권한 관리가 요구됩니다. |
  | **유연한 데이터 전달 방식** | - **환경 변수(Environment Variable)**: Secret 데이터를 Pod의 환경 변수로 주입하여 애플리케이션이 이를 참조하도록 할 수 있습니다.<br>- **파일 마운트(Volume Mount)**: Secret을 파일로 마운트하여 애플리케이션이 파일을 읽는 방식으로 데이터를 사용할 수 있습니다.<br>- **런타임 반영**: Secret 데이터가 변경되었을 때, Pod가 재시작 없이도 파일 마운트를 통해 즉시 반영됩니다. |
  | **👨‍💻 현업 빅테크 클라우드 엔지니어 코멘트** | Secret 데이터는 파일 마운트를 통해 갱신되더라도, 애플리케이션이 reload를 지원해야 실제로 반영됩니다. 즉, 파일 내용은 업데이트되지만, 애플리케이션이 이를 다시 읽지 않으면 설정은 그대로 유지됩니다. |
  | **타입 기반 관리** | Secret은 데이터를 관리하기 위해 opaque(기본값) 외에도 Docker Registry 인증 등 특정 목적으로 설계된 타입을 지원합니다. 이를 통해 다양한 애플리케이션 요구사항에 맞춘 Secret 관리를 구현할 수 있습니다. |
- #### Secret의 속성
- | 속성 | 설명 |
  | :--- | :--- |
  | **stringData** | 사용자 입력 시 사용되는 쓰기 전용 속성으로, 사람이 읽을 수 있는 평문(Plain Text) 키-값 데이터를 받습니다. |
  | **data** | `stringData`에 입력된 값이 Base64로 자동 인코딩되어 저장되는 속성입니다. 쿠버네티스 내부에서 실제 데이터가 보관되는 필드입니다. |
  | **타입 (type)** | Secret의 사용 목적에 따라 지정되며, 기본값은 `Opaque`입니다.<br>- **Opaque**: 일반적인 키-값 쌍 데이터를 저장하는 기본 타입 (예: API 키, DB 패스워드)<br>- **kubernetes.io/tls**: TLS/SSL 인증서와 개인 키를 저장하는 타입 (예: HTTPS 인증서 관리)<br>- **kubernetes.io/dockerconfigjson**: Docker 프라이빗 레지스트리의 인증 정보를 저장하는 타입 (예: 프라이빗 이미지 저장소 접근 권한) |
- #### Secret 사용 이유
- | 이유 | 설명 |
  | :--- | :--- |
  | **민감 데이터의 안전한 저장 및 전달** | Secret은 데이터베이스 비밀번호, API 키, TLS 인증서와 같은 민감 데이터를 안전하게 관리하기 위해 설계되었습니다. ConfigMap과 달리 Secret은 데이터를 Base64로 인코딩하여 저장하며, RBAC(Role-Based Access Control)을 통해 접근 권한을 제한할 수 있습니다. |
  | **유연한 데이터 전달 방식 제공** | Secret은 Pod에 환경 변수, 파일 마운트, 또는 특정 애플리케이션 설정으로 데이터를 전달할 수 있습니다. 특히 파일 마운트를 사용하면 Secret 데이터의 변경 사항이 Pod에 실시간으로 반영될 수 있어 운영 중에도 민감 데이터 변경이 가능합니다. |
  | **보안 사고 방지 및 규제 준수** | Secret을 사용하면 데이터 노출을 최소화하여 보안 사고를 예방할 수 있습니다. 예를 들어, 민감 데이터를 ConfigMap에 저장하면 쉽게 노출될 위험이 있지만, Secret은 해당 데이터를 필요한 Pod가 실행되는 노드에만 배포하여 보안성을 높입니다. |
