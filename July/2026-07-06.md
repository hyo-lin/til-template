### 새로 배운 내용
#### 주제 1: CI, Test Code
- CI: 개발자가 작성한 코드를 자동으로 통합 및 테스트하여 코드의 품질을 지속적으로 유지하는 개발 프로세스
  - 코드 통합 과정에서 발생하는 문제를 빠르게 찾고 빌드 및 테스트를 자동화하기 위해서
- ### 🚀 개발 프로세스 (Development Process)

| 단계 | 프로세스명 | 설명 |
| :---: | :--- | :--- |
| **1** | **개발 (Develop)** | 개발자가 기능 개발 및 버그 수정 등의 코드 작업을 수행하는 단계 |
| **2** | **소스 관리 (Source Control)** | 개발자의 코드 변경 사항을 중앙의 저장소에 체계적으로 관리하는 단계 |
| **3** | **빌드 (Build)** | 통합된 소스 코드를 컴파일하여 실행 가능한 형태(바이너리, 패키지 등)로 변환하는 단계 |
| **4** | **테스트 (Test)** | 빌드된 코드가 정상적으로 작동하는지 자동화된 유닛 테스트, 통합 테스트, E2E 테스트 등을 수행하는 단계 |
| **5** | **리포트 (Report)** | 빌드 및 테스트 결과를 팀 구성원에게 즉각적으로 보고하여 코드 품질 상태를 공유하는 단계 |
- Jenkins: 대표적인 오픈 소스 CI/CD 도구로, 빌드 및 테스트 과정을 자동화하여 관리할 수 있는 서버 환경을 제공
  - 다양한 플러그인을 통해 자바, 파이썬, Node.js 등 여러 언어와 환경을 지원하며, 유연한 파이프라인 설정이 가능해 복잡한 빌드 및 테스트 시나리오를 손쉽게 구현
- GitHub Actions: GitHub에서 기본으로 제공하는 CI/CD 서비스
  - 별도의 외부 설정 없이 GitHub 리포지토리 내에서 YAML 형식으로 워크플로우를 작성할 수 있으며, 코드 푸시(push)나 풀 리퀘스트(pull request) 등의 GitHub 이벤트가 발생할 때 자동으로 작업을 수행
## 1. 왜 CI가 필요한가?

### ❌ CI가 없을 때 발생하는 문제 (Integration Hell)
* **대형 충돌:** 개발자 각자가 기능을 로컬에서 오랫동안 개발(예: A 결제, B 주문, C 회원)한 뒤 한 번에 합치면, 같은 파일 수정 및 의존성 꼬임으로 인해 거대한 싱크 에러가 발생합니다.
* **추적 불가능:** "언제", "누구의 커밋" 때문에 문제가 생겼는지 원인을 추적하기가 극도로 힘들어집니다.
* **테스트 누락:** 로컬 환경에서만 "잘 되는데?" 하고 검증을 빼먹은 채 메인 브랜치에 병합되어 배포 직전에야 수많은 버그를 발견합니다.

###  CI가 해결하는 방식
| 기존 문제점 | CI 도입 후 해결 방식 |
| :--- | :--- |
| 개발자가 로컬에서만 테스트함 | 공통된 **독립 Runner 환경**에서 자동 검증 |
| 병합 후 빌드 실패 발견 | **PR 생성 및 main 병합 직후** 즉시 자동 빌드 |
| 테스트를 빼먹음 | **테스트 통과를 병합 조건(Quality Gate)**으로 강제 설정 |
| 코드 리뷰만으로 오류 탐색 | 자동 테스트와 **정적 분석(Static Analysis)** 병행 |
| 누가 깨뜨렸는지 모름 | 커밋·PR 단위의 **실행 로그와 결과 리포트** 제공 |
| 배포 직전 문제 일괄 발견 | 작은 변경 단위로 **빠르게 실패(Fail Fast)**하고 즉시 수정 |

## 2. CI를 구성하는 4대 원칙

### ① 하나의 신뢰할 수 있는 코드 베이스
* **`main` 브랜치:** 팀원 모두가 신뢰하는 브랜치로, **항상 빌드가 성공하고 언제든 배포가 가능한 상태**를 유지해야 합니다.
* **브랜치 전략 표준:** `main` ➡️ `dev` ➡️ `feature/기능명` 순으로 뻗어나가며, 최종적으로는 다시 `dev`와 `main`으로 안전하게 자동 검증을 거쳐 합쳐져야 합니다.

### ② 변경 사항을 "자주, 더 작게" 통합
* 기능을 4주 동안 꽁꽁 싸매다 한 번에 합치면 통합 비용과 테스트 비용이 기하급수적으로 커집니다. 개발자는 본능적으로 CI 작업을 회피(사이드 잡으로 인식)하게 됩니다.
* **권장하는 올바른 변경 단위:**
    * ✅ `로그인 API 형식 수정` ➡️ **통합**
    * ✅ `특정 예외 처리 로직 추가` ➡️ **통합**
    * ✅ `Dockerfile 개선` ➡️ **통합**
    * ❌ `인증, 결제, 주문, 쿠폰을 한 PR에 다 넣고 통합` (절대 금지)
    * ❌ `전역 리팩토링과 신규 기능 추가를 한 PR에 섞기` (절대 금지)

### ③ 재현 가능한 빌드 (Reproducible Build)
* *"내 노트북에서는 잘 되는데, CI 서버에서는 안 돼요!"*를 방지해야 합니다. Environment Context와 의존성이 모두 코드에 박혀있어야 합니다.
* **프로젝트 포함 필수 항목:**
    * **의존성 & 빌드:** `build.gradle` / `pom.xml` / `package.json`
    * **컨테이너 환경:** `Dockerfile`, `docker-compose.yml`
    * **자동화 스크립트:** `.github/workflows/*.yml` (GitHub Actions 설정)
    * **설정 공유:** `.env.example` (시크릿을 제외한 환경 변수 구조 백업)

### ④ 자동화된 테스트 실행
* 단순 컴파일/빌드 성공이 끝이 아닙니다. 코드가 합쳐질 때마다 비즈니스 요구사항(예: *"유저 가입 시 응답으로 ID가 나와야 함"*)이 완벽히 작동하는지 **자동으로 검증**해야 합니다.

## 3. 시점별 CI 검증 목적

동일한 코드더라도 검증하는 시점에 따라 목적이 다릅니다.

* **Pull Request 생성·수정 시:** 메인 브랜치에 병합되기 전, 시스템에 치명적인 영향을 줄 수 있는 위험한 변경을 선제적으로 차단합니다.
* **Main 브랜치 병합 후:** 여러 사람의 코드가 실제로 섞인 **최종 통합 상태**에서 예기치 못한 사이드 이펙트가 없는지 다시 검증합니다.
* **배포 직전:** 최종 릴리스 단계로 나가기 전, 최종 산출물(Artifact)이 완전히 정상인지 마지막으로 확인합니다.

## 테스트 종류 및 검증 대상 우선순위

모든 코드를 100% 다 테스트할 수는 없습니다. **장애 발생 시 피해가 크고 복잡한 비즈니스 로직**부터 촘촘하게 방어해야 합니다.

| 종류 | 확인 대상 | 특징 | CI 적용 우선순위 |
| :--- | :--- | :--- | :---: |
| **단위 테스트<br>(Unit Test)** | 함수, 클래스, 개별 서비스 로직 | 실행 속도가 매우 빠르고, 실패 시 원인 추적이 명확함 | **매우 높음** |
| **통합 테스트<br>(Integration Test)** | DB, Redis, API, 모듈 간 연동 | 실제 인프라 환경에서 발생하는 문제를 가장 잘 발견함 | **높음** |
| **정적 분석<br>(Static Analysis)** | 코드 규칙, 잠재적 코드 스멜 | 코드를 직접 실행하기 전에 문법과 품질 규격을 검사함 | **높음** |
| **E2E 테스트<br>(End-to-End)** | 사용자의 전체 시나리오 흐름 | 실제 사용자 경험과 가장 가까우나, 속도가 느림 | **선택적 (핵심만)** |

- Test Driven Development: 구현 코드를 작성하기 전에 → 테스트 코드를 먼저 작성하고 → 테스트 코드를 통과하는 구현 코드를 작성하는 개발 방법론

#### 주제 2: CD, Github Action
- CD: 코드가 자동화된 테스트를 통과하면 운영 환경까지 자동으로 배포되는 소프트웨어 배포 프로세스
  - 코드가 준비되는 즉시 사람의 승인 없이 자동으로 운영 환경에 반영하여, 배포 속도를 최대화하고 배포 과정에서 발생하는 지연·수동 작업을 제거하기 위해서
- | 단계 | 프로세스명 | 설명 | 관련 도구 예시 |
  | :---: | :--- | :--- | :--- |
  | **1** | **배포 (Deploy)** | 빌드 및 테스트를 통과한 소프트웨어를 운영 또는 스테이징 환경으로 자동 배포하는 단계 | Jenkins, GitHub Actions, Argo CD |
  | **2** | **모니터링 & 리포트** | 배포된 소프트웨어가 정상적으로 동작하는지 확인하고 결과를 보고하는 단계 | Jenkins, Slack, Grafana |

- CD = CI 이후의 "배포 과정"을 자동화하는 것. 배포 결과를 검증하고, 실패하면 이전 버전으로 복구하는 것까지 포함함.
- 수동 배포의 구체적 문제 상황
    - 핵심: 명령어 치는 시간이 오래 걸리는 게 문제가 아니라, 진행하는 사람마다 배포 결과가 달라질 가능성이 문제다.
    - 요청하신 내용을 한눈에 보기 편하게 정리한 마크다운 표입니다.
- ### CD가 해결하는 것들

| 해결하려는 문제 | CD(지속적 배포)가 제공하는 방식 |
| --- | --- |
| **반복적인 배포 작업** | 정해진 파이프라인으로 자동 실행 |
| **사람의 실수** | 테스트 성공한 경우에만 다음 단계 진행 |
| **배포 버전 추적 어려움** | 이미지 태그, Commit SHA, 배포 이력 관리 |
| **환경별 설정 혼동** | 개발·스테이징·운영 환경 분리 |
| **배포 후 장애 발견** | Health Check, 로그, 모니터링 |
| **장애 시 복구 지연** | 이전 안정 버전으로 롤백 |
| **동시 배포 충돌** | 배포 순서와 실행 권한 제어 |
- ### CD 흐름
| 단계 | 하는 일 | 예시 |
| --- | --- | --- |
| **CI** | 코드 품질 검증 | 빌드, 테스트, 정적 분석 |
| **Artifact 생성** | 배포 가능한 결과물 생성 | .jar, Docker 이미지, dist/ |
| **Registry 저장** | 결과물을 저장하고 배포 대상에 전달 | Docker Hub, Amazon ECR |
| **Deploy** | 서버/플랫폼에 새 버전 반영 | EC2, ECS, Kubernetes |
| **Health Check** | 새 버전이 실제로 정상 동작하는지 확인 | /health API 호출 |
| **Monitoring** | 배포 이후 장애 여부 확인 | 로그, 에러율, CPU, 응답 시간 |
| **Rollback** | 문제 발생 시 이전 안정 버전으로 복구 | 이전 이미지 재배포, 트래픽 전환 |

- Github Action: GitHub 저장소(Repository) 내에서 코드 빌드, 테스트, 배포 등의 워크플로우를 자동화하는 CI/CD 도구
- 수동 배포의 문제점 vs GitHub Actions의 해결 방식
  - 사람이 직접 Push ➔ Pull ➔ 의존성 설치 ➔ 테스트 ➔ 빌드 ➔ Docker 이미지 생성/Push ➔ EC2/ECS 배포 단계를 거치면 다음과 같은 문제가 생깁니다.

  - 작업 누락 및 사람의 실수: 특정 단계를 빼먹거나 명령어를 잘못 입력할 수 있음.
    
  - 환경 차이: 개발자 로컬 PC와 운영 서버의 환경(OS, Java/Node 버전 등)이 달라 오류 발생.
    
  - 속도 저하: 매번 반복적인 작업을 수동으로 하느라 배포 속도가 느려짐.

- | 구성 요소 | 📝 한 줄 설명 | 💡 대표 예시 |
  | :--- | :--- | :--- |
  | **Event** | 워크플로우를 트리거(시작)시키는 GitHub 내부의 사건 | `push`, `pull_request`, `workflow_dispatch` |
  | **Workflow** | 자동화 전체 흐름을 정의한 최상위 설정 파일 | `.github/workflows/ci.yml` |
  | **Job** | 동일한 Runner 내에서 실행되는 독립된 작업 단위 | `test`, `build`, `deploy` |
  | **Step** | Job 안에서 순차적으로 실행되는 세부 태스크(Task) | 코드 내려받기, 의존성 설치, 테스트 실행 |
  | **Action** | 자주 복습/반복되는 기능을 재사용할 수 있게 만든 코드 조각 | `actions/checkout`, `actions/setup-node` |
  | **Runner** | Job 인프라가 실제로 구동되는 가상 머신 또는 OS 환경 | `ubuntu-latest`, Self-hosted Runner |

### 🔍 구성 요소별 상세 개념

#### 1. Event (이벤트)
* 워크플로우를 실행시키는 '트리거' 역할을 합니다.
* 개발자의 행동(`push`, `PR 생성`)뿐만 아니라, 특정 시간에 주기적으로 실행하는 `schedule`이나 직접 수동으로 실행하는 `workflow_dispatch` 등이 있습니다.

#### 2. Workflow (워크플로우)
* 여러 Job으로 구성된 전체 프로세스를 담은 고수준 자동화 절차입니다.
* 리포지토리 루트의 `.github/workflows/` 디렉터리 하위에 `yaml` 파일 형태로 저장되어 형상 관리가 이루어집니다.

#### 3. Job (작업)
* 워크플로우 내에서 실행되는 독립적인 단위입니다.
* 각 Job은 **기본적으로 서로 다른 Runner 환경에서 병렬(Parallel)로 실행**되며, 설정에 따라 선행 Job이 끝나야만 후속 Job이 실행되도록 의존 관계(`needs`)를 맺을 수 있습니다.
- | 특징 | 📝 상세 설명 | ⚙️ 구현 및 제어 방식 |
  | :--- | :--- | :--- |
  | **기본 실행 방식** | 모든 Job은 기본적으로 **병렬(Parallel) 실행**이 가능합니다. | 순서 지정이 없으면 선후 관계없이 동시에 러너가 할당됩니다. |
  | **실행 환경** | 각 Job은 **완전히 분리된 독립된 Runner**에서 실행됩니다. | 컨테이너/VM 격리로 인해 상호 간에 환경 간섭이 없습니다. |
  | **파일 공유** | Job 간의 파일이나 데이터는 **자동으로 공유되지 않습니다.** | 빌드 아티팩트(`upload-artifact`)나 캐시를 명시적으로 써야 합니다. |
  | **실행 순서 제어** | Job 간의 선후 관계 및 의존성을 직접 지정할 수 있습니다. | 후속 Job에 `needs: [선행_Job_이름]` 속성을 명시합니다. |
  | **실패 처리** | 파이프라인 진행 중 특정 Job에서 에러가 나면 중단됩니다. | 선행 Job이 실패하면 후속 Job은 기본적으로 실행되지 않고 생략됩니다. |
#### 4. Step (단계)
* 하나의 Job 안에서 차례대로 실행되는 단일 명령들의 집합입니다.
* 쉘 스크립트 명령어(`run`)를 직접 실행하거나, 미리 정의된 플러그인(`uses`)을 호출하여 수행합니다.

#### 5. Action (액션)
* 복잡하고 자주 쓰이는 Step들을 모아 공유할 수 있게 만든 GitHub Actions의 핵심 플러그인 생태계입니다.
* 환경 셋업, 체크아웃, 클라우드 인증 등 반복적인 인프라 코드를 획기적으로 줄여줍니다.

#### 6. Runner (러너)
* GitHub Actions가 제공하는 호스팅 서버(`GitHub-hosted`) 또는 사내 내부망 및 특정 인프라에 직접 띄워두고 사용하는 서버(`Self-hosted`)를 지정할 수 있습니다.



#### 주제 3:Artifact
- Artifact: CI를 통과하고 나서 실제로 배포할 수 있는 결과물
  - 스프링 → .jar
  - 도커 → image
  - React/Vue → dist/
