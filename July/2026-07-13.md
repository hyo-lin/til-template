#### 주제 1: Kubernetes, 선언적 관리
### 1. 인프라 실행 환경의 발전사 (물리 서버부터 컨테이너까지)

#### 1) 물리 서버 (Bare Metal) 시대
* **구조:** 하나의 물리 하드웨어 위에 하나의 OS를 올리고, 그 위에 프론트엔드, 백엔드, DB 등을 직접 설치하여 구동.
* **한계점:**
    * **자원 격리 불가:** 특정 앱이 메모리를 많이 먹으면 다른 앱까지 통달하여 느려짐.
    * **라이브러리 충돌:** 애플리케이션 간 필요한 의존성 버전이 다를 때 충돌 발생.
    * **낮은 가용성과 확장성:** 서버 한 대가 죽으면 전체 서비스 다운. 물리 서버 증설은 리드 타임이 매우 긺.

#### 2) 가상 머신 (VM / 하이퍼바이저) 시대
* **구조:** 물리 서버 위에 하이퍼바이저(Hypervisor)를 두고, 자원을 쪼개어 독립된 **Guest OS**를 가진 VM들을 구동 (예: AWS EC2).
* **해결된 문제:** 애플리케이션 간 완벽한 격리, 자원 사용량 분리, 클라우드를 통한 유연한 확장성 확보.
* **새로운 문제점:** 각 VM마다 무거운 운영체제(Guest OS)를 통째로 올리기 때문에 **자원 오버헤드가 크고 무거움**. 이미지 용량이 수십 GB에 달하며, 부팅 및 초기 실행 시간이 느림. 매번 OS 보안 패치를 해야 하는 관리 포인트 발생.

#### 3) 컨테이너 (Container) 시대
* **구조:** Host OS의 커널(Kernel)을 공유하면서, 프로세스 레벨에서 실행 환경을 격리하는 기술 (예: Docker).
* **장점:** Guest OS가 제외되어 **가볍고 실행 속도가 VM과 비교 안 되게 빠름**. 애플리케이션 실행에 필요한 최소한의 파일만 담아 이미지 용량이 수백 MB로 감소. 환경 일관성이 보장되어 CI/CD 환경 통합에 최적.

### 2. 도커(Docker)의 한계와 쿠버네티스의 필요성

> 💡 **"도커는 단일 서버에서 컨테이너를 쉽게 실행해 주지만, 수많은 컨테이너를 여러 서버에 걸쳐 '운영 및 지휘'하는 문제는 해결하지 못합니다."**

서비스 규모가 커져 컨테이너 수가 수백 개로 늘어나면 사람이 수동으로 관리할 때 3대 대재앙이 발생합니다.

* **문제 1 (장애 복구):** 컨테이너가 에러나 메모리 부족(OOM)으로 죽었을 때, 35대의 서버 중 어느 서버에서 왜 죽었는지 사람이 일일이 찾아 재시작하기 어려움.
* **문제 2 (스케줄링/배치):** 백엔드 트래픽 급증으로 컨테이너를 늘려야 할 때, 여러 서버의 실시간 CPU/메모리 유휴 자원량을 고려하여 어느 노드에 배치해야 최적일지 수동 판단 불가.
* **문제 3 (서버 장애 대응):** 컨테이너들을 품고 있던 특정 물리 서버(EC2) 한 대가 완전히 뻗었을 때, 그 안의 워크로드들을 자원이 남는 다른 서버들로 신속하게 자동 재배치(Migration)해야 함.

#### 🎼 컨테이너 오케스트레이션 (Container Orchestration)
여러 서버에서 실행되는 수많은 컨테이너의 **배치, 연결, 감시, 복구, 확장 작업을 지휘자처럼 자동화**하는 것을 의미하며, 이를 수행하는 최강의 플랫폼이 바로 쿠버네티스(Kubernetes, k8s)입니다.

---

- Kubernetes : 컨테이너화된 애플리케이션을 어디서나 배포, 확장, 관리할 수 있는 오픈소스 시스템
  - 애플리케이션의 안정적이고 간편한 확장 및 관리를 자동화해 운영 복잡성을 줄이기 위해서
  - 컨테이너가 종료되거나 애플리케이션에 문제 발생 → 다시 실행하도록 구성
  - 애플리케이션 요구사항을 보고 알아서 필요한 노드에 배치
  - 확장성
  - 실행 환경, 원하는 상태를 YAML 파일로 정의하는데 이 파일을 관리하면 운영환경이 어디에서나 다 똑같이 돌릴 수 있다.
- 선언적 관리: 사용자가 작업 방법을 하나씩 명령하는 것이 아니라, 최종적으로 원하는 상태를 정의하는 방식
- Desired State: 쿠버네티스에서는 원하는 상태 ↔ 현재 상태를 지속적으로 비교
- 지속적으로 상태를 조정: 쿠버네티스는 현재 상태를 관찰, 원하는 상태와 다르면 필요한 작업을 수행
- #### 쿠버네티스 요소
  - 클러스터: 쿠버네티스가 관리하는 여러 서버, 컨테이너, 리소스의 집합
    - 쿠버네티스 클러스터는 하나 이상의 마스터 노드와 여러 워커 노드로 구성됩니다.
  - Node: 클러스터를 구성하는 서버
- 마스터 노드: 클러스터를 제어하고 관리하는 중앙 제어 장치
  - Control Plane: 클러스터 전체의 상태를 관리하고, 파드 배치 판단하는 중앙 제어 영역
    - kube-apiserver: 클러스터와 상호작용하는 주 인터페이스 입니다.
    - kube-controller-manager: 클러스터의 상태를 원하는 상태로 유지하기 위해 다양한 컨트롤러를 실행합니다.
    - kube-scheduler: 사용자의 요청에 따라 Pod를 적절한 워커 노드에 배치하는 스케줄러입니다.
    - etcd: 클러스터의 모든 데이터(구성 정보, 상태 등)를 저장하는 키-값 저장소입니다.
    - cloud-controller-manager: AWS, GCP, Azure와 같은 클라우드 플랫폼에 특화된 리소스를 제어하는 컴포넌트입니다.
- 워커 노드: 애플리케이션이 실행되는 파드를 호스팅하는 서버
  - 실제로 컨테이너 애플리케이션이 실행되는 노드입니다.
    - kubelet: 각 노드에서 실행되며, 마스터 노드와 통신하여 컨테이너의 상태를 보고하고 관리합니다.
    - kube-proxy: 각 노드에서 네트워킹을 관리하며, 서비스 디스커버리와 로드 밸런싱을 지원합니다.
    - container runtime: 컨테이너를 실행하는 소프트웨어입니다(예: Docker, containerd).
- Pod: 쿠버네티스에서 가장 작은 배포 단위로, 하나 이상의 컨테이너를 포함합니다.
  같은 Pod 내의 컨테이너는 네트워크와 스토리지를 공유합니다.


#### 주제 2: CNI 와 Flannel
### 1. CNI (Container Network Interface) 개요
* **정의:** 컨테이너의 네트워크를 설정하고 제거하는 방법을 정의한 **표준 규격 인터페이스**입니다.
* **약속:** "컨테이너끼리 통신할 때 최소한 이런 규격과 라이프사이클을 지키자"는 일종의 규칙 사양서입니다.
* **존재 이유:**
    * **관심사 분리:** 쿠버네티스는 '컨테이너 오케스트레이션' 툴이지 네트워크 전문 툴이 아닙니다. CNI가 없다면 쿠버네티스 코어 코드가 AWS, GCP, NCP, 온프레미스 등 세상의 모든 네트워크 환경을 직접 다 구현해야 합니다.
    * **인프라 종속성 탈피:** 표준 인터페이스를 둠으로써 특정 클라우드 공급사(CSP)에 종속되지 않고 동일한 사양으로 어디서나 클러스터를 구축할 수 있습니다.
* **대표적인 구현체 종류:** `Flannel`, `Calico`, `Cilium`

### 2. Flannel CNI 플러그인의 특징
* **개념:** 여러 노드에 흩어져 있는 Pod들이 서로 통신할 수 있도록 오버레이(Overlay) 네트워크를 구성하는 플러그인입니다.
* **IP 대역 분배 메커니즘:**
    * 클러스터 전체 Pod 대역이 `10.244.0.0/16`이라면, Flannel은 각 노드마다 겹치지 않게 서브넷 마스크(`/.../24`) 쪼개어 할당합니다.
    * **Node A (Worker 1):** `10.244.1.0/24` $\rightarrow$ (내부 Pod들은 `10.244.1.2`, `10.244.1.3` 등 할당)
    * **Node B (Worker 2):** `10.244.2.0/24` $\rightarrow$ (내부 Pod들은 `10.244.2.2`, `10.244.2.3` 등 할당)

####  CNI (Flannel) 플러그인의 역할

| 역할 분류 | 상세 설명 | 비고 |
| :--- | :--- | :--- |
| **노드별 Pod 대역 관리** | 각 노드가 겹치지 않고 독립적으로 사용할 가상 Pod IP 대역(Subnet)을 분배하고 관리합니다. | 클러스터 내 IP 충돌 방지 |
| **Pod 네트워크 구성** | Pod 생성 시 가상 인터페이스(veth pair)를 만들고 로컬 라우팅 경로를 잡아줍니다. | 컨테이너 삭제 시 네트워크 자원 정리 |
| **노드 간 통신 경로 제공** | 크로스 노드(Cross-Node) 환경에서 다른 서버에 있는 Pod끼리 통신할 수 있는 길을 엽니다. | 클러스터 통합 네트워크 맵 구축 |
| **패킷 캡슐화** | **VXLAN** 기술을 사용하여 가상 Pod 패킷의 겉면에 물리 Node 간 전송이 가능한 겉봉투를 씌웁니다. | AWS 등 기존 네트워크 장비 우회 |

---

### 3. 크로스 노드 통신의 핵심: VXLAN (Virtual eXtensible LAN)
> **왜 필요할까?** 같은 노드 내부의 Pod끼리는 리눅스 브릿지를 통한 로컬 가상 네트워크로 바로 통신이 가능합니다. 하지만 다른 노드로 갈 때는 AWS 라우터 같은 물리 장비가 가상 영역인 `Pod IP (10.244.x.x)`를 전혀 알지 못하므로, 이를 해결하기 위해 **터널링(VXLAN)** 기술이 필수적입니다.

#### 📦 VXLAN 이중 포장(캡슐화) 구조 안내
물리 네트워크 장비가 알아볼 수 있도록 원래의 TCP 패킷을 가벼운 UDP 패킷으로 감싸서 배송합니다.
