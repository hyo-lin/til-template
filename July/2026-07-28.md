#### 주제 1: ArgoCD
## ArgoCD
- ArgoCD: 쿠버네티스 클러스터의 애플리케이션 배포 및 관리를 자동화하는 GitOps 기반의 지속적 배포(Continuous Delivery) 솔루션
- #### ArgoCD 사용 이유

| 이유 | 설명 |
| --- | --- |
| **운영 환경의 일관성 유지** | 쿠버네티스 환경에서는 운영, 테스트, 개발 환경 간 설정 불일치가 발생할 수 있습니다. ArgoCD는 Git 저장소를 '단일 진실 공급원(Single Source of Truth)'으로 삼아, 모든 환경에서 동일한 설정을 유지하도록 보장합니다. |
| **배포 자동화 및 효율성 향상** | 수작업 배포는 시간이 오래 걸리고 오류 발생 가능성이 높습니다. ArgoCD는 CI/CD 파이프라인과 통합하여 Git 커밋만으로 배포를 자동화하고 즉각적인 환경 반영을 가능하게 합니다. |
| **변경 관리 및 감사 추적 강화** | 애플리케이션의 배포 변경 이력을 효과적으로 추적하기 위해서는 중앙 집중된 변경 관리가 필요합니다. ArgoCD는 Git을 기반으로 모든 변경 사항을 기록하여 누가 언제 어떤 변경을 했는지 확인할 수 있으며, 필요 시 Git 히스토리를 활용한 롤백을 간편하게 수행할 수 있습니다. |
| **다양한 배포 전략 지원** | ArgoCD는 기본적인 Rolling Update뿐만 아니라 Blue-Green 및 Canary 배포 전략을 지원합니다. 이를 통해 트래픽을 점진적으로 새로운 버전에 분배하거나, 문제 발생 시 즉시 이전 버전으로 롤백할 수 있습니다. |
| **실시간 모니터링 및 문제 대응** | ArgoCD는 대시보드를 통해 배포 상태를 시각적으로 확인할 수 있으며, Git과 클러스터 간 불일치 발생 시 이를 감지하여 자동으로 동기화합니다. 또한 Slack, 이메일과 같은 알림 시스템과 연동하여 문제를 조기에 인지하고 대응할 수 있도록 합니다. |
| **멀티 클러스터 배포 관리** | 하나의 ArgoCD 인스턴스를 통해 여러 클러스터를 관리할 수 있습니다. 이를 통해 글로벌 환경에서 여러 지역에 걸친 쿠버네티스 클러스터를 중앙에서 관리하고 환경별로 배포를 최적화할 수 있습니다. |

- #### ArgoCD 특징

| 특징 | 설명 |
| --- | --- |
| **GitOps 기반 배포** | 애플리케이션의 상태와 구성을 Git 저장소에 선언적으로 정의하고 이를 기준으로 Kubernetes 클러스터를 자동으로 동기화합니다. Git에 저장된 애플리케이션 정의가 변경되면 ArgoCD가 이를 감지하여 클러스터에 반영하며, 쿠버네티스 클러스터에서 수동 변경이 발생하더라도 Git과의 차이를 감지하여 동기화를 수행합니다. |
| **지속적 비교 및 상태 모니터링** | ArgoCD는 배포된 애플리케이션과 Git의 선언적 상태를 지속적으로 비교하며, 불일치가 발생할 경우 자동으로 조치를 취하거나 알림을 제공합니다. 이를 통해 수동 배포로 인한 설정 불일치 문제를 방지하고 항상 일관된 애플리케이션 상태를 유지합니다. |
| **다양한 배포 전략 지원** | ArgoCD는 기본적인 Rolling Update뿐만 아니라 Blue-Green Deployment 및 Canary Deployment와 같은 배포 전략을 지원합니다. 사용자 트래픽에 영향을 최소화하면서 점진적 배포 및 롤백이 가능하도록 설계되었습니다. |
| **다중 클러스터 관리** | 단일 ArgoCD 인스턴스를 사용하여 여러 쿠버네티스 클러스터를 동시에 관리할 수 있습니다. ApplicationSet Controller를 통해 환경별, 클러스터별 중복 구성을 최소화할 수 있습니다. |

- #### ArgoCD의 핵심 구성 요소

| 구성 요소 | 설명 |
| --- | --- |
| **API Server (Server)** | 사용자 인터페이스(UI)와 CLI 명령을 처리하며, Kubernetes API 서버와 통신하여 배포 작업을 수행합니다. |
| **Repo Server** | Git 저장소와 연동하여 선언적 구성 파일(Helm, Kustomize 포함)을 가져오고, 쿠버네티스 매니페스트로 변환합니다. |
| **Application Controller** | 쿠버네티스 클러스터의 상태를 지속적으로 모니터링하고, Git과의 일관성을 유지하도록 동기화 작업을 수행합니다. |
| **ApplicationSet Controller** | 여러 클러스터에 대한 배포를 간소화하고, 환경별 배포 구성을 템플릿화하여 관리할 수 있도록 지원합니다. |
| **기타 인프라 의존 요소** | Kubernetes API 서버, Git 리포지토리, 인증 시스템(Dex 등) 등이 ArgoCD의 기본 동작을 위해 필요합니다. |

### 1. 소스 코드 변경 및 빌드 단계 (CI)

> **CI(Continuous Integration)** 단계에서는 개발자가 소스 코드를 변경하면 자동으로 빌드, 테스트, 컨테이너 이미지 생성까지 완료하고 Kubernetes 배포 설정을 업데이트합니다.

| 순서 | 동작 | 설명 |
| --- | --- | --- |
| **1** | **개발자가 Git 저장소에 코드 커밋** | 개발자가 애플리케이션의 기능 추가, 수정 또는 버그 패치 등을 반영한 소스 코드를 로컬에서 수정한 후, GitHub과 같은 원격 저장소로 푸시합니다. |
| **2** | **CI 도구 트리거 동작** | Git 저장소에 푸시된 변경 사항을 CI 도구(Jenkins, GitHub Actions 등)가 감지하면 파이프라인이 자동 실행됩니다. 소스 코드 빌드 및 테스트 수행 후 성공 시 Docker 컨테이너 이미지를 생성하여 이미지 레지스트리(Docker Hub, AWS ECR 등)에 업로드합니다. |
| **3** | **Kubernetes 배포 파일 업데이트** | CI 파이프라인 완료 후, 새 컨테이너 이미지 태그가 쿠버네티스 배포 매니페스트(YAML 또는 `values.yaml`)에 반영되어 Git 저장소에 커밋/푸시됩니다. 이후 ArgoCD가 감지할 수 있도록 준비합니다. |

### 2. ArgoCD의 GitOps 배포 단계 (CD)

> **CD(Continuous Delivery)** 단계에서는 ArgoCD가 GitOps 방식을 통해 Git 저장소를 모니터링하고, 배포 매니페스트 기준으로 클러스터를 자동으로 동기화합니다.

| 순서 | 동작 | 설명 |
| --- | --- | --- |
| **1** | **ArgoCD가 Git 리포지토리 모니터링** | ArgoCD는 Git 저장소를 주기적으로 모니터링하여 쿠버네티스 배포 매니페스트(YAML 파일)의 변경 사항을 감지하고, 변경된 구성과 현재 클러스터 상태를 비교합니다. |
| **2** | **동기화(Synchronization) 수행** | Git에 선언된 이상적인 상태와 현재 클러스터 상태를 비교하여 불일치가 발생하면 자동으로 쿠버네티스 리소스를 업데이트합니다. (Helm, Kustomize 등 사용 가능) |
| **3** | **상태 모니터링 및 롤백 가능** | ArgoCD 대시보드 또는 CLI를 통해 배포 상태를 실시간으로 추적하고, 문제 발생 시 이전의 안정적인 상태로 손쉽게 롤백할 수 있습니다. |

---

### 3. 운영 및 모니터링 단계

> 배포 완료 후 운영 환경에서 애플리케이션이 안정적으로 실행되는지 지속 검사하며, Prometheus/Grafana 등과 연동해 실시간 시각화 및 자동 복구를 제공합니다.

| 순서 | 동작 | 설명 |
| --- | --- | --- |
| **1** | **애플리케이션 상태 시각화** | ArgoCD UI를 통해 Kubernetes 리소스의 배포 상태, 의존성 관계, 동기화 여부를 한눈에 시각적으로 확인합니다. |
| **2** | **실시간 동기화 및 자동 복구** | 클러스터 리소스를 지속 검사하여 Git 저장소의 선언적 구성과 불일치(Drift)가 발생하면 자동으로 동기화(Auto-sync)하고 일관성을 유지하며, 필요 시 알림 및 자동 롤백을 수행합니다. |

### 1. 기존 배포 방식의 한계 및 문제점

* **명령어 및 배포 순서의 파편화**: 담당자에 따라 `kubectl` 명령어나 디테일이 달라져 배포 일관성이 깨짐
* **클러스터 상태 파악 및 이력 추적 난항**: 클러스터 내 변경 이력을 알기 어렵고, 이전 설정으로 복구하기가 까다로움
* **CI 서버의 과도한 권한 보유 (보안 위험)**: GitHub Actions/Jenkins 등에 `kubectl` 접근 권한을 직접 부여해야 하므로, CI 계정이 탈루될 경우 클러스터 전체가 위험해짐
* **상태 불일치 (State Drift)**: Git 저장소의 배포 매니페스트와 실제 클러스터 리소스 상태가 서로 달라지는 문제 발생

---

### 2. GitOps 및 Pull 방식 배포 메커니즘

* **GitOps 원칙**: Git 저장소에 선언된 매니페스트(YAML, Helm, Kustomize)를 단일 진실 공급원(Single Source of Truth)으로 지정하고 운영 환경을 제어
* **Push 방식 (기존 CI/CD)**: CI 서버가 클러스터 외부에 존재하며 직접 `kubectl apply`를 실행해 배포를 밀어 넣는 방식 (과도한 권한 필요)
* **Pull 방식 (ArgoCD)**:
* CI 서버는 컨테이너 이미지 빌드 및 Git 저장소의 태그 수정까지만 담당
* 클러스터 내부의 ArgoCD Pod가 Git 저장소를 주기적으로 Polling(감시)하여 변경 사항을 감지하고 스스로 반영

### 3. ArgoCD 주요 기능 및 상태 값 (Status)

#### ① ArgoCD 핵심 제어 기능

| 기능 | 설명 |
| --- | --- |
| **Self-Healing (자동 복구)** | 누군가가 `kubectl`로 클러스터 리소스를 임의 변경하더라도, Git의 선언 상태를 기준으로 자동 원복함 |
| **Prune (리소스 삭제 동기화)** | Git 저장소에서 매니페스트 파일(예: `service.yaml`)이 삭제되면 클러스터 내 실제 리소스도 함께 삭제 |
| **Auto / Manual Sync** | 동기화 타이밍을 지정 (개발 환경은 `Auto-Sync`, 운영 환경은 `Manual Sync` + PR 승인 방식 적용) |

#### ② ArgoCD 상태 표기 (Status)

* **Sync Status (Git ↔ 클러스터 일치 여부)**:
* `Synced`: Git의 선언과 클러스터 상태가 완전히 일치함
* `OutOfSync`: Git과 클러스터 간 설정 차이가 존재함


* **Health Status (애플리케이션 동작 상태)**:
* `Healthy`: 리소스가 정상 실행 중임
* `Progressing`: 배포 또는 변경 작업이 진행 중임
* `Degraded`: 일부 리소스(Pod 등)가 에러로 인해 비정상 상태임
* `Missing`: Git에는 정의되어 있으나 클러스터에는 리소스가 존재하지 않음

### 4. 기존 CI 배포 vs ArgoCD 비교

| 구분 | **기존 CI 직접 배포** | **ArgoCD (GitOps)** |
| --- | --- | --- |
| **배포 주체** | CI 서버 (GitHub Actions, Jenkins 등) | 클러스터 내부의 ArgoCD Pod |
| **배포 방식** | **Push 방식** (`kubectl apply`) | **Pull 방식** (Git 저장소 주기적 Polling) |
| **클러스터 권한** | CI 서버가 클러스터 관리자 권한 소유 | ArgoCD만 내부 권한 소유 (CI 서버 권한 최소화) |
| **자동 복구** | 제공하지 않음 (수동 조치 필요) | **Self-Healing**으로 Git 상태 자동 복구 |
| **불필요 리소스 정리** | 별도 스크립트 작성 필요 | **Prune** 기능으로 자동 삭제 |

### 5. 실무 적용 시 주의 사항

1. **클러스터 직접 수정 금지**: `kubectl scale` 등으로 클러스터를 직접 수정하면 ArgoCD가 이를 'Drift'로 인지하고 Git 상태로 원복시키므로, 반드시 Git 커밋을 통해 수정해야 합니다.
2. **`latest` 태그 사용 지양**: 이미지 태그가 `:latest`로 고정되어 있으면 Git의 문자열 변경이 없어 ArgoCD가 배포 변경 사항을 감지하지 못합니다. (반드시 고유 커밋 SHA 또는 버전 태그 사용)
3. **운영(Prod) 환경 수동 승인 적용**: 운영 환경은 `automated.prune` / `selfHeal` 사용에 주의하고, PR 승인 후 운영자가 UI에서 직접 Sync 버튼을 누르는 수동 방식을 권장합니다.



#### 주제 2: PLG Stack
## PLG Stack
- PLG Stack: Prometheus로 메트릭을 저장하고, Loki로 로그를 저장하며, Grafana에서 두 데이터를 함께 조회·시각화하는 오픈소스 관측성 구성입니다.
- **P — Prometheus:** 시스템의 수치 데이터를 수집하고 저장
- **L — Loki:** 애플리케이션과 시스템의 로그를 수집하고 저장
- **G — Grafana:** Prometheus와 Loki의 데이터를 조회하고 시각화

---

### 1. 모니터링 vs 관측성 (Observability)

> **관측성(Observability)**
> 시스템 외부로 출력되는 데이터(Metrics, Logs, Traces)를 통해 **시스템 내부에서 무슨 일이 일어났는지 추론하고 장애의 근본 원인을 파악할 수 있는 능력**입니다.

| 구분 | **모니터링 (Monitoring)** | **관측성 (Observability)** |
| --- | --- | --- |
| **목적** | 시스템의 **현재 상태 및 문제 발생 여부** 확인 | 시스템 내부 **상태 추론 및 장애 원인 분석** |
| **질문 예시** | *"CPU 사용률이 높아졌는가?"*, *"Pod가 재시작되었는가?"* | *"왜 14시에 특정 API 요청이 느려졌는가?"* |
| **한계** | 복잡한 쿠버네티스 환경에서는 수치만으로 원인 파악 불가 | 시스템의 명확한 출력이 전제되어야 내부 추론 가능 |

#### 관측성의 3대 데이터 요소 (M.L.T)

| 데이터 종류 | 의미 | 주요 예시 |
| --- | --- | --- |
| **Metrics** | 시간에 따라 측정되는 숫자 데이터 | CPU 사용률, HTTP 요청 수, 평균 응답 시간 |
| **Logs** | 시스템에서 발생한 개별 사건/이벤트 기록 | 애플리케이션 에러 로그, 요청 처리 내역 |
| **Traces** | 단일 요청이 여러 Microservice를 거치는 전체 경로 | API ➔ WAS ➔ Redis ➔ DB 처리 경로 |

---

### 2. PLG Stack (Prometheus + Loki + Grafana) 개념 및 도입 이유

> **PLG Stack**: 쿠버네티스 환경의 관측성을 확보하기 위해 **Prometheus(Metrics)**, **Loki(Logs)**, **Grafana(Visualization)**를 조합한 중앙 집중형 관측 플랫폼입니다. *(단 순수 PLG 기본 구성에는 Tracing은 포함되지 않음)*

#### 💡 대규모 Kubernetes 환경에서 PLG Stack이 필요한 이유

1. **상태 파악의 어려움 극복**: 백 단위의 노드와 파드에 관리자가 일일이 접속하여 `htop`, `kubectl logs` 명령어로 모니터링하는 한계를 해결
2. **Pod 휘발성 문제 해결**: Pod는 장애/recreate 시 내부 컨테이너 로그와 임시 데이터가 삭제되므로, 사후 장애 분석을 위해 **중앙 집중식 데이터 수집 및 저장**이 필수적임
3. **분산 환경의 장애 추적**: 여러 노드에 퍼져 있는 메트릭과 로그를 중앙으로 수집하고 Grafana 단일 대시보드로 시각화하여 장애 원인 분석 시간 단축

### 3. Exporter 및 메트릭 데이터 구조

#### ① Exporter란?

Prometheus용 메트릭 포맷을 기본 제공하지 않는 대상(노드 OS, DB 등)의 상태를 읽어 **Prometheus가 수집(Pull)할 수 있는 텍스트 메트릭 형태로 변환/노출해 주는 프로그램**입니다.

#### ② 주요 Exporter 종류

| Exporter | 수집 대상 및 주요 메트릭 |
| --- | --- |
| **Node Exporter** | OS 수준의 CPU, 메모리, 디스크, 파일 시스템, 네트워크 메트릭 |
| **MySQL Exporter** | MySQL DB 커넥션 수, 쿼리 처리량, 복제 상태 메트릭 |
| **Redis Exporter** | Redis 메모리 사용량, 명령 처리량, 클라이언트 연결 상태 |
| **NGINX Exporter** | NGINX 활성 연결 수 및 HTTP 요청 처리 상태 |

#### ③ Prometheus 메트릭 데이터 구조 (시계열 데이터)

```text
http_requests_total{method="GET", status="200", pod="backend-7c8d9f"} 1250
└───────┬─────────┘ └───────────────────────┬──────────────────────┘ ───┬──
    Metric Name                        Labels                          Value

```

* **시계열(Time-series) 데이터**: 단순 숫자가 아니라 "특정 시점(Timestamp)의 수치"를 누적하여 기록함

---

### 4. Kubernetes 환경의 주요 메트릭 및 PromQL

#### ① 자주 활용하는 k8s 메트릭 분류

* **Node Exporter 메트릭**: 노드 물리 자원 사용량 (CPU, Memory, Disk I/O 등)
* **kube-state-metrics**: 쿠버네티스 API 상태 변환 데이터 (Desired/Current Replicas 수, Pod Phase, Pod 재시작 횟수, PVC/Node 상태 등)
* **애플리케이션 메트릭**: 비즈니스 및 성능 지표 (Spring/Node.js 등의 HTTP 요청 수, DB Connection Pool 사용량, 주문 처리 수 등)

#### ② PromQL (Prometheus Query Language)

Prometheus에 시계열로 저장된 메트릭 데이터를 조회·집계·계산하기 위해 사용하는 전용 쿼리 언어입니다.

```promql
# 최근 5분간의 HTTP 요청 증가율(초당) 계산
rate(http_requests_total[5m])

# 최근 5분간의 컨테이너 CPU 사용량 계산
rate(container_cpu_usage_seconds_total[5m])

```

## Prometheus
- Prometheus: 모니터링 및 알림을 위한 오픈소스 시스템 
### Prometheus 주요 특징

| 특징 | 설명 |
| --- | --- |
| **Kubernetes 네이티브 통합** | Prometheus는 Kubernetes의 서비스 디스커버리 기능을 활용하여 동적으로 Pod, Node, 서비스 등에서 메트릭을 수집합니다. |
| **Pull 방식 데이터 수집** | Prometheus는 대상(target)에서 데이터를 Pull 방식으로 주기적으로 가져오며, 타겟 가용성과 안정성을 보장합니다. *(단, Pushgateway나 Remote Write Receiver를 통해 Push 방식을 지원하기도 하지만 기본 수집 모델은 아닙니다.)* |
| **시계열 데이터 처리** | 메트릭 데이터를 시계열(time-series)로 저장하며, 시간에 따른 클러스터 상태와 성능 변화를 추적하고 분석할 수 있습니다. |
| **Alertmanager 연동** | Alertmanager와 연동되어 CPU 과부하, 메모리 부족 등 클러스터 상태에 따라 경고를 생성하고 알림을 전송할 수 있습니다. |
| **확장성 및 유연성** | Exporter, Operator, kube-state-metrics 등과 통합하여 다양한 메트릭 데이터를 수집하고 Kubernetes 환경에 맞게 확장 가능합니다. |
| **경량화 및 독립적 실행** | Prometheus는 외부 DB나 추가 컴포넌트 없이 단일 바이너리로 실행 가능한 경량화 구조를 가집니다. Kubernetes 환경에서는 StatefulSet 또는 Operator 기반으로 손쉽게 운영할 수 있습니다. |

### ⚙️ Kubernetes에서 Prometheus 동작 방식
#### 1. 단계별 동작 내용

| 순서 | 동작 | 내용 |
| --- | --- | --- |
| **1** | **데이터 수집** *(데이터 노출 및 수집)* | 각 노드의 메트릭은 Node Exporter가 노출하고, Kubernetes 상태 메트릭은 kube-state-metrics가 노출합니다. Prometheus(Server)는 이 엔드포인트들을 Pull 방식으로 주기적으로 수집합니다. |
| **2** | **구성 및 관리** | Prometheus Operator는 Prometheus, Alertmanager, kube-state-metrics 등을 Kubernetes-native 방식으로 배포 및 관리합니다. 또한 ServiceMonitor, PodMonitor 같은 CRD로 Prometheus의 스크랩 대상과 설정을 자동화합니다. |
| **3** | **데이터 활용** | Prometheus 내부 Alert 규칙에 따라 Alertmanager가 동작하고, 지정된 채널로 알림을 전송합니다. |

### 💡 [참고] CRD(Custom Resource Definition)란?

CRD(Custom Resource Definition)는 Kubernetes에 새로운 리소스 유형을 추가하기 위한 확장 기능입니다.

* **기본 리소스의 한계**: 기본적으로 Kubernetes는 `Pod`, `Deployment`, `Service` 같은 표준 리소스만 제공합니다. 하지만 운영 환경에서는 서비스마다 특화된 리소스가 추가로 필요할 수 있습니다.
* **사용자 정의 확장**: CRD를 사용하면 사용자가 직접 새로운 리소스(예: `MySQLCluster`, `ServiceMonitor`)를 정의하여 Kubernetes 클러스터에 등록할 수 있습니다.
* **표준 명령어 지원**: 이렇게 등록된 리소스는 기존 리소스처럼 `kubectl apply`, `kubectl get` 등의 명령어를 사용해 동일하고 일관성 있게 관리할 수 있습니다.

## Loki
- Loki: Grafana Labs에서 개발한 오픈소스 로그 집계 시스템
#### Loki 사용 이유

| 이유 | 설명 |
| --- | --- |
| **경제적인 로그 수집 및 저장** | Loki는 로그 전체를 인덱싱하지 않고 메타데이터(Label)만 인덱싱하므로, 데이터베이스 저장소 비용을 획기적으로 절감하면서도 대규모 로그를 효율적으로 처리합니다. |
| **메트릭과 로그의 통합 분석** | Prometheus와 동일한 라벨링 구조를 공유하므로, 메트릭 데이터 그래프에서 클릭 한 번으로 특정 시점의 로그를 쉽게 연계 분석할 수 있습니다. |
| **빠르고 유연한 검색 기능** | 전용 쿼리 언어인 LogQL(Log Query Language)을 사용하여 다양한 필터 조건에 맞춰 필요한 로그를 정밀하게 추출하고 분석할 수 있습니다. |
| **실시간 문제 진단** | Grafana와 완벽하게 통합되어 실시간 로그 분석 대시보드를 구축할 수 있으며, 장애 및 이상 징후 발생 시 즉각적으로 원인을 시각화하여 파악할 수 있습니다. |

#### Loki 주요 특징

| 특징 | 설명 |
| --- | --- |
| **시계열 메타데이터 기반의 로그 처리** | Loki는 로그 본문 전체를 직접 인덱싱하지 않고 `namespace`, `pod`, `container`, `application` 같은 메타데이터(Label)만을 인덱싱합니다. 실제 로그 본문은 압축된 시계열 블록 형태로 저장하여 필요 시 Label을 기준으로 신속하게 검색합니다. |
| **Prometheus와의 긴밀한 통합** | Loki는 Prometheus의 메트릭 데이터와 라벨 구조가 동일하여 로그와 메트릭을 상호 연계 분석할 수 있습니다. 이를 통해 특정 Pod의 CPU 사용량이 급증한 시점의 로그를 즉시 추적하고 문제 원인을 파악할 수 있습니다. |
| **구조화되지 않은 로그 지원** | Loki는 애플리케이션에서 생성된 비구조화(Unstructured) 로그를 별도의 파싱 스키마 정의 없이 수집하며, 검색 시점에 로그 내용과 메타데이터를 조합하여 자유롭게 분석할 수 있습니다. |
| **Grafana와의 연동** | Loki는 Grafana의 기본 로그 데이터 소스로 연결되어 로그 검색 및 시각화를 지원하며, 단일 대시보드 내에서 메트릭과 로그를 통합 모니터링할 수 있게 해줍니다. |

#### Loki 주요 구성 요소

| 구성 요소 | 설명 |
| --- | --- |
| **Distributor** | 클라이언트(Promtail 등)로부터 수신된 로그를 검증하고, 데이터가 균등하게 처리되도록 Ingester에 분산 전달합니다. |
| **Ingester** | 전달받은 로그 데이터를 수신하여 메모리에 임시 저장하며, 일정 크기나 시간이 도달하면 데이터를 청크(Chunk) 단위로 분리하여 장기 저장소에 기록합니다. |
| **Querier** | 사용자의 LogQL 쿼리 요청을 처리하며, Ingester의 메모리 데이터 및 저장소의 블록 데이터를 함께 검색하여 결과를 반환합니다. Grafana 연동 시 주된 조회 엔진 역할을 합니다. |
| **Promtail** | Loki의 전용 로그 수집 에이전트(DaemonSet)로, Node 내 컨테이너 및 시스템 로그를 수집하고 쿠버네티스 API를 통해 `namespace`, `pod`, `container` 등의 메타데이터(Label)를 부착하여 Loki로 전송합니다. |

#### Loki 동작 방식

| 순서 | 동작 | 내용 |
| --- | --- | --- |
| **1** | **로그 수집** | Promtail이 쿠버네티스 환경 내 컨테이너와 Pod의 로그를 수집하고, `namespace`, `pod`, `container` 등의 메타데이터(Label)를 부착하여 Loki로 전송합니다. |
| **2** | **데이터 저장** | Distributor가 수신한 로그를 검증 후 Ingester로 전달하면, Ingester가 메모리에 임시 저장한 뒤 청크(Chunk) 단위로 분리하여 객체 저장소에 영구 기록합니다. |
| **3** | **데이터 조회 및 검색** | Grafana에 Loki를 데이터 소스로 연결한 뒤, LogQL 쿼리를 사용하여 특정 Pod, 컨테이너, 이벤트 조건에 맞춰 로그를 정밀하게 필터링 및 검색합니다. |
| **4** | **데이터 시각화** | Grafana 대시보드를 통해 수집된 로그를 실시간으로 시각화하며, Prometheus 메트릭과 연계하여 시점별 통합 분석을 수행합니다. |


작성하신 노트를 검토해보니 **PLG Stack의 주요 개념, 각 컴포넌트(Prometheus, Grafana, Loki)의 특징 및 동작 방식, 모니터링 vs 관측성 비교**가 매우 체계적이고 깔끔하게 정리되어 있습니다.

다만, 원문 자료에 포함되어 있던 **Loki의 핵심 저장 원리(Index vs Chunk, 인덱싱하지 않는 이유, 레이블 모범 사례/안티패턴)** 및 **Grafana의 모범 역할(쿼리 수집기 개념)** 내용이 일부 빠져 있어, 이 부분을 정리해 추가하면 완벽한 기술 노드가 됩니다.

기존 노트의 **Loki 섹션 하단**과 전체 문서 **마지막**에 바로 연결해 붙이실 수 있도록 정돈한 마크다운 문서입니다.

---

### 1. Loki의 저장 구조 및 레이블 설계 전략

#### ① Index vs Chunk 저장 구조

Loki는 인덱스 크기를 최소화하기 위해 메타데이터와 로그 본문을 분리하여 관리합니다.

* **Index (위치 정보)**: `cluster`, `namespace`, `app` 등 낮은 카디널리티(Low Cardinality)를 갖는 레이블 조합과 해당 로그 Chunk의 저장 위치만 기록합니다.
* **Chunk (실체 로그 데이터)**: 압축된 실제 로그 메시지 텍스트와 타임스탬프의 집합체입니다.

```text
[Index]
└─ cluster=prod-k8s, namespace=production, app=order-api
   └─ Chunk A의 위치 참조

[Chunk A]
├─ 14:00:01 INFO  주문 조회 성공
├─ 14:00:02 ERROR DB 연결 실패
└─ 14:00:03 INFO  DB 연결 재시도

```

---

#### ② 로그 본문을 인덱싱하지 않는 이유 (Full-text Indexing 지양)

* **비용 절감**: 전체 로그 문장을 쪼개서(Tokenizing) 역인덱스(Reversed Index)로 구성하는 방식(Elasticsearch 등)은 수 TB 단위의 로그 환경에서 인덱스 DB 비용을 기하급수적으로 증가시킵니다.
* **압축률 극대화**: Loki는 레이블로 1차 검색 범위를 대폭 줄인 뒤, 좁혀진 Chunk 내부의 압축 텍스트를 고속으로 스캔 및 필터링합니다. 이로 인해 높은 압축률과 저장 공간 절약 효과를 얻습니다.

---

#### ③ Loki 레이블 설정 모범 사례 (High Cardinality 주의)

레이블을 잘못 설정하면 인덱스가 폭발적으로 커지고(High Cardinality) 검색 성능이 급격히 저하됩니다.

| 구분 | **좋은 레이블 (Good Labels)** | **피해야 할 레이블 (Anti-Patterns)** |
| --- | --- | --- |
| **특성** | 값의 종류가 적고 오래 유지되는 값 (Low Cardinality) | 요청마다 새로 생성되는 고유값 (High Cardinality) |
| **예시** | `environment` (`prod`, `dev`), `namespace`, `app`, `job` | `request_id`, `trace_id`, `user_id`, `client_ip`, `timestamp` |
| **처리 방식** | **Loki Label**로 등록해 1차 범위 지정에 활용 | **LogQL의 텍스트 필터링** 단계에서 검사 |

---

### 2. Grafana의 핵심 역할 재정의

* **Non-Storage / Query-Driven Architecture**: Grafana는 자체적으로 메트릭이나 로그 데이터를 **저장(Storage)하지 않습니다.**
* **중앙 집중식 시각화**: Prometheus, Loki, MySQL 등 다양한 외부 데이터 소스에 **쿼리를 날려 수집된 결과를 단일 UI 화면에 매핑/시각화**해 주는 대시보드 역할에 집중합니다.

---

### 3. PLG Stack 전체 데이터 흐름 요약

```text
[ Metrics Stream ]
Node / Pod ➔ Exporter / kube-state-metrics ➔ Prometheus (Pull & Storage) ──┐
                                                                            ├──➔ Grafana (Query & Visual)
[ Logs Stream ]                                                             │
Container Log ➔ Promtail (Labeling & Push) ➔ Loki (Chunk Storage) ──────────┘

```

1. **Metrics**: Exporter가 메트릭 노출 ➔ Prometheus가 Pull 수집 및 시계열 저장
2. **Logs**: Promtail이 컨테이너 로그 수집 및 K8s 레이블 부착 ➔ Loki가 Distributor/Ingester를 거쳐 Chunk 단위로 저장
3. **Visualization**: Grafana가 PromQL/LogQL을 통해 두 데이터 소스를 동시에 조회하여 단일 대시보드에 시각화



### 오늘의 회고
- Prometheus, Grafana, Loki (PLG Stack)의 동작 방식과 관측성(Observability)의 중요성을 이해했다.
    - 특히 Loki가 전체 로그 본문 대신 '라벨(Label)'만 인덱싱하여 저장 효율을 극대화하는 저장 구조(Index vs Chunk) 메커니즘이 인상 깊었다.
- ArgoCD가 Git Repository를 지속적으로 모니터링(Polling)하며 클러스터 상태를 동기화하는 GitOps 배포 원리를 파악했다.
    - 기존 CI/CD의 Push 방식(CI 서버에 과도한 kubectl 권한 부여) 대신, 클러스터 내부에서 Pull 방식으로 Git의 목표 상태(Desired State)와 실시간 클러스터 상태(Live State)를 일치시키는 구조의 안정성을 배웠다.
    - Self-Healing 기능을 통해 수동 변경(Drift)이 발생해도 Single Source of Truth인 Git 상태로 자동 복구되는 메커니즘이 신기하다.
