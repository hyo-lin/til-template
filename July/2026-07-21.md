#### 주제 1: Controller
### 💡 Controller 개념
* **Controller**: 클러스터의 현재 상태를 지속적으로 모니터링하고, 사용자가 정의한 목표 상태와 일치하도록 조치를 취하는 자동화된 관리 루프 (Control Loop / Reconciliation)

---

### ❓ Controller 사용 이유
| 이유 | 설명 |
| :--- | :--- |
| **안정적인 운영 환경 유지** | 컨트롤러는 클러스터 내 리소스의 상태를 지속적으로 감시하고, 목표 상태에 맞지 않으면 자동으로 수정 조치를 취합니다.<br> - *예시*: Pod가 예기치 않게 종료되거나 손실되었을 때, 컨트롤러는 이를 자동으로 복원하여 사용자가 설정한 상태를 유지합니다. |
| **운영 효율성 증대** | 컨트롤러는 수동으로 개입하지 않아도 클러스터의 상태를 자동으로 관리하므로, 운영자가 개별 리소스나 애플리케이션 상태를 지속적으로 확인하고 수정할 필요가 없습니다.<br> - *예시*: Deployment 컨트롤러는 운영자가 배포나 스케일링을 지시하면, 해당 작업을 자동으로 수행해 일관된 방식으로 적용하고 수동 개입을 최소화합니다. |
| **자동화된 복구 (Self-Healing)** | 컨트롤러는 클러스터에서 발생하는 문제를 자동으로 감지하고 복구합니다. 시스템의 가용성을 유지하고, 장애 발생 시 자동으로 복구 조치를 취하여 서비스 중단을 최소화할 수 있습니다.<br> - *예시*: StatefulSet 컨트롤러는 각 Pod가 고유한 정체성을 유지하면서도 자동으로 복구될 수 있도록 보장합니다. |
| **확장성과 유연성 제공** | 컨트롤러는 리소스의 수를 자동으로 조정하여 클러스터의 부하와 사용량에 맞게 동적으로 확장할 수 있습니다.<br> - *예시*: ReplicaSet 컨트롤러는 지정된 수의 Pod가 항상 실행되도록 보장하며, 필요에 따라 자동으로 Pod의 수를 조절합니다. |
| **정책 기반 관리** | 컨트롤러는 클러스터 내 리소스에 대해 정책 기반의 관리를 가능하게 합니다. 사용자는 목표 상태를 설정하면, 컨트롤러가 이를 자동으로 적용하고 유지합니다.<br> - *예시*: Job 컨트롤러는 일회성 작업이나 배치 작업을 관리하고, 작업이 완료될 때까지 자동으로 모니터링하며 재시작 정책을 적용합니다. |
### 🔄 핵심 원리: Desired State vs Current State

* **Desired State (원하는 상태)**: 운영자가 YAML의 `spec.replicas` 등에 정의한 클러스터의 최종 목표 상태
* **Current State (현재 상태)**: 클러스터 내에 실제로 작동 중인 리소스의 상태

---

### ⚔️ Pod 직접 생성 vs Controller 관리 비교

| 구분 | Pod 직접 생성 | Controller로 Pod 관리 |
| :--- | :--- | :--- |
| **생성 방식** | 사용자가 `kubectl run/apply`로 직접 생성 | Controller가 Pod Template을 바탕으로 생성 |
| **Pod 삭제/장애 시** | 삭제된 상태로 방치 (유실) | 설정된 수치만큼 **새로운 Pod 자동 생성** |
| **복제본/수량 유지** | 지원하지 않음 | 지정한 수량(`replicas`) 지속적 유지 |
| **스케일링 (확장/축소)** | 수동으로 Pod 추가/삭제 | YAML의 `replicas` 값만 변경하면 자동 조정 |
| **운영 적합성** | 일회성 테스트 및 단기 학습용 | **실제 운영 환경**의 애플리케이션 배포 |

### 📑 Controller YAML 구성 요소 및 역할

| 구성 요소 | 역할 | 비고 |
| :--- | :--- | :--- |
| **`replicas`** | 유지할 Pod의 목표 수량 정의 | 예: `replicas: 3` |
| **`selector`** | Controller가 관리할 Pod을 식별하는 검색 조건 | `matchLabels`로 대상 라벨 지정 |
| **`template`** | Pod이 부족할 때 새로 생성할 Pod의 설계도 | `template.metadata.labels`는 `selector`와 **반드시 일치**해야 함 |

### ⚙️ Controller와 API Server 간의 처리 흐름 (작업 주체 표)

| 단계 | 주체 | 수행 역할 |
| :---: | :--- | :--- |

| **2** | **API Server** | 저장소인 `etcd`에 목표 상태(Desired State) 기록 |
| **3** | **Controller** | `API Server`를 통해 현재 상태 감지 후, 차이 발생 시 **생성/삭제 요청** |
| **4** | **Scheduler** | `API Server`로부터 생성 요청을 받고, 배치할 최적의 워커 노드 지정 |
| **5** | **kubelet** | `API Server`의 명령을 받아 노드의 **Container Runtime**으로 컨테이너(Pod) 생성 |

### 📦 주요 Controller 종류

| Controller | 주요 목적 및 특징 |
| :--- | :--- |
| **ReplicaSet** | 지정된 개수의 동일한 Pod 복제본을 유지 |
| **Deployment** | ReplicaSet을 관리하며 무중단 배포, 롤아웃 업데이트, 롤백 지원 |
| **StatefulSet** | 고유한 식별자(이름) 및 영구 스토리지 보장이 필요한 상태 유효(Stateful) 앱 관리 |
| **DaemonSet** | 클러스터 내 모든(또는 특정) 노드마다 Pod을 하나씩 강제 실행 (예: 로그 수집기, 모니터링) |
| **Job / CronJob** | 일회성 작업 완료를 목적으로 실행하거나, 정해진 일정(크론식)에 따라 주기적으로 실행 |

#### 주제 2: ReplicaSet
### 💡 ReplicaSet 개념
* **ReplicaSet**: 특정 수의 Pod 복제본을 항상 유지하는 데 사용되는 컨트롤러

---

### ❓ ReplicaSet 사용 이유

| 이유 | 설명 |
| :--- | :--- |
| **Pod 복제본 유지** | 설정된 복제본 수를 항상 일정하게 유지하며, Pod 수가 부족할 경우 자동으로 새로운 Pod을 생성하고, 초과된 경우에는 삭제하여 균형을 유지합니다. |
| **자동 복구** | Pod이 중단되거나 삭제되더라도 ReplicaSet이 이를 감지하고, 템플릿을 기반으로 새로운 Pod을 생성하여 애플리케이션의 중단 없는 동작을 보장합니다. |
| **확장 및 축소 지원** | 부하가 증가하면 Pod 수를 확장하여 더 많은 요청을 처리할 수 있으며, 부하가 감소하면 Pod 수를 줄여 리소스를 절약합니다. |
| **라벨 기반 관리** | 라벨 셀렉터를 사용하여 특정 라벨 조건에 맞는 Pod만 선택적으로 관리할 수 있으며, `matchExpressions`를 통해 보다 세밀한 조건으로 Pod을 필터링할 수 있습니다. |
| **애플리케이션 가용성 보장** | 장애 발생 시에도 복제본을 유지하여 애플리케이션의 연속성을 보장하고, 서비스 품질 저하를 방지합니다. |

#### 🌐 Stateless Application

| 구분 | 내용 |
| --- | --- |
| **적합성** |  ReplicaSet의 주요 사용 목적 |
| **특징** | - Pod의 고유한 이름이나 IP, 상태 정보가 보존될 필요가 없음<br>- 트래픽 증가 시 동일한 Pod를 빠르게 수평 확장(Scale-out)하기에 최적화<br>- Pod 장애 발생 시 즉시 새 Pod로 자동 교체(Self-Healing)되어 서비스 중단 방지 |
| **대표 예시** | Web Server (Nginx, Apache), API Server, Frontend WAS 등 |

---

#### 🗄️ Stateful Application

| 구분 | 내용 |
| --- | --- |
| **적합성** | ReplicaSet 대신 **StatefulSet** 사용 권장 |
| **특징** | - Pod마다 고유한 순서(index), 고유 네트워크 식별자, 전용 볼륨(Persistent Volume)이 필요함<br>- ReplicaSet은 Pod를 무작위 생성/삭제하므로 데이터 손실 및 순서 꼬임 위험 발생<br>- Pod가 재생성되어도 기존 데이터와 정체성이 유지되어야 하므로 ReplicaSet 구조와 맞지 않음 |
| **대표 예시** | Database (MySQL, MongoDB, PostgreSQL), Distributed Cache (Redis Cluster) 등 |

### 🧩 ReplicaSet 구성 요소

| 구성 요소 | 설명 |
| :--- | :--- |
| **Replicas** | Pod 복제본 수를 정의하며, 해당 수의 Pod이 항상 실행되도록 보장합니다.<br>예: `replicas: 3`으로 설정 시 Pod 3개가 생성 및 유지됩니다. |
| **Selector** | 관리 대상 Pod을 지정하기 위해 라벨 셀렉터를 사용합니다.<br>`matchLabels`와 `matchExpressions`로 조건을 세밀하게 설정 가능합니다. |
| **Pod Template** | Pod 생성 시 사용할 템플릿을 정의합니다.<br>Pod의 메타데이터와 사양(`spec`)을 포함하며, 템플릿 변경 시 새로운 Pod 생성에 반영됩니다. |

### ⚙️ ReplicaSet 주요 역할

ReplicaSet은 클러스터 내 애플리케이션의 안정적 운영을 위해 다양한 역할을 수행합니다.

| 주요 역할 | 설명 |
| :--- | :--- |
| **Pod 복제본 유지** | 설정된 복제본 수(`replicas`)에 따라 Pod 수를 항상 일정하게 유지하며, 부족 시 새로운 Pod을 생성하고 초과 시 초과된 Pod을 제거합니다. |
| **자동 복구** | Pod이 중단되거나 삭제될 경우, ReplicaSet은 이를 감지하고 템플릿을 기반으로 새로운 Pod을 자동으로 생성하여 복구합니다. |
| **안정성 보장** | Pod 복제본 관리와 자동 복구를 통해 애플리케이션의 안정적 동작과 서비스 가용성을 보장합니다. |
| **확장 및 축소** | 부하에 따라 복제본 수를 동적으로 조정하여, 필요 시 애플리케이션의 처리 능력을 확장하거나 축소합니다. |

### 🔄 ReplicaSet 동작 순서

| 순서 | 동작 방식 |
| :---: | :--- |
| **1** | 사용자가 ReplicaSet의 설정(`spec`)을 정의하며, 이 설정에는 복제본 수(`replicas`), 라벨 셀렉터(`selector`), Pod 템플릿(`template`) 등이 포함됩니다. |
| **2** | ReplicaSet은 클러스터 내 Pod의 상태를 지속적으로 확인하여, 설정된 복제본 수와 일치하지 않는 경우 자동으로 Pod을 추가하거나 삭제합니다. |
| **3** | 새로운 Pod이 필요할 경우, 정의된 템플릿을 사용하여 동일한 구성의 Pod을 생성합니다. |

### 🧩 ReplicaSet 구성 요소 및 YAML 구조

```aiignore
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-replicaset
spec:
  replicas: 3               # 1) 유지할 Pod 복제본 수
  selector:
    matchLabels:
      app: web              # 2) 관리 대상 Pod을 찾는 라벨 조건 (Selector)
  template:                 # 3) Pod 부족 시 새로 생성할 Pod의 설계도 (Template)
    metadata:
      labels:
        app: web            # ⚠️ selector.matchLabels와 반드시 일치해야 함
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```

### ⚠️ Label / Selector 사용 시 주의점 (기존 Pod 자동 편입 문제)

| 구분 | 내용 |
| :--- | :--- |
| **동작 원리** | ReplicaSet은 자신이 직접 생성한 Pod만 관리하는 것이 아니라, 오직 **라벨(`Label`)의 일치 여부만 보고 대상을 식별**합니다. |
| **발생 문제** | ReplicaSet을 생성하기 전에 이미 동일한 라벨(`app: web`)을 가진 독립된 Pod(`existing-pod`)가 존재한다면, ReplicaSet은 이를 **자신의 관리 대상으로 자동 편입**시킵니다. |
| **실무적 위험성** | - 목표가 `replicas: 3`일 때 기존 Pod 1개가 이미 존재하면, 새 Pod는 2개만 생성됩니다.<br>- **ReplicaSet을 삭제할 때 기존에 독립적으로 만들어 두었던 Pod까지 함께 삭제**됩니다. |

### 🛑 ReplicaSet의 한계와 Deployment의 필요성

ReplicaSet은 오직 '복제본 수 유지'에만 집중하기 때문에, 애플리케이션 버전을 업데이트할 때 명확한 한계가 존재합니다.

| 구분 | 상세 내용 |
| :--- | :--- |
| **이미지 버전 업데이트 불가** | `spec.template.spec.containers[0].image`를 `nginx:1.27` ➔ `nginx:1.28`로 변경해도 **기존에 실행 중이던 Pod들은 업데이트되지 않습니다.** |
| **한계 발생 이유** | 기존 Pod들이 이미 `replicas` 수량을 충족하고 있으므로, ReplicaSet은 새로운 Pod를 만들어 교체할 필요가 없다고 판단하기 때문입니다.<br>*(※ 기존 Pod가 수동으로 삭제되거나 장애로 죽어서 새로 생성될 때만 변경된 이미지 버전이 적용됨)* |
| **결과적 문제** | 점진적 교체(Rolling Update), 배포 진행 상태 확인, 롤백(Rollback), 배포 이력 관리 등을 ReplicaSet 단독으로는 수행할 수 없습니다. |

---

> **💡 해결책: Deployment 사용**
>
> 실무에서는 `ReplicaSet`을 직접 YAML로 작성하지 않습니다.  
> `Deployment`가 내부적으로 ReplicaSet을 생성하고 관리하면서, 상위 단계의 배포/업데이트/롤백 전략을 자동 제어합니다.

### 🤔 ReplicaSet에 대해 자주 헷갈리는 오개념 4가지

| 오개념 | 실제 동작 (팩트) |
| :--- | :--- |
| **1. ReplicaSet이 아픈 Pod를 수리한다?** | **NO.** 쿠버네티스는 Pod를 수리(Repair)하지 않고 **삭제 후 재선언(Re-create)**합니다.<br>*(Pod는 애완동물이 아닌 가축처럼 다루어집니다. 문제가 생기면 즉시 파기하고 템플릿으로 새로 만듭니다.)* |
| **2. 부족할 때만(생성만) 동작한다?** | **NO.** 원하는 수보다 **많으면 삭제**하여 줄입니다.<br>*(목표가 3개인데 현재 5개라면 2개를 즉시 삭제하여 3개로 맞춥니다.)* |
| **3. Probe와 Controller는 같은 역할이다?** | **NO.** 관리하는 레벨이 완전히 다릅니다.<br>- **Probe (Liveness/Readiness)**: **Container 레벨**의 복구 (컨테이너 재시작, IP/Pod 유지)<br>- **Controller (ReplicaSet)**: **Pod 레벨**의 복구 (Pod 삭제 후 새 Pod 생성, IP/Pod Name 변경됨) |
| **4. ReplicaSet이 트래픽을 분산한다?** | **NO.** ReplicaSet은 오직 Pod의 '개수'만 유지합니다.<br>*(트래픽을 L4/L7 수준으로 분산하고 Endpoints를 관리하는 것은 **Service**의 역할입니다.)* |

| **ReplicaSet이란?** | 지정된 수의 Pod 복제본을 항상 유지하는 Controller            |
| **원하는 Pod 수는 어디에 작성하는가?** | `spec.replicas`                               |
| **관리할 Pod은 어떻게 찾는가?** | `spec.selector`와 Pod의 `metadata.labels` 일치 여부 |
| **Pod이 부족하거나 많으면 어떻게 되는가?** | 부족하면 `spec.template`으로 새로 생성 / 많으면 초과분 삭제     |
| **삭제된 Pod 자체가 복구되는가?** | 아니요. 고쳐 쓰지 않고 새로운 Pod(새 IP, 새 이름)이 생성됨        |
| **트래픽을 직접 분산하는가?** | 아니요. 트래픽 전달 및 로드밸런싱은 **Service**의 역할          |
| **실무에서 직접 YAML로 만드는가?** | 아니요. 보통 **Deployment**를 통해 간접적으로 사용 및 제어함     |

#### 주제 3: Deployment
### 💡 Deployment 개념
* **Deployment**: 쿠버네티스에서 Pod와 ReplicaSet을 관리하며, 애플리케이션의 배포, 업데이트, 확장, 복구를 자동으로 수행하는 컨트롤러

---
### ❓ Deployment 사용 이유

| 이유 | 설명 |
| :--- | :--- |
| **Pod과 ReplicaSet의 관리 자동화** | Deployment는 Pod과 ReplicaSet의 생성, 삭제, 스케일링을 자동으로 처리합니다.<br>이를 통해 사용자는 개별 Pod를 직접 관리할 필요가 없으며, 클러스터의 상태를 정의하면 쿠버네티스가 이를 유지하도록 보장합니다. |
| **무중단 업데이트** | Deployment는 `RollingUpdate` 전략을 통해 서비스 중단 없이 애플리케이션 업데이트를 진행합니다.<br>새로운 Pod를 생성하면서 기존 Pod를 점진적으로 교체하므로, 사용자에게 안정적인 서비스를 지속적으로 제공할 수 있습니다. |
| **장애 복구 및 롤백** | Deployment는 장애 발생 시 롤백 기능을 통해 빠르게 이전 안정 상태로 복구할 수 있습니다.<br>새로운 애플리케이션 버전에서 오류가 발생해도 기존 버전의 ReplicaSet을 유지하므로, 신속하게 이전 버전으로 전환 가능합니다. |
| **목표 상태 선언 및 지속적 동기화** | Deployment는 사용자가 선언한 목표 상태(Desired State)를 자동으로 유지합니다.<br>쿠버네티스 컨트롤러는 현재 상태(Actual State)와 목표 상태를 지속적으로 비교하며, 필요한 작업(예: Pod 생성/삭제)을 통해 이를 동기화합니다. |

### 🚀 Deployment 주요 역할

| 역할 | 설명 |
| :--- | :--- |
| **Pod와 ReplicaSet 관리** | Deployment는 Pod를 직접적으로 관리하지 않고, ReplicaSet을 생성하여 Pod의 생성 및 삭제를 제어합니다.<br>새로운 배포 시 새로운 ReplicaSet을 생성하고, 기존 ReplicaSet을 유지하여 롤백 가능성을 확보합니다. |
| **점진적 업데이트 및 복구** | Deployment는 롤링 업데이트 방식을 통해 서비스 중단 없이 점진적으로 새로운 버전의 Pod를 배포합니다.<br>문제가 발생할 경우 이전 안정 상태로 신속히 롤백할 수 있습니다. |
| **상태의 선언과 동기화** | Deployment는 사용자가 선언한 애플리케이션의 목표 상태를 기반으로 현재 상태를 지속적으로 동기화합니다.<br>Pod의 생성, 삭제 등의 작업이 필요할 경우 이를 자동으로 수행합니다. |
| **고급 배포 전략 지원** | Deployment는 Recreate와 RollingUpdate 전략을 기본적으로 지원하기 때문에 애플리케이션 특성에 맞는 유연한 운영이 가능합니다.<br>Blue/Green이나 Canary와 같은 고급 배포 방식은 Service 또는 외부 배포 도구(예: Istio)와 함께 구성하여 구현할 수 있습니다. |


### Deployment - Recreate
### 🔄 Recreate 배포 전략

#### ⚙️ 동작 방식

| 순서 | 단계 | 설명 |
| :---: | :--- | :--- |
| **1** | **기존 Pod 유지** | 기존 애플리케이션 버전(v1)의 Pod이 실행 중이며, 서비스가 이를 통해 사용자 요청을 처리합니다. |
| **2** | **기존 Pod 삭제** | Deployment는 기존 Pod(v1)를 모두 삭제합니다.<br>**⚠️ 서비스가 임시로 중단(Downtime)되고 사용자 요청을 처리할 수 없습니다.** |
| **3** | **새로운 Pod 생성** | 모든 기존 Pod이 삭제된 상태에서 새로운 애플리케이션 버전(v2)의 Pod 생성을 시작합니다. |
| **4** | **새로운 Pod 안정화** | 새로운 Pod(v2)가 정상적으로 생성되고 안정화된 이후, 서비스가 다시 사용자 요청을 처리합니다. |

---

#### 💡 활용 사례

| 사례 | 설명 |
| :--- | :--- |
| **테스트 환경 배포** | 서비스 중단이 큰 문제가 되지 않는 테스트 또는 개발 환경에서 간편하게 배포를 진행할 때 사용합니다. |
| **데이터베이스와의 강한 의존성** | 스키마 변경 등으로 인해 이전 버전(v1)과 신규 버전(v2)의 Pod가 동시에 존재하면 안 되는 경우에 유용합니다. |
| **긴급 결함 제거** | 기존 버전의 Pod에 심각한 보안 결함이나 이슈가 있어 즉시 전면 제거가 필요한 경우에 적합합니다. |

---

### Deployment - RollingUpdate
### 🔄 RollingUpdate 배포 전략

#### ⚙️ 동작 방식

| 순서 | 단계 | 설명 |
| :---: | :--- | :--- |
| **1** | **새로운 Pod 생성** | Deployment는 새로운 애플리케이션 버전(v2)의 Pod를 하나 생성합니다. |
| **2** | **기존 Pod 제거** | 새로운 Pod(v2)가 정상 구동(Running 및 Ready)되어 안정적으로 실행되면 기존 버전(v1)의 Pod 하나를 제거합니다. |
| **3** | **반복** | 지정된 비율(`maxSurge`, `maxUnavailable`)에 맞춰 위 과정을 반복하며 모든 Pod을 순차적으로 교체합니다. |
| **4** | **완료** | 모든 기존 Pod(v1)가 제거되고 새로운 Pod(v2)만 남게 되어, **무중단(Zero-Downtime)으로 배포가 완료**됩니다. |

---

#### 💡 활용 사례

| 사례 | 설명                                                                  |
| :--- |:--------------------------------------------------------------------|
| **프로덕션 환경 배포** | 연중무휴 서비스와 같이 서비스 중단(Downtime)이 허용되지 않는 운영 환경에 필수적입니다.               |
| **점진적 업데이트 검증** | 가용성을 유지하면서 새 버전이 정상 동작하는지 트래픽을 조금씩 받아보며 안정적으로 배포할 수 있습니다.           |
| **대규모 배포 환경** | 수십~수백 개의 Pod를 동시에 교체할 때 리소스 과부하 없이 일정한 스케일 규칙에 따라 안정적인 업데이트가 가능합니다. |


### 🔄 배포 전략 비교: RollingUpdate vs Recreate

| 구분 | RollingUpdate | Recreate |
| :--- | :--- | :--- |
| **동작 방식** | 기존 Pod과 새 Pod을 하나씩/점진적으로 교체 | 기존 Pod을 모두 삭제 후 새 Pod 생성 |
| **서비스 중단 (Downtime)** | 없음 (무중단 배포) | 발생 함 (다운타임 존재) |
| **버전 공존 여부** | 배포 진행 중 v1과 v2가 동시 존재 | v1 완전히 종료 후 v2 실행 (공존 X) |
| **주요 사용 환경** | 프로덕션 운영 환경 | 개발/테스트 환경, DB 스키마 파괴적 변경 시, 라이브 게임 등 |

---

### 📐 RollingUpdate 세부 옵션 (`maxSurge` & `maxUnavailable`)

> 기본 `replicas: 3`, `maxSurge: 1`, `maxUnavailable: 1` 설정 기준

| 옵션 | 의미 | 계산 예시 (`replicas: 3`) |
| :--- | :--- | :--- |
| **`maxSurge`** | 업데이트 중 초과하여 추가 생성할 수 있는 최대 Pod 수 | `1` 설정 시 ➔ 배포 순간 최대 **4개**까지 Pod 허용 (`3 + 1`) |
| **`maxUnavailable`** | 업데이트 중 비활성화(사용 불가)를 허용하는 최대 Pod 수 | `1` 설정 시 ➔ 배포 진행 중 최소 **2개** 이상의 Pod는 항상 Ready 상태 유지 (`3 - 1`) |

---

### ⚠️ RollingUpdate가 '진정한 무중단'이 되기 위한 필수 조건

| 구분 | 설명 |
| :--- | :--- |
| **Readiness Probe 필수 설정** | Pod 컨테이너가 뜬 후(Running), Spring Boot 등 애플리케이션 프레임워크가 요청을 받을 준비가 완벽히 될 때까지 Traffic 인입을 차단해야 합니다. |
| **DB 스키마 하위 호환성 유지** | 배포 중간에는 v1과 v2 Pod가 동시 실행되므로, DB 컬럼 삭제/변경 시 두 버전 모두 처리 가능하도록 호환성을 확보해야 합니다. |
| **최소 버전(Minimum Version) 관리** | 앱 클라이언트(Mobile/Web)의 구버전 이용자를 위한 API 호환성 및 강제 업데이트 정책이 필요합니다. |

### 📊 Deployment 조회 상태 읽는 법 (`kubectl get deployment`)

| 항목 | 설명 |
| :--- | :--- |
| **`READY`** | 현재 준비 완료된 Pod 수 / 원하는 Pod 수 (예: `3/3`) |
| **`UP-TO-DATE`** | 최신 Pod Template 사양으로 업데이트가 완료된 Pod 수 |
| **`AVAILABLE`** | 사용자 요청을 즉시 처리할 수 있는 정상 상태의 Pod 수 |
| **`AGE`** | Deployment가 처음 생성된 후 경과된 시간 |

### 🛠️ 실무 배포 운영 Checklist & Best Practices

| 구분 | 설명 |
| :--- | :--- |
| **Stateless App은 무조건 Deployment 사용** | WAS, Web Server, Frontend, Auth API 등은 ReplicaSet을 직접 쓰지 않고 Deployment로 관리합니다. |
| **`latest` 태그 사용 금지** | `image: nginx:latest`로 지정 시 YAML 변경 사항이 감지되지 않아 새 ReplicaSet 생성이 누락될 수 있습니다. Semantic Versioning(`v1.0.3`)이나 SHA Digest를 명시하세요. |
| **기존 ReplicaSet 보존 및 롤백** | 업데이트가 끝난 구버전 ReplicaSet은 바로 삭제되지 않고 `replicas: 0` 상태로 남아서 배포 이력(Revision) 역할을 수행합니다. (`kubectl rollout undo`로 즉시 복원 가능) |
| **배포 상태 검증 자동화** | `kubectl apply` 후 반드시 `kubectl rollout status deployment/<app-name>`을 실행하여 실제 Pod들이 Probe 헬스체크를 통과하고 정상 배포되었는지 확인하세요. |

### 📝 핵심 Q&A 및 퀴즈 정답

| 질문 | 답변 요약 |
| :--- | :--- |
| **Deployment란?** | ReplicaSet을 거느리며 Pod 배포/업데이트/롤백을 자동화하는 상위 Controller |
| **Deployment가 직접 관리하는 대상은?** | ReplicaSet (Pod를 직접 관리하지 않음) |
| **새로운 ReplicaSet은 언제 만들어지는가?** | Pod Template (`spec.template`)의 내용이 변경될 때 |
| **`replicas` 숫자만 변경하면 새 RS가 생기는가?** | 아니요. 기존 RS의 복제본 수만 조절됨 |
| **이전 버전으로 되돌리려면?** | `kubectl rollout undo` 명령어로 이전 Revision RS를 다시 확장 |
