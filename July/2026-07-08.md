### 새로 배운 내용
#### 주제 1: ECR
- ECR: AWS에서 제공하는 컨테이너 이미지 저장소 서비스로, 사용자가 직접 서버를 구축하거나 운영하지 않아도 이미지 저장, 버전 관리, 접근 제어, 보안 스캔까지 자동으로 처리되는 완전 관리형(fully managed) 레지스트리
  - 컨테이너 이미지를 AWS 환경 안에서 안전하게 저장하고, ECS, EKS, EC2 등 다양한 서비스에서 빠르고 안정적으로 가져와 실행할 수 있기 때문
  - ### 🐳 Amazon ECR 도입 이유
| 주요 이유 | 상세 설명 |
| :--- | :--- |
| **안전한 이미지 저장 및 관리** | ECR은 AWS 보안 인프라와 Amazon S3를 기반으로 이미지를 안전하게 저장하며, AWS IAM을 통해 액세스 제어와 권한 관리를 제공하여 이미지의 무결성과 보안을 보장합니다. |
| **AWS 서비스와의 원활한 통합** | Amazon ECS, Amazon EKS, AWS Fargate 등과 통합되어 DevOps 워크플로우를 간소화하고, CI/CD 파이프라인을 효율적으로 운영하여 이미지를 쉽게 배포하고 사용할 수 있습니다. |
| **자동화된 이미지 보안 스캔** | 컨테이너 이미지에 대한 취약점 스캔을 자동으로 수행하여 보안 위협을 탐지하고 리포트를 제공함으로써 안전한 컨테이너 배포를 지원합니다. |
| **확장성과 고가용성** | AWS 글로벌 인프라를 활용해 높은 확장성과 가용성을 제공하며, 여러 가용 영역에 걸쳐 이미지 데이터를 복제하여 단일 지점 장애 없이 안정적인 서비스 운영이 가능합니다. |
| **비용 효율성** | 사용한 만큼 지불하는 요금 구조를 통해 필요한 만큼의 저장 공간과 데이터 전송량에 대해서만 비용을 지불할 수 있어 효율적인 이미지 관리가 가능합니다. |
- IAM 기반의 강력한 보안 관리와 AWS 서비스 간의 손쉬운 통합으로 운영 효율성이 뛰어나기 때문에 ECR을 사용
- AWS Fargate: 서버를 직접 관리할 필요 없이 컨테이너를 실행할 수 있는 서버리스 컴퓨팅 엔진
- ECS: 컨테이너 실행환경 관리형 서비스
- EKS: 쿠버네티스 마스터 관리형 서비스
- ### 🆚 Container Registry 3사 비교 (ECR vs Docker Hub vs GCR)

| 항목 | Amazon ECR | Docker Hub | Google Container Registry (GCR) |
| :--- | :--- | :--- | :--- |
| **제공 플랫폼** | AWS | 독립적 (Docker 제공) | GCP |
| **레지스트리 유형** | 퍼블릭 및 프라이빗 | 퍼블릭 및 프라이빗 | 퍼블릭 및 프라이빗 |
| **주요 통합 서비스** | AWS ECS, EKS, Lambda 등 | 다양한 클라우드 및 로컬 환경 | GCP (GKE, Cloud Run 등) |
| **보안 통합** | AWS IAM을 통한 세분화된 권한 관리 | 기본적인 인증/권한 관리 (개별 설정 필요) | Google Cloud IAM을 통한 권한 관리 |
| **자동 스캔 기능** | 컨테이너 이미지 취약점 자동 스캔 제공 | 이미지 취약점 스캔 (프리미엄 기능) | 컨테이너 이미지 취약점 스캔 제공 |
| **요금 정책** | 저장 및 데이터 전송에 따른 요금 부과 | 무료 플랜 및 유료 플랜 제공 | 저장 및 데이터 전송에 따른 요금 부과 |
| **사용 편의성** | AWS 콘솔 및 CLI에서 직접 관리 가능 | Docker CLI에서 쉽게 접근 가능 | GCP 콘솔 및 gcloud CLI에서 관리 가능 |
| **리전 선택 가능성** | 다중 AWS 리전에서 저장 및 배포 가능 | 글로벌 서비스 (리전 선택 기능 제한적) | 다중 GCP 리전에서 저장 및 배포 가능 |
| **캐시 및 성능 최적화**| AWS S3 기반으로 성능 최적화 | 제한적인 캐시 지원 | Cloud Storage 기반 성능 최적화 |
| **주요 사용 사례** | AWS 기반 애플리케이션의 이미지 저장/배포 | 다양한 클라우드 환경의 이미지 저장/공유 | GCP 기반 애플리케이션의 이미지 저장/배포 |

- #### 1. Docker Image 를 보관 하기 위해
  - 대규모 배포의 한계 극복: 서버가 수십~수백 대일 때 각각 git pull 후 빌드하거나 scp로 이미지를 복사하는 방식은 비효율적이며 명령어 실수 가능성이 큼.
  - 환경 일관성 보장: 서버마다 빌드 환경이 미세하게 달라질 수 있는 리스크를 없애고, 미리 구워진 동일한 컨테이너 이미지만 다운받아 띄우도록 함.
  - 버전 관리 및 빠른 롤백: 800MB가 넘는 무거운 이미지 내역을 개별 서버에 다 남길 수 없으므로, 중앙 저장소(Registry)에서 빌드 내역을 추적하고 문제 발생 시 빠르게 이전 버전으로 롤백함.
  - 보안 및 권한 제어: 회사 내부 이미지는 민감한 정보가 포함되어 있어 외부에 노출되면 안 됨. ECR은 AWS IAM 권한 제어를 통해 안전하게 프라이빗 공유가 가능함.
- #### 2. ECS, EC2, EKS 같은 AWS 내부 컴퓨팅 리소스랑 연결하기 위해서
  - 인프라 종속성과 높은 연동성: 타 클라우드를 섞어 쓰는 멀티 클라우드가 아닌, 오직 AWS 환경만 사용할 경우 AWS 서비스 간의 권한 연동 및 이미지 다운로드 속도가 가장 최적화됨.
  - 네트워크 비용 최적화: AWS는 외부 인터넷 망을 타는 것보다 내부 네트워크 통신 비용이 훨씬 저렴함. Private Subnet에 있는 대용량(예: 1.2GB) 이미지를 땡겨올 때 NAT Gateway 비용 등을 크게 아낄 수 있음.
- #### 3. 보안 스캔
  - 단계별 스캔 분리: 이미지 업로드 시 자동으로 취약점을 찾아주는 Basic Scanning을 기본 제공함.
  - 실무 CI/CD 적용: 일반 PR이나 테스트 태그일 때는 Basic 스캔만 돌리고, 실제 운영 환경으로 머지되어 배포용 태그(Prod Tag)가 찍힐 때는 더욱 정밀한 취약점 조사 서비스인 AWS Inspector를 연동해 강력한 보안 검증을 수행함.

- ### ECR 사용할 때 주의사항
  - #### 1. latest 태그 사용 지양 및 명확한 태그 규칙 수립
    - 버전 불명확성: latest 태그만 쓰면 현재 운영 환경에 정확히 어떤 소스 코드 버전이 배포되어 있는지 파악하기 어려움.
    - 배포 충돌 위험: 여러 개발자가 동시에 CI/CD를 돌리는 환경에서는 내가 빌드한 버전이 아닌 다른 사람의 엉뚱한 최근 버전이 배포될 위험이 있음.
    - 해결책 (Naming Rule): 환경별로 레포지토리를 분리하거나, 태그명에 커밋 해시와 버전을 명확히 명시하는 규칙(prod-${version}-${commit-sha})을 사용해야 함.
  - #### 2. 비용 최적화를 위한 수명 주기(Lifecycle Policy) 설정
    - 비용 스노우볼: ECR은 S3 기반의 유료 저장소임. 대용량(예: 1.2GB) 이미지가 CI/CD 파이프라인을 탈 때마다 쌓이면 수 TB 단위로 불어나 매달 수십만 원의 고정 비용이 발생할 수 있음.
    - 해결책 (Lifecycle 규칙): "생성된 지 N일 지난 이미지 삭제" 또는 "최근 N개의 이미지만 보관" 같은 수명 주기 정책을 필수 적용해야 함. (개발용/운영용 태그별로 조건을 분리하면 더 효율적임)
  - #### 3. 최소 권한 원칙에 따른 IAM 권한 분리
    - 보안 리스크: 이미지 저장소 전체 권한(*)을 남발하면 보안 사고나 실수로 이미지가 삭제되는 대참사가 날 수 있음.
  - #### 4. ECR 인증 토큰의 유효 기간(12시간) 고려
    - 로그인 만료 특성: 한 번 로그인하면 오래 유지되는 도커 허브와 달리, ECR은 보안을 위해 인증 토큰의 유효 시간이 12시간으로 제한됨.
    - 해결책: 그렇기 때문에 배포할 때 세션이 끊겨서 에러가 나지 않도록, CI/CD 스크립트(또는 자동화 프로세스) 상단에는 항상 ECR 로그인 명령어를 선행하도록 작성해야 함.

#### 주제 2: Code Deploy
- Code Deploy: AWS에서 제공하는 자동화된 애플리케이션 배포 서비스
  - 애플리케이션 배포 과정을 자동화하여 배포 중단 없이 신속하고 안정적으로 소프트웨어를 업데이트하기 위해 사용됨
- ### 🚀 도입 이유
| 주요 이유 | 상세 설명 |
| :--- | :--- |
| **배포 자동화** | 수동 배포 오류를 줄이고 배포 속도를 높이며, 복잡한 배포 과정을 자동화하여 일관된 배포 실행을 보장합니다. |
| **중단 없는 배포** | 블루/그린 배포, 롤링 업데이트 등의 전략을 사용해 가용성에 영향을 주지 않고 애플리케이션을 배포할 수 있습니다. |
| **자동 롤백 기능** | 배포 실패 시 자동으로 이전 버전으로 롤백하여 서비스 중단이나 장애를 최소화할 수 있습니다. |
| **배포 관리 및 모니터링** | 배포 상태를 실시간으로 모니터링하고 로그를 제공하여 배포 과정 중 발생하는 문제를 즉시 해결할 수 있도록 지원합니다. |
| **온프레미스 및 클라우드 지원** | AWS 클라우드뿐만 아니라 온프레미스 환경에도 배포가 가능하여 하이브리드 클라우드 환경에서 일관된 배포 프로세스를 유지할 수 있습니다. |
| **DevOps 통합** | AWS CodePipeline, Jenkins, GitHub Actions 등 다양한 CI/CD 도구와 통합되어 DevOps 파이프라인 내에서 효율적인 지속적 배포(CD)를 지원합니다. |


- #### 1. 다중 서버 배포 자동화 및 동적 환경(Auto Scaling) 대응
  - 병렬 배포 및 수동 관리 제거: 배포 타겟 서버가 10대, 100대로 늘어나도 각각 SSH로 접속해 도커 환경을 세팅하고 배포 명령을 치는 반복적이고 비효율적인 작업이 사라짐.
  - 동적 IP 할당 문제 해결: Auto Scaling Group(ASG)에 의해 트래픽에 따라 EC2가 동적으로 생성(예: 2대 ➡️ 10대)되는 상황에서는 배포 시점에 새로 생긴 서버들의 IP를 미리 알 수 없음.
  - 배포 그룹(Deployment Group) 활용: 로드밸런서의 타겟 그룹처럼 CodeDeploy가 '배포 그룹'을 기준으로 인프라를 묶어 관리하기 때문에, 서버가 몇 대가 되든 어떤 IP를 가졌든 간에 그룹 내 모든 인스턴스에 일관되게 병렬 배포를 수행함.
- #### 2. 배포 실패 시 강력하고 자동화된 롤백
  - 지능적인 상태 감지: 배포가 완료된 직후 애플리케이션이 제대로 구동되는지 확인하는 헬스 체크(Health Check) 및 AWS CloudWatch 메트릭과 연동됨.
  - 장애 최소화 (자동 롤백): 배포 중 에러가 발생하거나 헬스 체크가 실패하면, CodeDeploy가 정상 작동하던 이전 버전의 안전한 이미지/코드로 즉시 자동 롤백을 실행하여 서비스 중단 시간을 최소화함.

- ### AWS CodeDeploy 구성 요소 
  - #### 1. Application (애플리케이션)
    - 정의: CodeDeploy에서 배포를 관리하는 최상위 기본 단위.
    - 특징: 서비스 단위별로 생성함 (예: backend-prod, frontend-dev). 배포하려는 컴퓨팅 플랫폼(EC2/On-Premises, ECS, Lambda 중 하나)을 지정함.
  - #### 2. Deployment Group (배포 그룹)
    - 정의: 실제로 서비스 코드가 올라갈 배포 대상 서버(인스턴스)들의 묶음.
    - 관리 방식 (Tag 기반): 개별 서버의 IP 목록을 일일이 등록하는 것이 아니라, Key-Value 태그(key: app, value: was / key: env, value: prod)의 조합으로 배포 대상을 동적으로 매핑함.
    - 핵심: EC2 생성 시 태그 설정이 필수이며, Auto Scaling Group(ASG)과 연동 시 인스턴스가 늘어나도 동일한 태그를 부여받아 자동으로 배포 그룹에 포함됨.
  - #### 3. Revision (버전 / 리비전)
    - 정의: 지정된 배포 그룹에 실제로 전달되어 배포될 결과물(소스 코드 패키지 및 설정 파일).
    - 플랫폼별 형태:
      - EC2 / On-Premises: S3에 업로드된 .zip 압축 파일 (소스 코드 + appspec.yml).
      - ECS: Task Definition ARN + appspec.json (또는 yaml).
  - #### 4. AppSpec File (appspec.yml)
    - 정의: CodeDeploy 에이전트가 각 생명주기(Lifecycle Hook) 단계마다 어떤 커스텀 스크립트 실행 명령을 수행할지 정의한 배포 명세서.
    - 주요 라이프사이클 훅(Lifecycle Hooks) 흐름:
      - ApplicationStop: 기존에 가동 중인 이전 버전 앱 중지.
      - BeforeInstall: 새 버전 설치 전 사전 작업 (디렉토리 정리, 기존 파일 삭제 등).
      - AfterInstall: 파일 복사 완료 후 의존성 설치 및 파일 권한 설정.
      - ApplicationStart: 새 애플리케이션/컨테이너 실행.
      - ValidateService: 헬스 체크 포트 검사 및 정상 동작 여부 최종 검증.
  - #### 5. Deployment Configuration (배포 구성 / 배포 전략)
    - 정의: 배포 시 인스턴스들에 어떤 속도와 배포 전략(Blue/Green, In-Place 등)으로 진행할지 결정하는 규칙.
    - 대표적인 제공 옵션:
        - AllAtOnce: 전체 대상 서버에 동시에 한 번에 배포 (속도는 가장 빠르나 다운타임 발생 위험).
        - OneAtTime: 한 번에 딱 1대의 서버씩 순차적으로 배포 (가용성은 최고 수준으로 유지되나 배포 시간이 길어짐).
        - HalfAtATime: 전체 서버의 50%씩 절반 단위로 나누어 배포.
- ### CodeDeploy의 장점
  - 배포 전략의 표준화: 롤링, 블루/그린 등 복잡한 무중단 배포 메커니즘을 개발자가 직접 스크립트로 구현할 필요 없이, AWS가 검증한 표준화된 기능을 제공함.
  - 정교한 배포 제어: 배포 속도나 타이밍(OneAtTime, HalfAtTime 등)을 마우스 클릭이나 단순 옵션 설정만으로 조절할 수 있음.
  - 동적 인프라 최적화: IP가 계속 변하는 Auto Scaling Group 같은 동적 자원 환경에서도 대상 추적 및 배포를 완벽하게 지원함.
- ### CodeDeploy의 단점
  - #### 1. 방대한 초기 설정과 파편화된 리소스 관리
    - 높은 설정 피로도: GitHub Actions만 쓸 때와 달리 AWS 인프라 단에서 챙겨야 할 설정이 너무 많고 각 서비스에 흩어져 있어 초기 세팅에 시간이 오래 걸림.
    - 연동해야 하는 리소스: 
     - IAM Role: GitHub Actions와 CodeDeploy, EC2 간의 권한 유기적 세팅. 
     - S3 / ECR: 배포할 압축 파일(Revision)이나 컨테이너 이미지를 저장할 공간 세팅. 
     - Deployment Group & AppSpec: 배포 대상 태그 정의 및 수명 주기(Hooks) 스크립트 작성.
  - #### 2. EC2 내부 Agent 관리 부담
    - 에이전트 의존성: CodeDeploy가 작동하려면 배포 대상 EC2 서버 안에 CodeDeploy Agent가 무조건 설치되어 있고, 상시 Running 상태여야 함.
- ### 언제 CodeDeploy를 선택해야 할까?
  - EC2 배포를 완전히 표준화하고 싶을 때: 수동 SSH 접속 배포에서 벗어나 인적 실수(Human Error)를 원천 차단하고 싶을 때.
  - Auto Scaling 환경일 때: 트래픽에 따라 여러 대의 EC2가 동적으로 생성되고 삭제되는 환경을 운영할 때.
  - AWS 중심의 아키텍처일 때: 인프라가 AWS 서비스 위주로 끈끈하게 결합되어 있어, CD 파이프라인의 안정성을 극대화하고 싶을 때.
  - 다양한 배포 전략이 필요할 때: 서비스 중단 없이 안정적으로 새 버전을 밀어 넣는 롤링이나 블루/그린 배포 전략을 쉽게 도입하고 싶을 때.
