### 새로 배운 내용
#### 주제 1: VPC, Public subnet, Private subnet
- VPC: 공용 클라우드 환경에서 사용자에게 독립된 가상 네트워크를 제공하는 서비스
  - 서비스 간 격리를 통해 보안 위험을 최소화하고, 제어 가능한 폐쇄형 네트워크 환경을 구성하기 위해서
- 서브넷 (Subnet): VPC 내의 IP 주소 범위를 나눠 생성한 논리적 네트워크 단위
- 퍼블릭 서브넷: 인터넷과 연결되어 외부 접근이 가능한 서브넷
- 프라이빗 서브넷: 인터넷과 직접 연결되지 않고, 내부 통신만 가능한 서브넷
- ### 📌 서브넷 구분 및 배치 기준
    - | 구분 | 라우팅 테이블 기준 | 일반 배치 대상 |
      | :--- | :--- | :--- |
      | **Public Subnet** | 외부 인터넷과 통신할 수 있는 **인터넷 게이트웨이(IGW)**로 향하는 라우팅 경로가 존재함 | `ALB (Application Load Balancer)`, `Bastion Host`, `NAT Gateway` |
      | **Private Subnet** | 외부 인터넷 게이트웨이로 직접 연결되는 **라우팅 경로가 존재하지 않음** (비공개 격리 대역) | `App Server (API 서버)`, `RDS (데이터베이스)`, `ElastiCache (캐시 서버)` |
  
- 라우팅 테이블: 서브넷 간 또는 인터넷과의 데이터 흐름을 결정하는 라우팅 규칙 목록
- 인터넷 게이트웨이(IGW): VPC와 인터넷 간의 연결을 지원하는 게이트웨이 장치
- NAT 게이트웨이: 프라이빗 서브넷에서 인터넷으로의 아웃바운드 연결을 지원하는 장치
- 가용 영역(Availability Zone, AZ): AWS 리전 내에서 물리적으로 분리된 데이터 센터의 한 단위
- ### 🌐 VPC 인프라 아키텍처 구축 단계
  - | 작업 단계 | 핵심 설명 |
    | :--- | :--- |
    | **VPC 생성** | 네트워크의 가장 기본 틀을 만드는 단계로, **IP 대역(CIDR 블록, 예: `10.0.0.0/16`)을 지정**하고 네임 태그 등 기본 인프라 설정을 진행합니다. |
    | **서브넷 생성** | 생성한 VPC 내부 공간을 **퍼블릭(Public) 서브넷**과 **프라이빗(Private) 서브넷** 등으로 쪼개어, 호스트 규모를 제한하고 논리적으로 대역을 격리합니다. |
    | **라우팅 테이블 설정** | 서브넷별로 패킷이 나갈 목적지(CIDR)와 통로(게이트웨이)를 매핑하여, **네트워크 트래픽의 실제 흐름과 이정표를 결정**합니다. |
    | **인터넷 / NAT 게이트웨이** | 퍼블릭 서브넷에는 외부 인터넷과 직결되는 **인터넷 게이트웨이(IGW)**를, 프라이빗 서브넷에는 안전한 아웃바운드 통신을 위한 **NAT 게이트웨이**를 연결하여 외부 통신을 제어합니다. |
    | **보안 그룹 / 네트워크 ACL** | 포트(Port)와 프로토콜(Protocol)을 기반으로 **인바운드/아웃바운드 트래픽을 제어**하며, 인스턴스 및 서브넷 단계의 다중 보안 경계 벽을 구축합니다. |
    | **VPN / Direct Connect** | 회사 내부망(온프레미스)과 클라우드 VPC를 안전하게 터널링으로 연결하여 하나의 망처럼 쓰는 **하이브리드 클라우드 환경을 구성**합니다. |


#### 주제 2: IAM, Security Group, Route53, DNS
- IAM: AWS 리소스에 대한 사용자 인증과 권한 관리를 제공하는 서비스
  - 사용자와 리소스에 대한 세밀한 권한 제어를 통해 보안성을 강화하고 운영을 안전하게 관리하기 위해
- ### 🔑 AWS IAM 핵심 구성 요소 및 역할
    - | 구성 요소 | 역할 |
      | :--- | :--- |
      | **Root User** | AWS 계정을 처음 생성할 때 만들어지는 **최고 관리자 계정**으로, 모든 리소스에 대한 전권을 가집니다. |
      | **User** | AWS 인프라에 접근하는 **개별 사용자** 계정으로, 고유의 인증 정보와 권한을 가집니다. |
      | **Group** | 다수의 User들을 하나의 묶음으로 관리하며, **공통된 권한을 효율적으로 한 번에 부여**할 때 사용합니다. |
      | **Role** | 개별 사용자가 아닌, 특정 자격이나 **AWS 서비스(EC2 등)가 임시로 권한을 위임받아 역할을 수행**할 때 사용하는 임시 권한 체계입니다. |
      | **Policy** | 어떤 리소스에 대해 어떤 작업(Action)을 허용하고 거부할지 JSON 형식 등으로 명시해 둔 **실제 권한 규칙**입니다. |
      | **MFA** | 멀티 팩터 인증(Multi-Factor Authentication)으로, 로그인 시 아이디/비밀번호 외에 **추가적인 보안 인증을 요구**하여 계정을 보호합니다. |

- Security Group: 클라우드 환경에서 인스턴스에 대한 네트워크 트래픽을 제어하는 가상 방화벽
  - 인스턴스에 대한 트래픽을 필터링하여 보안을 강화하기 위해서
- Route53: AWS(Amazon Web Services)에서 제공하는 확장 가능한 클라우드 도메인 네임 시스템(DNS) 서비스
  - AWS 리소스를 포함한 도메인 기반 서비스들을 클라우드 환경에서 안정적이고 자동화된 방식으로 연결(매핑)하기 위해 사용하기 위해서
  - | 사용 이유 | 설명 |
    | :--- | :--- |
    | **도메인 이름 등록 및 관리** | 도메인 이름을 직접 등록하고 **DNS 레코드를 체계적으로 관리**하여, 웹사이트나 애플리케이션의 도메인을 효율적으로 연결합니다. |
    | **고급 트래픽 라우팅 기능** | **지리적 위치 기반, 가중치 기반** 등 다양한 라우팅 정책을 제공하여 트래픽을 효율적으로 분산하고 사용자 경험(UX)을 최적화합니다. |
    | **헬스 체크 및 자동 장애 조치** | 서버와 앱의 상태를 실시간 모니터링하며, 장애 발생 시 **정상 서버로 트래픽을 자동 라우팅(Failover)**하여 서비스 가용성을 극대화합니다. |
    | **글로벌 분산 및 확장성** | AWS 글로벌 엔드포인트를 활용해 **전 세계 사용자에게 빠른 DNS 응답을 제공**하며, 대규모 트래픽 증가에도 탄력적으로 대응합니다. |
    | **통합된 관리 및 보안** | CloudFront, ALB 등 다른 AWS 서비스와 유기적으로 연동되며, **DNSSEC 및 IAM 권한 제어**를 통해 DNS 데이터 보안을 강화합니다. |
  - NS(Name Server) 레코드: 특정 도메인 이름에 대한 권한을 가진 DNS 서버를 지정하는 레코드
  - SOA(Start of Authority) 레코드: 특정 DNS 영역(Zone)에 대한 관리 정보를 나타내며, 주 DNS 서버, 관리자 이메일, 영역의 갱신 주기 등을 정의
- ### 🌐 DNS 레코드 유형별 역할 및 예시 총정리
    - | 레코드 | 역할 | 예시 |
      | :--- | :--- | :--- |
      | **A** | 도메인 이름을 **IPv4 주소**로 매핑합니다. | `example.com` ➔ `203.0.113.10` |
      | **AAAA** | 도메인 이름을 **IPv6 주소**로 매핑합니다. | `example.com` ➔ `2001:db8::1` |
      | **CNAME** | 도메인 이름을 **또 다른 도메인 이름(별칭)**으로 매핑합니다. | `www.example.com` ➔ `example.com` |
      | **Alias**<br>*(Route 53 전용)* | 도메인 이름을 **AWS 내부 리소스**에 비용 없이 직접 연결하는 방식입니다. | `example.com` ➔ `ALB 엔드포인트` |
      | **MX** | 해당 도메인으로 오는 이메일을 처리할 **메일 서버를 지정**합니다. | `example.com` ➔ `mail.example.com` |
      | **TXT** | 도메인에 대한 **텍스트 기반의 인증 및 정책 정보**를 저장합니다. | `SPF, DKIM 설정` 및 `ACM SSL/TLS 인증 검증` |
      | **NS** | 도메인의 DNS 쿼리를 처리할 권한이 있는 **담당 네임서버**를 지정합니다. | `Route 53에서 배정받은 네임서버 주소` |
      | **SRV** | 특정 **서비스의 호스트와 포트(Port) 정보**를 동시에 제공합니다. | 일부 서비스 디스커버리 및 도메인 기반 서비스 연결 |

- ### 🗺️ AWS Route 53 라우팅 정책 (Routing Policies)

DNS의 가장 기본 역할은 도메인 이름을 입력받아 해당되는 IP 주소(A 레코드 등)를 리턴하는 것입니다. AWS의 Route 53은 단순한 IP 매핑을 넘어 **부하 분산(Load Balancing), 장애 조치(Failover), 카나리 배포(Canary Deployment)** 등 고도화된 트래픽 제어 기능을 제공합니다.

- ### 📊 Route 53의 다양한 트래픽 라우팅 정책
    - | 정책 유형 | 핵심 동작 원리 | 실무 활용 및 배포 전략 |
      | :--- | :--- | :--- |
      | **1. 단순 라우팅<br>(Simple)** | 하나의 도메인 이름에 하나의 특정 IP(또는 리소스)를 다이렉트로 매핑하여 전달합니다. | 가장 기본적인 연결 방식으로, 사용자의 요청을 **퍼블릭 ALB(Application Load Balancer)**로 바로 보낼 때 사용합니다. |
      | **2. 가중치 기반 라우팅<br>(Weighted)** | 하나의 도메인에 연결된 여러 엔드포인트에 대해 **사용자가 설정한 비율(%)대로 트래픽을 분산**합니다. | **실무에서 매우 중요한 무중단 배포 및 카나리(Canary) 배포**에 활용됩니다. (예: 기존 v1 서버에 가중치 90, 신규 v2 서버에 가중치 10을 설정하여 안정성 검증) |
      | **3. 장애 조치 라우팅<br>(Failover)** | **Active-Passive(주-부) 구조**로 운영됩니다. 주 서버의 헬스 체크 상태가 정상이면 주 서버로만 보내고, 비정상 감지 시 대기 중인 부(Standby) 서버로 트래픽을 넘깁니다. | **재해 복구(DR) 환경 구축**에 필수적입니다. (예: 평소에는 서울 리전 ALB로 서비스하다가, 서울 리전 장애 시 도쿄 리전 ALB로 자동 전환) |
      | **4. 지연 시간 기반 라우팅<br>(Latency)** | 전 세계 여러 AWS 리전 중, **사용자와 AWS 리전 간의 네트워크 지연 시간(Latency)이 가장 낮은(빠른) 곳**으로 트래픽을 보냅니다. | 글로벌 유저를 대상으로 서비스할 때, 상대적으로 네트워크 응답 속도가 가장 빠른 리전의 서버로 연결하여 **사용자 경험을 최적화**합니다. |
      | **5. 지리적 위치 라우팅<br>(Geolocation)** | 사용자의 **실제 IP 주소를 기반으로 대륙/국가 위치를 판별**하여, 그 지역과 매핑된 가장 가까운 리전으로 라우팅합니다. | **지역별 콘텐츠 현지화 및 규제 준수**에 활용됩니다. (예: 한국에서 접속한 유저는 한국어 페이지를 제공하는 리전으로, 유럽 접속자는 유럽 리전으로 안내) |


#### 주제 3: 가상화, 하이퍼바이저, EC2, EBS
- 가상화: 하나의 물리 컴퓨터를 여러 개의 “독립된” 가상 컴퓨터를 실행하는 기술
- 하이퍼바이저: 물리 서버 한 대에 CPU, 메모리, 디스크, 네트워크 등의 자원을 여러 개 “가상 컴퓨터” 가 나눠서 사용하고 서로를 격리 해주는 소프트웨어 계층
  - | 역할 | 설명 |
    | :--- | :--- |
    | **CPU 분배** | 물리 서버의 CPU 자원을 효율적으로 나누어, 어떤 EC2 인스턴스가 언제 CPU를 사용할지 스케줄링하고 조정합니다. |
    | **Memory 분리** | 물리 메모리를 논리적으로 분할하여, 각 EC2 인스턴스가 오직 자신만의 독립된 메모리 공간을 사용하는 것처럼 보이게 제어합니다. |
    | **가상 장치 제공** | 물리적인 하드웨어를 추상화하여 각 인스턴스에 가상 디스크(EBS 등), 가상 네트워크 카드(ENI) 등의 가상 리소스를 제공합니다. |
    | **격리 (Isolation)** | 다중 테넌트 환경에서 보안을 유지하기 위해, 다른 고객의 EC2 인스턴스 메모리·프로세스·디스크에 절대 접근하지 못하도록 완벽히 차단합니다. |
- EC2: 사용자가 필요에 따라 쉽게 가상 서버(인스턴스)를 생성, 구성, 관리할 수 있도록 하여 다양한 워크로드를 지원하는 확장 가능하고 안전한 클라우드 컴퓨팅 서비스
  - 필요한 시점에 서버를 즉시 확보·확장해 비용 부담 없이 안정적이고 유연한 컴퓨팅 환경을 제공하기 위해서
- EBS:  EC2 인스턴스에 연결해 사용할 수 있는 블록 스토리지 서비스로, 클라우드 내에서 서버의 하드 디스크처럼 동작하는 가상 디스크 
- ### 🔄 EC2 인스턴스 생명주기(Lifecycle) 및 EBS 상태 변화
    - | 상황 | EC2 인스턴스 상태 | EBS (디스크) 상태 |
      | :--- | :--- | :--- |
      | **인스턴스 실행 (Start)** | 물리 서버 자원이 할당되어 **OS 및 서버가 정상 구동**됩니다. | 인스턴스에 마운트되어 **실시간 데이터 읽기/쓰기(디스크)**가 가능합니다. |
      | **인스턴스 중지 (Stop)** | **CPU 및 메모리 자원 사용이 즉시 중단**되며, 인스턴스 요금은 청구되지 않습니다. | 데이터는 휘발되지 않고 **EBS에 그대로 유지**되며, 디스크 스토리지 요금은 계속 청구됩니다. |
      | **인스턴스 시작 (Restart)** | 중지 상태에서 다시 실행 시, **새로운 물리 장비에 가상 서버가 재할당**되어 구동됩니다. | 기존에 연결되어 있던 **EBS가 그대로 자동 연결**되어 이전 데이터를 이어 씁니다. |
      | **인스턴스 종료 (Terminate)** | 가상 서버 가동이 완전히 중단되고 **인스턴스 자체가 영구 삭제**됩니다. | **종료 시 삭제(Delete on Termination)** 기본 정책 설정 여부에 따라 인스턴스와 함께 자동 삭제되거나 분리됩니다. |
      | **스냅샷 생성 (Snapshot)** | 인스턴스 상태(실행/중지 등)와 무관하게 언제든 수행 가능합니다. | 특정 시점의 EBS 데이터 상태를 그대로 얼려 **S3에 독립적인 백업본(Snapshot)**으로 저장합니다. |
- 온프레미스 (On-Premises): 소프트웨어나 하드웨어가 외부의 클라우드 서비스나 호스팅 서비스가 아닌, 조직 내부의 물리적 장소에서 운영되고 관리되는 방식
- ### 🏗️ 인프라 운영 환경별 특성 비교 (온프레미스 vs 호스팅 vs 클라우드)

      | **확장성** | 🔴 **제한적** (물리 장비 추가 구매 필요) | 🔴 **제한적** (제공 업체 스펙 안에서 가능) | 🟢 **우수** (몇 번의 클릭/명령어로 즉시 확장) |

      | **성능 최적화** | 🟢 **우수** (인프라 전체를 커스텀 가능) | 🟡 **상황에 따라 다름** | 🟡 **상황에 따라 다름** |
