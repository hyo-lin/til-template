#### 주제 1: Inline, Out of Path, Wireshark
- Inline: 네트워크 상의 데이터 패킷이 반드시 해당 장치를 통과하도록 설계된 네트워크 구조
  - 데이터를 중간에서 가로채지 않고, 네트워크 경로에 직접적으로 개입하여 트래픽이 목적지에 도달하기 전에 허용, 차단, 필터링과 같은 작업을 수행할 수 있습니다.
  - | 특징 | 설명 |
    | :--- | :--- |
    | **🔒 네트워크 경로 제어** | 모든 데이터 패킷은 Inline 장치를 통과하며, 장치가 설정한 규칙에 따라 네트워크 내 이동이 결정됨. 이는 네트워크 경로의 완전한 통제를 가능하게 함. |
    | **⚡ 강제적 통과** | Inline 구조에서 장치는 네트워크 경로 상 필수적인 요소로 작동하므로, 트래픽은 반드시 이를 거쳐야 함. 이를 통해 트래픽의 차단, 허용, 수정 작업을 효과적으로 수행할 수 있음. |
    | **🛣️ 연결된 경로 기반 설계** | Inline 장치는 물리적으로 네트워크 장치와 연결되거나 논리적으로 데이터 경로의 필수 노드로 구성됨. 따라서 네트워크의 중추적인 위치에 배치됨. |
    | **🛡️ 보안 및 관리 중심 설계** | 실시간 트래픽 제어와 보안 작업 수행을 목적으로 설계되었으며, 악성 트래픽 차단, 데이터 유출 방지, 규칙 기반 네트워크 관리 기능 제공. |
  - 🛠️ 네트워크 제어 및 보안 장치 요약
  - | 장치명 | 설명 |
    | :--- | :--- |
    | **🌐 공유기 (Router)** | 네트워크 트래픽을 경유하며, 내부망과 외부망을 연결하고 기본적인 데이터 흐름 관리를 수행함. |
    | **🔥 방화벽 (Firewall)** | 미리 정의된 보안 규칙에 따라 네트워크를 통과하는 트래픽을 실시간으로 허용하거나 차단함. |
    | **🎛️ 네트워크 스위치 (Switch)** | 내부 네트워크(LAN) 안에서 트래픽을 목적지 MAC 주소나 특정 조건에 따라 정확하게 포트로 라우팅(전송)함. |
    | **🛡️ 침입 방지 시스템 (IPS)** | 패킷 내부를 심층 분석하여 악성 트래픽을 실시간으로 탐지하고 즉각 차단하여 네트워크 보안을 적극적으로 강화함. |

  - Inline 장치의 패킷 처리 메커니즘 단계
  - | 단계 | 프로세스명 | 설명 |
    | :---: | :--- | :--- |
    | **01** | **📥 패킷 통과** | Inline 구조의 장치를 통과하는 모든 실시간 데이터 패킷을 유실 없이 캡처함. |
    | **02** | **🔍 분석 및 검사** | 캡처한 패킷의 헤더(L3/L4 정보)와 페이로드(실제 데이터 영역)를 정밀 분석하여 규칙 위반이나 패턴 일치 여부를 판단함. |
    | **03** | **🛡️ 처리 및 통과** | 사전에 정의된 규칙(Policy)에 따라 트래픽을 그대로 허용(Pass), 차단(Drop), 또는 특정 세션만 필터링하는 작업을 수행함. |
    | **04** | **⚡ 성능 최적화** | 사용자 영역으로의 컨텍스트 스위칭을 최소화하기 위해 커널 모드(Kernel Mode)에서 데이터를 다이렉트로 처리하여 빠르고 효율적인 성능을 유지함. |
    | **05** | **📝 이벤트 기록** | 차단되거나 탐지된 모든 트래픽 이벤트를 로그(Log)로 데이터베이스에 저장하고, 심각한 위협 발생 시 관리자에게 실시간으로 경고를 보고함. |
  
  - Inline 구조의 한계점
  - 1. 병목현상: 병목현상은 장치의 하드웨어 성능이 부족하거나, 고속 네트워크에서 모든 트래픽을 실시간으로 처리하는 과정에서 처리 지연이 발생할 때 발생합니다.
       또한 복잡한 보안 규칙이나 암호화 작업이 증가하면 이 문제가 더욱 심화될 수 있습니다.
  - 2. 단일 장애점 (Single Point of Failure): 네트워크 경로 상의 필수 노드로 작동하기 때문에, 장치에 문제가 발생하면 전체 네트워크가 중단되는 "단일 장애점" 문제가 발생할 수 있습니다.
  
  - Inline 구조의 안정성 확보 및 관리 방안
  - | 운영 방안 | 상세 설명 |
    | :--- | :--- |
    | **🔗 이중화** | 동일한 역할을 하는 Inline 장비를 2대 이상(Active-Active 또는 Active-Standby) 구성하여 시스템 전반의 단일 장애점(SPOF)을 제거함. |
    | **🔄 Failover** | 운영 중인 메인 장비에 장애가 발생했을 때, 대기하고 있던 백업 장비로 트래픽 경로를 실시간 자동 전환하여 서비스 연속성을 보장함. |
    | **🛣️ Bypass Mode** | 하드웨어 고장이나 전원 차단 등 심각한 장비 장애 발생 시, 패킷 검사를 생략하고 트래픽을 물리적/논리적으로 그냥 통과(우회)시켜 네트워크 단절을 막음. |
    | **⚖️ 로드밸런싱** | 부하 분산 장치를 전면에 배치하여 대용량 네트워크 트래픽을 여러 대의 검사 장비로 나누어 전송함으로써 개별 장비의 성능 과부하를 방지함. |
    | **🧪 정책 테스트** | 새로운 차단 규칙을 실제 운영 환경에 바로 적용하지 않고, 사전 탐지 모드(Inline-Tap/Simulation)나 별도의 테스트 환경에서 정상 패킷 오차단 여부를 검증함. |
    | **📊 모니터링** | 장비의 실시간 패킷 처리 지연 시간(Latency), 오차단/정상 차단 수, 에러율, 시스템 자원(CPU/Memory) 상태를 상시 감시하여 이상 징후를 조기에 파악함. |
    | **🧹 규칙 최적화** | 시스템 부하를 줄이고 처리 속도를 높이기 위해, 기간이 만료되었거나 중복·과도하게 설정된 불필요한 방화벽/IPS 규칙을 주기적으로 정리하고 관리함. |

- Out of Path: 네트워크 경로에서 데이터를 실시간으로 처리하지 않고, 트래픽을 복사하거나 분석용으로 수집하여 별도 장치에서 처리하는 네트워크 구조
  - | 특징 | 설명 |
    | :--- | :--- |
    | **🔄 경로 외부 동작** | 데이터를 실제 네트워크 통신 경로 외부에서 복사하거나 감청(TAP)하여 처리함. 즉, 트래픽의 실제 흐름에 직접적인 간섭을 주지 않음. |
    | **👁️ 비간섭성 (Read-Only)** | 네트워크 경로와 완전히 독립적으로 동작하므로, 장비의 데이터 분석 부하가 원래 네트워크의 전송 성능이나 서비스 안정성에 전혀 영향을 미치지 않음. |
    | **⏱️ 비실시간 처리** | 실시간 트래픽 차단이나 제어가 목적이 아니라, 원본 데이터에 영향을 주지 않고 뒤에서 조용히 수집·기록하는 사후 데이터 분석 및 탐지 목적으로 설계됨. |
    | **🔍 탐지 및 분석 중심** | 보안 위협 유입, 불법 네트워크 접근 등을 감지하고, 현재 전체적인 네트워크 트래픽 상태를 모니터링하여 경고 및 통계 분석 결과를 제공함. |
    | **🟢 서비스 안정성 보장** | 트래픽 경로 외부에서 작동하기 때문에, 해당 분석 장치에 고장이나 전원 차단 등 장애가 발생하더라도 실제 사용자의 네트워크 흐름은 100% 정상 유지됨. |
 
  - | 채택 이유 | 상세 설명 |
    | :--- | :--- |
    | **🟢 트래픽 흐름 영향 제로** | 실제 통신 경로 외부에서 복사된 데이터를 처리하므로, 실시간 사용자 트래픽의 대역폭이나 속도에 전혀 영향을 주지 않으면서 안정적인 모니터링 작업을 수행할 수 있음. |
    | **🚨 보안 위협 탐지 및 예방** | 데이터를 백그라운드에서 실시간으로 심층 분석하여 악성 코드 유입, 보안 정책 위반, 중요 데이터 외부 유출 등의 위협을 감지하고, 관리자에게 즉각적인 대응 경고를 제공함. |
    | **💎 서비스 가용성 극대화** | 분석 장비에 과부하가 걸리거나 하드웨어 장애(Fault)가 발생하더라도 메인 네트워크 선로와 격리되어 있어, 대고객 서비스 중단 없이 시스템을 안정적으로 유지할 수 있음. |
    | **🧩 유연한 아키텍처 확장성** | 전체 네트워크 인프라를 재구성할 필요 없이, 모니터링이 필요한 구간에 분석 장치(Sensor)만 독립적으로 추가 배치할 수 있어 다양한 규모의 인프라 환경에 유연하게 대응 가능함. |
  - 동작 방식
    - 1. 트래픽 복사 및 수집
    - 2. 실시간 데이터 분석
    - 3. 대응 및 조치
    - 4. 로그 저장 및 모니터링

- Inline 구조 vs Out-of-Path 구조 비교 요약
  - | 구분 | 🔒 Inline | 📡 Out-of-Path (Mirroring) |
    | :---: | :--- | :--- |
    | **위치** | 실제 트래픽이 통과하는 **경로 내부 (On-Path)** | 실제 트래픽 경로와 격리된 **경로 외부 (Off-Path)** |
    | **원본 트래픽 처리** | 원본 패킷을 장비가 직접 수신하여 통과시킴 | 원본 패킷을 복사한 **복사본(Mirror)**을 전달받아 분석 |
    | **차단 능력** | 규칙 위반 시 실시간으로 **직접 차단(Drop/Reset) 가능** | 실시간 직접 차단은 불가하며 차단 기능이 매우 제한적 |
    | **서비스 영향** | 장비 과부하 및 장애 발생 시 **네트워크 단절 위험 큼** | 센서(Sensor) 장비에 장애가 나도 **실제 서비스 영향 없음** |
    | **주요 목적** | 트래픽 실시간 제어, 능동적 차단, 보안 필터링 | 네트워크 탐지, 이상 징후 분석, 상시 모니터링 |
    | **대표 장비** | 방화벽(Firewall), IPS, WAF, 로드밸런서(LB) | IDS, SIEM, Zeek, Wireshark, Flow Logs |
    | **📌 직관적 비유** | 🚧 **도로 위의 검문소** (지나가지 못하게 바로 막음) | 📹 **도로 옆의 CCTV** (지나가는 것을 찍어서 기록함) |

- WireShark: 네트워크의 문제, 분석, 소프트웨어 및 통신 프로토콜 개발, 교육에 쓰이는 오픈 소스 패킷 분석 프로그램

#### 주제 2: 네트워크 캡쳐
- 네트워크 캡처 도구(Wireshark) 사용 이유: 애플리케이션(API 서버 등)에 트래픽이 도달하기 전, 네트워크 인프라단에서 발생하는 문제를 진단하기 위해 사용합니다. "서버 로그에도 아무것도 안 찍힐 때" 가 외독(Isolation) 단계의 시작입니다.
- 와이어샤크 필터(Filter) 아키텍처
  - | 필터 종류 | 적용 시점 | 주요 특징 | 예시 식 |
    | :---: | :--- | :--- | :--- |
    | **Capture Filter** | 패킷 수집 **전** | • 조건에 맞는 패킷만 디스크/메모리에 저장<br>• 시스템 부하 및 저장 파일 용량을 최소화할 때 사용 | `host 8.8.8.8`<br>`port 22`<br>`tcp` |
    | **Display Filter** | 패킷 수집 **후** | • 일단 전부 캡처한 후 화면에 보여줄 때만 필터링<br>• 실시간으로 필터 식을 수정해도 기존 캡처 데이터가 유지되어 안전함 | `ip.addr == 172.168.0.1`<br>`ip.dst == 8.8.8.8` |

- 실무 필수 디스플레이 필터 (Display Filter)
  - 🔹 프로토콜 및 계층별 필터
* `dns` : 애플리케이션 계층의 DNS 질의 및 응답 패킷만 선별
* `http` : 평문 웹 트래픽 (기본 HTTP 80 포트 중심) 분석
* `tls` : 암호화된 HTTPS 보안 트래픽 (TLS 프로토콜) 추적
* `tcp` / `udp` : 전송 계층(L4) 프로토콜 타입별 모아보기

  - 🔹 IP 주소 및 포트 타겟팅 필터
* `ip.addr == 8.8.8.8` : 출발지(Src) 혹은 목적지(Dst)에 해당 IP가 포함된 모든 트래픽
* `ip.src == 192.168.0.10` : 특정 호스트가 송신한 패킷만 추적
* `ip.dst == 8.8.8.8` : 특정 서버를 목적지로 하는 인바운드 트래픽 모니터링
* `tcp.port == 443` : TCP 포트 번호가 443(HTTPS)인 패킷만 필터링

  - 🔹 고급 장애 진단 및 트래픽 분석 필터
* `tcp.flags.syn == 1` : TCP 연결 요청 단계인 **`[SYN]`** 패킷만 추출 (접속 시도 및 핸드셰이크 시작점 파악)
* `tcp.analysis.retransmission` : 패킷 유실 및 네트워크 혼잡으로 인해 발생한 **`TCP 재전송`** 패킷 집중 감지

- 💡 서버 로그에 아무것도 안 찍힐 때의 디버깅 순서
  1. **DNS 분석 (`dns`)**
      * 클라이언트가 도메인에 매핑된 올바른 서버 IP를 받아오는지 확인합니다.
  2. **TCP 핸드셰이크 분석 (`tcp.flags.syn == 1`)**
      * 서버의 보안 그룹(Inbound Port)이 막혀있다면, 클라이언트가 보낸 `[SYN]` 패킷에 대해 서버가 응답하지 않아 `Operation timed out`이 발생합니다.
  3. **네트워크 유실 분석 (`tcp.analysis.retransmission`)**
      * 서버 스펙 대비 과도한 트래픽이 몰리거나 인프라 선로가 불안정할 경우, 재전송 패킷 비율이 급증하며 클라이언트단에서 응답 지연(Latency)을 겪게 됩니다.


### 오늘의 회고
- nline 구조는 실시간 제어/차단뿐만 아니라 통과 트래픽의 성능 모니터링을 동반하며, Out-of-Path 구조는 서비스 간섭 없이 안정적인 탐지 및 모니터링을 수행한다는 것을 알게되었다.
- 네트워크 분석 방식을 익혀 서버 트러블슈팅에 적용해야겠다.
