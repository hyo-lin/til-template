#### 주제 1: Proxy, VPN
- Proxy: 클라이언트와 서버 사이에서 중계자 역할을 하는 네트워크 장치
  - 프록시(Proxy) 서버의 주요 기능 및 역할
    - | 기능 | 상세 설명 |
      | :--- | :--- |
      | **🔒 보안 강화** | • 클라이언트와 서버 간의 직접적인 연결을 차단하여 외부 공격 및 내부 데이터 유출을 방지함.<br>• 리버스 프록시(Reverse Proxy)를 통해 실제 서버의 IP를 외부에 숨기고 DDoS 공격을 효과적으로 차단함. |
      | **⚡ 트래픽 최적화** | • 자주 요청되는 데이터를 저장하는 캐싱(Caching) 기술을 활용하여 응답 속도를 개선하고 대역폭을 절약함.<br>• 로드 밸런싱(Load Balancing) 기능을 통해 여러 대의 서버로 부하를 분산하여 대규모 트래픽을 안정적으로 처리함. |
      | **👁️ 정책 준수 및 감시** | • 사내 콘텐츠 필터링, 특정 사이트 접근 제한 등을 통해 조직의 네트워크 사용 정책을 강제함.<br>• 지나가는 모든 트래픽을 실시간 모니터링하여 비인가 활동이나 보안 정책 위반 소지를 사전에 탐지함. |
      | **🎭 익명성 제공** | • 포워드 프록시(Forward Proxy)를 통해 클라이언트의 실제 IP 주소를 숨기거나 우회하여 개인정보를 보호함.<br>• 국가별 지리적 제한이 걸려 있는 웹 콘텐츠 및 서비스에 대한 접근을 가능하게 함. |
  - Forward Proxy vs Reverse Proxy 비교 요약
    - | 유형 | 🎭 대리 역할 및 위치 | 🎯 주요 목적 및 활용 |
      | :---: | :--- | :--- |
      | **Forward Proxy** | **클라이언트(공객) 대리**<br>• 클라이언트망 내부 환경에 위치하여 요청을 가로채 외부 서버로 전달함. | • 사내 보안 정책 준수 (특정 웹사이트 차단)<br>• 클라이언트의 실제 IP 우회 및 익명 브라우징<br>• 자주 방문하는 외부 자원 캐싱으로 속도 개선 |
      | **Reverse Proxy** | **서버(대고객) 대리**<br>• 서버망의 전면에 위치하여 외부 클라이언트의 요청을 받아 내부 WAS로 분산함. | • 실제 API/웹 서버 인프라의 IP 은닉 (보안 강화)<br>• 여러 대의 서버로 트래픽을 나누는 로드 밸런싱<br>• HTTPS/SSL 인증서 암호화 처리 집중화 |
  - 프록시(Proxy)를 바라보는 두 가지 관점
    - | 관점 | 상세 설명 | 주요 활용 영역 |
      | :---: | :--- | :--- |
      | **🔓 우회 관점** | • 네트워크의 인위적인 제약이나 방화벽을 우회함.<br>• 클라이언트의 익명성을 보장하며 차단된 국가/콘텐츠에 자유롭게 접근 가능함. | • VPN 서비스 및 우회 프록시<br>• IP 은닉을 통한 익명 브라우징<br>• 국가 제한 콘텐츠 시청 |
      | **🛡️ 보호 및 감시 관점** | • 내부 네트워크 보안을 체계적으로 강화함.<br>• 비인가 트래픽을 차단하는 정책 준수와 실시간 트래픽 감시를 통해 인프라를 안전하게 운영함. | • 사내 방화벽 및 보안 게이트웨이<br>• 악성 사이트/콘텐츠 필터링<br>• 기업 내 네트워크 감사 및 로그 기록 |
  - 프록시(Proxy) 서버 도입 이유 및 기대 효과
    - | 도입 이유 | 상세 설명 |
      | :--- | :--- |
      | **🛡️ 보안 및 익명성** | 클라이언트와 서버 간의 직접적인 세션 연결을 차단하고 IP 주소를 은닉(Masking)하여, 외부 해킹 공격과 내부 개인정보 유출을 방지하며 사용자의 네트워크 익명성을 철저히 보장함. |
      | **⚡ 트래픽 최적화** | 반복적인 요청에 대해 대역폭을 절약하는 **캐싱(Caching)**과 대규모 트래픽을 분산 전송하는 **로드 밸런싱(Load Balancing)**을 통해 네트워크 응답 속도를 향상시키고 백엔드 서버의 부하를 줄임. |
      | **🌐 접근성 향상** | 방화벽이나 인프라 정책상 차단된 내부 콘텐츠 및 서비스에 접근할 수 있도록 지원하며, 특정 국가/지역에 걸려 있는 지리적 접근 제한(Geo-blocking)을 유연하게 우회하여 서비스를 이용할 수 있게 함. |
      | **📊 네트워크 관리** | 통과하는 모든 요청(Request)과 응답(Response)을 정밀 모니터링하고, 유해 자원 콘텐츠 필터링 및 비인가 트래픽 제어 정책을 적용함으로써 전체적인 네트워크 자원을 효율적이고 안정적으로 관리함. |
  - Forward Proxy vs Reverse Proxy 기본 개념 비교
    - | 유형 | 🔄 핵심 동작 방식 | 🎭 대리 역할 및 흐름 |
      | :---: | :--- | :--- |
      | **Forward Proxy** | 클라이언트의 요청을 프록시 서버가 받아 목적지 서버로 전달하고, 서버 응답을 다시 클라이언트로 반환함. | **클라이언트를 대리**하여 외부 인터넷 서버와 통신함. |
      | **Reverse Proxy** | 클라이언트 요청을 리버스 프록시가 받아 내부 서버로 전달하며, 서버 응답을 프록시를 통해 클라이언트로 반환함. | **서버를 대리**하여 외부 클라이언트의 요청을 맞이함. |
  
  - Forward Proxy 동작 과정
    - | 단계 | 머메이드 노드 | 상세 설명 |
      | :---: | :--- | :--- |
      | **1. 요청 캡처** | `A[클라이언트 요청 캡처]` | 클라이언트가 외부 인터넷 서버에 직접 요청하지 않고, 자신이 설정한 프록시 서버로 요청을 보냄. |
      | **2. 요청 대리 수행** | `B[프록시 서버에서 요청 대리 수행]` | 프록시 서버가 요청을 수신하여 실제 목적지 서버로 전달하며, 이때 클라이언트의 실제 IP 주소를 은닉함. |
      | **3. 응답 수신** | `C[목적지 서버로 요청 전달]` | 목적지 인터넷 서버가 처리하여 반환한 응답 패킷을 중계 장비인 프록시 서버가 먼저 수신함. |
      | **4. 응답 전달** | `D[서버 응답 수신]` 및 `E[프록시 서버로 응답 전달]` | 프록시 서버가 수신한 서버의 응답 데이터를 클라이언트 방향으로 안전하게 전달하며 중계 역할을 완료함. |
      | **5. 클라이언트 반환** | `F[클라이언트에게 응답 반환]` | 클라이언트가 프록시로부터 최종 응답을 전달받아 제한되거나 차단되었던 콘텐츠에 정상 접근함. |
  - Forward Proxy 핵심 기능
    - | 기능 | 상세 설명 |
      | :--- | :--- |
      | **👤 IP 주소 변경** | 클라이언트의 모든 아웃바운드 요청이 프록시 서버를 거치므로, 목적지 서버가 프록시의 IP만 보게 만들어 클라이언트의 실제 IP 주소를 숨김. |
      | **🔓 인터넷 검열 우회** | 지리적 제한(Geo-blocking)이나 내부 방화벽 정책으로 인해 차단된 외부 콘텐츠, 웹사이트 및 서비스에 정상적으로 접근할 수 있도록 지원함. |
      | **💾 캐싱 (Caching)** | 자주 요청되는 파일이나 데이터를 프록시 서버가 내부에 미리 저장해두어, 동일 요청 시 서버까지 가지 않고 즉시 반환하여 요청 속도를 높이고 대역폭을 절약함. |
      | **⚡ 트래픽 최적화** | 내부에서 외부로 나가는 네트워크 트래픽의 흐름을 효율적으로 조율하고 최적화하여 인프라 전반의 부하를 줄이고 성능을 향상시킴. |
  
  - Reverse Proxy 동작 과정
    - | 단계 | 머메이드 노드 | 상세 설명 |
      | :---: | :--- | :--- |
      | **1. 요청 캡처** | `A[클라이언트 요청 캡처]` | 외부 클라이언트의 요청이 최전방에 위치한 리버스 프록시 서버로 도달하며, 이 과정에서 실제 백엔드 웹/API 서버의 IP 주소는 외부로부터 철저히 은닉됨. |
      | **2. 규칙 검사** | `B[리버스 프록시에서 규칙 검사]` | 수신된 요청의 HTTP 헤더 정보, 들어오는 트래픽 패턴, 출발지 IP 주소 등을 정밀 분석하여 사전에 정의된 방화벽 및 인프라 보안 정책 위반 여부를 검사함. |
      | **3. 요청 처리** | `C{정상 요청인가?}` | 스크리닝을 통해 검증된 정상적인 요청은 내부 타겟 서버로 안전하게 포워딩(전달)하고, 비정상적이거나 유해한 요청은 내부망으로 들어오기 전에 즉시 격리 차단함. |
      | **4. 응답 전달** | `D[서버로 요청 전달]` 및 `E[서버 응답 수신]` | 백엔드 WAS 서버가 안전하게 처리하여 반환한 응답 데이터를 리버스 프록시가 수신한 뒤, 다시 클라이언트 방향으로 역전송하며 중계 세션을 완료함. |
      | **5. 차단 및 기록** | `H[차단 및 로그 기록]` | 정책 유해 요구나 보안 규칙 위반 트래픽은 원천 차단 조치하고, 해당 세션의 상세 내역을 감사 로그(Log)에 기록하여 향후 침입 탐지 및 네트워크 보안 관리에 활용함. |
  - Reverse Proxy 핵심 기능
    - | 기능 | 상세 설명 |
      | :--- | :--- |
      | **🔒 보안 강화** | 실제 운영 서버의 고유 IP 주소를 외부 네트워크 공간에 노출하지 않으며, 무차별적인 DDoS 공격, 웹 취약점 악성 인젝션 요청을 프록시 단에서 1차로 필터링하여 서버 인프라를 보호함. |
      | **🔑 SSL 암호화** | 외 외부 클라이언트와의 HTTPS 보안 통신(SSL/TLS 핸드셰이크 및 데이터 암복호화) 연산을 리버스 프록시가 전담(SSL Offloading)하여, 내부 WAS 서버의 CPU 연산 자원 부하를 획기적으로 경감시킴. |
      | **⚖️ 로드 밸런싱** | 단일 진입점으로 들어오는 대규모 사용자 트래픽을 뒷단에 배치된 다수의 애플리케이션 인프라 서버로 골고루 분산 전송함으로써, 특정 장비의 과부하를 막고 전체 서비스 가용성을 극대화함. |
      | **💾 캐싱 (Caching)** | 이미지, CSS, JS 파일이나 자주 요청되는 정적/동적 API 응답 데이터를 프록시 메모리에 임시 저장하여, 본 서버까지 세션을 연결하지 않고 즉시 응답을 반환함으로써 백엔드 부하를 줄이고 응답 속도를 가속화함. |

  | **핵심 역할** | **클라이언트의 대리인**으로 외부 서버와 통신하며, 사용자의 익명성 확보와 콘텐츠 우회를 중점적으로 처리함. | **서버의 대리인**으로 외부 클라이언트의 요청을 관리하며, 내부 인프라 보안 강화와 트래픽 최적화에 중점을 둠. |
  | **주요 사용 목적** | • 인터넷 검열 및 지리적 접근 제한 우회<br>• 클라이언트 식별 정보 숨김 (익명 브라우징) | • 백엔드 서버 보호 및 웹 취약점 공격 차단<br>• 부하 분산(로드 밸런싱) 및 서비스 고가용성 확보 |
  | **동작 방식** | 클라이언트가 프록시 서버를 목적지로 지정하여 요청을 보내면, 프록시가 클라이언트 IP를 숨기고 대신 인터넷 서버와 통신함. | 클라이언트는 리버스 프록시를 실제 서버로 알고 요청을 보내며, 프록시가 내부 보안 규칙 적용 후 백엔드 서버로 트래픽을 중계함. |
  | **대표적인 예시** | • 사내 유해 사이트 차단 및 웹 필터링<br>• VPN 서비스를 통한 IP 및 국가 우회 접속 | • 대규모 트래픽 분산을 위한 Nginx / AWS ALB 도입<br>• Cloudflare를 통한 DDoS 방어 및 HTTPS(SSL) 인증서 통합 처리 |

    | **🔒 데이터 암호화** | • 사용자의 장치에서 전송되는 모든 데이터를 암호화하여 외부의 도청이나 해킹 시도를 원천 차단함.<br>• **송신:** VPN 클라이언트가 데이터를 암호화하여 VPN 서버로 보내면, 서버가 이를 복호화하여 인터넷 목적지로 전송함.<br>• **수신:** 인터넷에서 올 때는 VPN 서버가 데이터를 다시 암호화하여 클라이언트로 보내고, 클라이언트가 이를 최종 복호화함. |
    | **🎭 가상 IP 주소 할당** | • VPN 연결 시 사용자의 실제 IP 주소 대신 VPN 서버 소속의 가상 IP 주소를 강제로 부여함.<br>• 이로 인해 사용자의 실제 물리적 위치와 식별 정보가 숨겨지며, 웹사이트들은 사용자가 VPN 서버가 위치한 국가(예: 한국에서 미국 서버 접속 시 미국으로 인식)에 있는 것으로 판단함. |
    | **🛣️ VPN 터널링** | • 터널링 프로토콜을 사용해 공용 인터넷망 위에 외부에서 접근할 수 없는 독립된 '전용 보안 경로(터널)'를 개설함.<br>• 데이터를 안전한 패킷 단위로 쪼갠 뒤 암호화된 터널로 통과시키며, 일반 네트워크 트래픽과 철저히 격리함.<br>• *주요 프로토콜: OpenVPN, L2TP/IPsec, WireGuard 등* |
    | **📡 VPN 서버 역할** | • 클라이언트가 인터넷에 직접 다이렉트로 연결되지 않도록 최전방에서 모든 통신을 중계하는 게이트웨이 역할을 수행함.<br>• 이 중계 과정 덕분에 사용자와 인터넷 서비스 간의 데이터는 항상 암호화 스크리닝 상태를 유지하며, 철저한 네트워크 익명성이 완성됨. |
  

#### 주제 2: NAT
- NAT: 사설 IP 주소를 공인 IP 주소로 변환하여 인터넷 통신을 가능하게 하는 기술
  - | 도입 이유 | 상세 설명 |
    | :--- | :--- |
    | **💎 IPv4 주소 절약** | 한정된 공인(Public) IP 주소 자원을 고갈시키지 않고, 하나의 공인 IP를 수많은 내부 사설(Private) IP 장치들이 공유하여 인터넷에 접속할 수 있도록 주소 효율성을 극대화함. |
    | **🛡️ 보안 강화 (인프라 은닉)** | 내부에서 사용하는 실제 사설 IP 주소를 외부에 절대 노출하지 않음. 외부 인터넷 공간에서는 라우터의 대표 공인 IP만 보이기 때문에, 내부 네트워크 구조를 숨기고 외부의 직접적인 침입 공격을 1차로 차단함. |
    | **⚙️ 유연한 네트워크 관리** | 외부 공인 IP 변경과 무관하게 내부 네트워크 관리자가 사설 IP 대역(예: `10.0.0.0/8`, `192.168.0.0/16`)을 독립적이고 자유롭게 설계할 수 있어 인프라 변경 및 확장 관리가 매우 유연해짐. |
  
- Symmetric NAT: 동일한 내부 IP와 포트를 사용해도 외부 대상에 따라 서로 다른 매핑된 IP와 포트를 생성하며, 비대칭적 통신을 제한하는 네트워크 주소 변환 방식
  - 매핑된 정보를 NAT 테이블에 저장하며, 저장된 매핑 정보는 동일한 목적지와의 재전송에만 사용됩니다.
  - 외부에서 NAT 장치를 통해 내부로 접근하려면 NAT가 생성한 정확한 매핑 정보(외부 IP와 포트)가 필요하며, 이를 모를 경우 접근이 제한됩니다.
  - | 특징 | 상세 설명 |
    | :--- | :--- |
    | **🔄 매핑 독립성** | 내부 네트워크의 출발지 IP와 포트가 완전히 동일하더라도, 연결하고자 하는 **외부 목적지(IP/Port)가 다르면 매핑되는 외부 공인 IP와 포트가 각각 고유하게 새로 지정**됨. 목적지별로 철저히 독립적인 NAT 매핑 테이블을 생성하고 관리함. |
    | **🛡️ 보안 강화** | 대칭형 NAT 테이블에 미리 기록된 정확한 매핑 정보(출발지-목적지 쌍)가 일치하지 않으면 외부에서 내부망으로의 임의 접근이 원천적으로 불가능함. NAT 유형 중 **가장 강력한 인프라 보안성**을 제공함. |
    | **⚠️ P2P 연결 제약** | 목적지가 바뀔 때마다 공인 포트가 계속 변경되는 비대칭적 특성 때문에, 장치 간 직접 통신하는 P2P(Peer-to-Peer) 연결 수립이 매우 까다로움. 실시간 통신 기술인 **WebRTC 환경 등에서는 STUN 서버만으로 우회가 어려워 TURN(릴레이) 서버 활용이 필수적**임. |
    | **📊 리소스 사용량 증가** | 동일한 내부 호스트가 여러 외부 서버와 통신할 때 목적지 수만큼 NAT 테이블 레코드가 기하급수적으로 늘어남. 이로 인해 라우터나 게이트웨이 장비의 **메모리(NAT 테이블 크기) 및 세션 리소스 관리 능력이 중요**하게 작용함. |

- Cone NAT: 특정 내부 IP와 포트에 대한 NAT 매핑이 고정되어, 특정 조건에 따라 외부 IP에서 해당 매핑에 접근할 수 있는 NAT 유형
  - Full Cone NAT: 어떤 외부 IP나 포트에서든 매핑된 외부 IP와 포트를 통해 내부 네트워크의 해당 클라이언트로 패킷을 전송할 수 있습니다.
  - Restricted Cone NAT: 내부 클라이언트가 아웃바운드 요청을 보낸 외부 IP에만 접근을 허용합니다.
    - 송신 데이터를 보낸 외부 목적지와만 통신이 가능하며, 포트 번호는 신경 쓰지 않습니다.
  - Port Restricted Cone NAT: 외부 IP와 포트 번호까지 매칭 조건으로 설정하여, 동일한 IP라 하더라도 포트 번호가 다르면 접근 불가합니다.
  - | NAT 유형 | 🔒 접근 조건 | 🛡️ 보안 수준 | 🎯 사용 사례 |
    | :---: | :--- | :---: | :--- |
    | **Full Cone NAT** | 내부에서 한 번이라도 외부로 연결을 생성하여 NAT 테이블에 매핑 정보가 등록되면, **외부의 어떤 IP와 포트에서든** 해당 공인 IP/포트를 통해 내부 호스트로 접근이 가능함. | **낮음** | P2P 멀티플레이어 게임, 실시간 양방향 통신 |
    | **Restricted Cone NAT** | NAT 테이블에 매핑 정보가 존재하고, 내부 호스트가 **먼저 패킷을 보낸 적이 있는 '특정 외부 IP 주소'**에서 들어오는 요청만 접근을 허용함 (포트는 달라도 됨). | **중간** | 제한적인 P2P 연결 환경, 화상 통화 서비스 |
    | **Port Restricted Cone NAT** | NAT 테이블에 매핑 정보가 존재하고, 내부 호스트가 **먼저 패킷을 보낸 적이 있는 '정확한 외부 IP 주소와 포트 번호'**가 완전히 일치하는 요청만 접근을 허용함. | **높음** | 일반적인 Cone NAT 중 가장 높은 보안이 요구되는 환경 |

#### 주제 3: TCP/IP Model, CIDR, 서브넷 마스크
- TCP/IP Model: 인터넷에서 컴퓨터 간 통신을 위한 표준 프로토콜 스택
  - | 계층 번호 | 계층명 (Layer) | 🎯 핵심 역할 및 인터페이스 대상 | 🛠️ 주요 프로토콜 및 기술 |
    | :---: | :--- | :--- | :--- |
    | **4** | 응용 계층 (Application) | 사용자 및 응용 프로그램의 서비스 요청 처리 | HTTP, FTP, SMTP, DNS, SSH |
    | **3** | 전송 계층 (Transport) | 프로세스 간 신뢰성 있는 데이터 전송 및 흐름 제어 | TCP, UDP |
    | **2** | 인터넷 계층 (Internet) | 논리 주소(IP) 기반 경로 지정 및 패킷 라우팅 | IP, ICMP, ARP |
    | **1** | 네트워크 인터페이스 (Network Interface) | 물리 매체를 통한 인접 장치 간 프레임 전송 (MAC 주소 활용) | 이더넷 (Ethernet), Wi-Fi |
  - 캡슐화(Encapsulation): 네트워크에서 데이터가 주고받을 때, 데이터가 각 계층을 거치면서 각 계층에서 패킷에 헤더가 추가
    - 응용 계층: 데이터 → 전송 계층: 세그먼트/데이터그램 → 인터넷 계층: 패킷 → 네트워크 인터페이스 계층: 프레임
  - 역캡슐화(Decapsulation): 데이터가 네트워크 인터페이스 계층에서 도착한 후, 각 계층에서 추가된 헤더를 제거하면서 응용 계층으로 전달
  - | 과정 | 🔄 정의 및 메커니즘 | 🎯 데이터 흐름 방향 |
    | :---: | :--- | :---: |
    | **Encapsulation**<br>(캡슐화) | 상위 계층의 데이터가 하위 계층으로 내려오면서, 각 계층의 프로토콜 제어 정보가 담긴 **헤더(Header)를 추가하며 데이터를 순차적으로 감싸는 과정**입니다. | **송신 측**<br>(응용 계층 ➔ 물리 계층) |
    | **Decapsulation**<br>(역캡슐화) | 수신한 데이터가 상위 계층으로 올라가면서, 각 계층의 프로토콜 **헤더를 순차적으로 제거 및 분석하여 최종적으로 원래의 원본 데이터를 복구하는 과정**입니다. | **수신 측**<br>(물리 계층 ➔ 응용 계층) |

- CIDR: 라우팅할 때 트래픽 경로를 명확하게 지정하기 위해 네트워크 범위를 구분하는 주소 표준
  - IP 주소 공간을 효율적으로 사용하고, 라우팅 테이블의 크기를 줄이기 위해 사용
  - 클래스 기반 IP 주소 체계
    - 이 방식에서는 서브넷 마스크가 클래스별로 미리 정해져 있으며, 네트워크 크기를 환경에 맞게 세분화하거나 유연하게 조정할 수 없다는 한계가 있습니다.
    - 클래스 기반 주소체계는 프리픽스가 주소에 의해 자동으로 고정되는 방식이고, CIDR은 프리픽스를 관리자가 설계하는 방식
  - 옥텟: IP 주소를 구성하는 네 부분 중 하나로, 각 부분은 8비트로 이루어져 있어 0부터 255까지의 값을 가질 수 있습니다.
  - 라우팅 테이블: 데이터를 어느 경로로 보낼지 결정하는 데 사용하는 표
  - | 항목 | 🔢 네트워크 데이터 및 할당 구조 |
    | :--- | :--- |
    | **IP 주소 및 접두사** | `192.168.1.0/24` (총 32비트) |
    | **네트워크 영역 (Network ID)** | **앞의 24비트** (`192.168.1.`) ➔ 서브넷 마스크 `255.255.255.0`에 의해 고정되는 영역 |
    | **호스트 영역 (Host ID)** | **나머지 8비트** (`.0`) ➔ 고유한 장치(호스트)들에 주소를 유연하게 할당할 수 있는 영역 |
  - 호스트 수 = 2^(호스트 비트 수) - 2
    - 여기서 2를 빼는 이유는 네트워크 주소와 브로드캐스트 주소를 제외하기 때문입니다.
- Subnet Mask: IP 주소에서 네트워크 영역과 호스트 영역을 구분하기 위해 사용되는 32비트 숫자 혹은 값
  - IP 네트워크를 여러 개의 작은 서브넷으로 분할하여, 네트워크 주소를  관리하기 위해 사용됨
  - 큰 네트워크를 여러 서브넷으로 나누면, 각 서브넷이 독립적으로 운영되며, 불필요한 트래픽이 다른 서브넷으로 확산되는 것을 방지할 수 있다.
  - 서브넷 마스크에서 1로 설정된 비트는 네트워크 부분을, 0으로 설정된 비트는 호스트 부분을 나타냅니다.


### 오늘의 회고
- 평소 계산법이 헷갈렸던 서브넷 마스크와 CIDR의 핵심 메커니즘을 학습했다. 비트 AND 연산을 통해 네트워크 ID와 호스트 ID가 분리되는 과정을 이해하는 계기가 되었다.
- 용어만 접해봤던 NAT의 동작 원리와 도입 필요성을 파악했다. IP 주소 절약 및 내부 인프라 은닉을 통한 보안 강화 이점을 배운 만큼, 향후 백엔드 인프라 아키텍처 설계 시 NAT를 적용해 보면 좋을 거 같다.
