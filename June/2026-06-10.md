### 새로 배운 내용
#### 주제 1: 공유자원, 임계영역
- 공유자원: 여러 사용자나 프로세스, 스레드가 동시에 접근하거나 사용하는 시스템 내의 자원을 의미
  - 임계 영역은 공유 자원을 사용하려는 프로그램 내부의 코드 중에서도 충돌이 발생할 가능성이 있는 부분
  - 리소스 낭비를 방지하고 메모리 사용 효율성을 극대화하기 위해
  - 1. 데이터 무결성 유지
  - 2. 경합 조건(Race Condition) 방지
- 임계영역: 공유 자원에 접근하는 프로그램 코드의 일부분

#### 주제 2: 동기화(Synchronization)
- 동기화: 동기화는 여러 작업(스레드 또는 프로세스)이 공유 자원을 사용할 때 발생할 수 있는 충돌이나 데이터 무결성 문제를 방지하고, 작업의 일관성을 보장하기 위한 기술
  - 데이터 무결성 손실, 데이터 경합, 데드락 등의 문제를 제대로 이해하여 안전한 소프트웨어를 설계하기 위해서
- Mutual Exclusion (상호 배제)
  - 임계 영역에는 반드시 하나의 프로세스만 진입하도록 보장
- Progress (진행)
  - 경쟁 프로세스가 없을 때, 즉시 실행이 가능해야 함
- Bounded Waiting (유한한 대기)
  - 대기 중인 프로세스가 영구적으로 차단되지 않도록 함

#### 주제 3: 락 (Lock)
- 락: 하나의 스레드나 프로세스가 자원을 점유할 경우 다른 스레드/프로세스가 해당 자원에 접근하지 못하도록 제어하는 기법
  - 데이터 무결성 손실, 데이터 경합, 데드락 등의 문제를 제대로 이해하여 공유 자원의 데이터 무결성을 보호하기 위해서
- Thread 간의 배타적 접근 보장: 한 Thread가 락을 점유하면, 다른 Thread는 해당 락이 해제될 때까지 공유 자원에 접근할 수 없습니다. 이를 통해 데이터의 동시 수정으로 인한 충돌을 방지하며, 동기화를 보장하여 자원의 안전한 사용을 가능하게 합니다.
- 락의 종류
  - 스핀락
    - 한 Thread가 임계 영역을 점유하고 있을 때, 다른 Thread가 락이 해제되기를 기다리며 "계속해서 반복적으로 락 상태를 확인하는" 방식의 락
    - 스핀락(Spinlock)의 장점
    - | 항목 | 설명 |
      | :--- | :--- |
      | **빠른 락 점유 해제** | 락을 기다리면서 대기 상태로 전환하지 않고 반복적으로 확인하므로, 락이 빠르게 해제될 경우 즉시 점유가 가능합니다. |
      | **컨텍스트 스위칭 없음** | 락 대기 중 컨텍스트 스위칭(스레드 스케줄링)이 발생하지 않으므로, 락이 짧은 시간 내에 해제될 경우 오버헤드*가 적습니다. |
      | **간단한 구현** | 스핀락은 구현이 비교적 간단하며, 하드웨어나 운영체제의 지원이 필요 없는 경우도 많습니다. |
    - 오버헤드(Overhead): 시스템의 효율성을 저하시키는 원인 중 하나로, 특정 작업을 수행하기 위해 추가적으로 필요한 리소스를 가리킵니다.
    
    - 스핀락의 단점
    - | 항목 | 설명 |
      | :--- | :--- |
      | **CPU 사용률 증가** | 락이 해제될 때까지 루프를 돌며 반복 확인을 하기 때문에 CPU 자원을 계속 소비하며, CPU 사용률이 급격히 증가할 수 있습니다. |
      | **비효율적인 대기** | 락 해제가 오래 걸릴 경우 바쁜 대기(Busy-waiting)*로 인한 비효율이 발생하며, 다른 프로세스/스레드의 CPU 자원 사용을 방해할 수 있습니다. |
      | **단일 CPU 환경 부적합** | 단일 CPU(싱글 코어) 환경에서는 락을 점유한 스레드와 대기 중인 스레드가 동시에 실행될 수 없기 때문에 바쁜 대기 자체가 무의미하고 비효율적입니다. |
    - 바쁜 대기(Busy-waiting): 특정 조건이 충족될 때까지 반복적으로 상태를 확인하며 아무 작업도 하지 않고 CPU를 사용하는 방식을 의미합니다.
  
  - 낙관적 락 (Optimistic Lock)
    - 데이터 충돌이 드물다는 가정하에 락 없이 작업을 수행하고, 충돌이 발생하면 롤백을 통해 해결하는 방식
    - 낙관적 락의 장점
    - | 항목 | 설명 |
      | :--- | :--- |
      | **데이터 경합 없는 환경에서 효율적** | 실제로 락을 걸지 않으므로, 트랜잭션 충돌이 거의 발생하지 않는 환경에서는 동시성 제어에 따른 성능 저하가 거의 없습니다. |
      | **낮은 오버헤드** | 데이터를 수정하기 전까지는 별도의 락을 획득하지 않고 작업을 수행하므로, 초기 락 관리에 드는 비용(오버헤드)이 최소화됩니다. |
      | **병렬 처리 강화** | 여러 스레드가 동시에 공유 자원에 접근하여 읽고 쓸 수 있으므로, 경합이 적은 경우 시스템 전체의 병렬 처리 성능이 극대화됩니다. |

    - 낙관적 락의 단점
    - | 항목 | 설명 |
      | :--- | :--- |
      | **롤백 비용 발생** | 커밋 시점에 데이터 충돌이 감지되면 지금까지 진행한 변경 사항을 모두 취소(Rollback)하고 처음부터 다시 시도해야 하므로, 이에 따른 자원 소모가 발생합니다. |
      | **충돌 시 성능 저하** | 데이터 경합이 빈번하게 발생하는 환경(High Contention)에서는 재시도와 롤백이 반복되면서 오히려 시스템 성능이 급격히 떨어질 수 있습니다. |
      | **복잡한 구현** | 애플리케이션 레벨에서 버전(Version) 충돌을 직접 감지하고, 실패 시의 재시도(Retry)나 예외 처리 메커니즘을 직접 구현해야 하므로 설계가 비교적 복잡합니다. |
  
  - Mutex(뮤텍스)
    - 락의 소유권과 해제 권한을 특정 스레드에 부여하는 것
    - 뮤텍스의 장점
    - | 항목 | 설명 |
      | :--- | :--- |
      | **데이터 보호** | 한 번에 하나의 스레드만 공유 자원을 사용하도록 엄격하게 제한하여, 멀티스레드 환경에서도 데이터의 무결성을 완벽하게 보장합니다. |
      | **직관적인 동작** | 스레드 간 자원 보호와 동기화의 목적이 명확하며, 개발자가 예측하기 쉬운 안전한 방식으로 동작하므로 동기화 문제가 발생할 가능성을 줄입니다. |
      | **범용성** | 운영체제나 언어 차원에서 기본적으로 널리 제공되는 표준 내장 기능이며, 복잡한 설계 없이 대부분의 동기화 문제에 가장 쉽게 적용할 수 있습니다. |

    - 뮤텍스의 단점
    - | 항목 | 설명 |
      | :--- | :--- |
      | **컨텍스트 스위칭 오버헤드** | 다른 스레드가 락을 쥐고 있으면 대기 중인 스레드는 블로킹(Sleep) 상태로 전환됩니다. 이후 락이 풀려 다시 깨어날 때 **컨텍스트 스위칭(Context Switching)**이 발생하므로 오버헤드가 큽니다. |
      | **데드락(Deadlock) 위험** | 특정 스레드가 예외 발생 등으로 락을 해제하지 못하거나, 여러 스레드가 서로 다른 락을 교차하여 요청할 경우 시스템 전체가 멈추는 **교착 상태(데드락)**가 발생할 수 있습니다. |
      | **병렬 처리 제한** | 공유 자원에 접근하려는 스레드가 많더라도 무조건 한 번에 하나의 스레드만 진입할 수 있으므로, 경합이 심할수록 시스템 전체의 병렬 처리 성능이 제한됩니다. |

- 뮤텍스와 조건 변수(Condition Variable)
  - 조건 변수(Condition Variable): 스레드가 특정 조건이 충족될 때까지 대기하거나, 다른 스레드가 신호(Signal)를 보내 대기 중인 스레드를 깨워 실행을 재개하도록 하는 동기화 메커니즘
  - 조건 변수는 일반적으로 뮤텍스 락(Mutex Lock)과 함께 동작
- 리드-라이트 락 (Read-Write Lock): 다중 스레드 환경에서 읽기(Reader) 작업과 쓰기(Writer) 작업을 구분하여 락을 관리하는 동기화 메커니즘
  - 리드-라이트 락 장점
  - | 항목 | 설명 |
    | :--- | :--- |
    | **높은 동시성** | 공유 자원에 대해 다수의 Reader가 동시에 접근하여 읽을 수 있으므로, 읽기(Read) 중심의 작업 환경에서 동시성 성능을 크게 향상시킵니다. |
    | **데이터 무결성 보장** | 데이터를 수정하는 Writer는 자원을 완전히 독점(Exclusive)하여 작업을 수행하므로, 멀티스레드 환경에서도 데이터의 일관성과 무결성을 완벽하게 보장합니다. |
    | **효율적인 리소스 활용** | 읽기 작업의 비중이 압도적으로 높고 쓰기 작업은 간헐적으로 발생하는 실무 환경에서 CPU와 메모리 자원을 가장 효율적으로 활용할 수 있는 동기화 방식입니다. |

  - 리드-라이트 락 단점
  - | 항목 | 설명 |
    | :--- | :--- |
    | **Writer 기아 현상** | 새로운 Reader가 끊임없이 연속적으로 들어와 자원을 점유할 경우, 쓰기 작업을 수행해야 하는 Writer가 락을 획득하지 못하고 무한정 대기하는 **기아 상태(Starvation)**가 발생할 수 있습니다. |
    | **복잡한 구현** | 내부적으로 Reader의 수(Read Count)를 카운팅하고, Reader 락과 Writer 락의 상태 및 우선순위를 분리하여 관리해야 하므로 단순한 뮤텍스보다 내부 로직과 구현이 복잡합니다. |
    | **데드락 가능성** | Reader 락을 보유한 스레드가 내방하여 다시 Writer 락을 요청하거나, Reader와 Writer 간의 잘못된 락 요청 순서 및 교차가 발생할 경우 **교착 상태(데드락)**로 이어질 위험이 존재합니다. |
