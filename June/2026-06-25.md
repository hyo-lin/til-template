- ### 아키텍처 동작 메커니즘 비교: Serverless vs Server 기반

요청(Request) 발생 시 인프라 자원이 할당되고 연산(Compute)이 수행되는 라이프사이클의 근본적인 차이점입니다.

### 1. 인프라 구조별 흐름 비교

#### Serverless (Vercel / AWS Lambda)
* **요청 (Request):** 사용자가 웹사이트 접속이나 API 호출을 통해 요청을 보냅니다.
* **실행 환경 생성:** 상시 가동되는 서버가 존재하지 않으며, 요청이 들어오는 순간 이를 처리하기 위한 독립적인 함수 실행 환경이 즉시 프로비저닝됩니다.
* **처리 (Compute):** Lambda나 Vercel Functions가 로직을 수행합니다. 연산 작업이 완료되면 할당되었던 실행 환경은 즉시 소멸(Dispose)됩니다.
* **응답 (Response):** 처리된 결과를 클라이언트에게 반환합니다.

#### Server 기반 (AWS EC2)
* **요청 (Request):** 사용자가 인프라 내에 항시 구동 중인 EC2 인스턴스로 요청을 보냅니다.
* **처리 (Compute):** EC2는 24시간 프로세스가 프로세서 메모리에 상주하며 대기하는 구조이므로, 들어오는 요청을 지연(Cold Start) 없이 즉시 연산 처리합니다.
* **응답 (Response):** 처리 결과를 클라이언트에게 반환합니다.

### 2. 인프라 특징 한눈에 비교하기

| 비교 항목 | Serverless (AWS Lambda / Vercel) | Server 기반 (AWS EC2) |
| :--- | :--- | :--- |
| **인프라 상태** | 요청 시점에만 동적으로 생성 후 소멸 | 24시간 항상 구동 및 대기 상태 유지 |
| **초기 요청 지연** | 인프라가 처음 켜질 때 지연(Cold Start) 가능성 존재 | 항상 켜져 있으므로 즉시 처리 가능 |
| **자원 효율성** | 유휴 자원으로 인한 낭비가 전혀 없음 | 트래픽이 없어도 고정 자원이 계속 소모됨 |
| **적합한 워크로드** | 비동기 이벤트 처리, 파일 업로드 트리거, 배치 작업 | 대규모 트래픽이 상시 유지되는 코어 API 서버 |


- ### ⚡ AWS Lambda (Serverless) 아키텍처 및 실행 메커니즘

### 1. AWS Lambda 함수 실행 라이프사이클 (Lifecycle)

사용자의 요청이나 시스템 이벤트가 발생했을 때, 람다가 내부적으로 격리된 인프라 환경을 동적으로 구축하고 소멸시키는 4단계 과정입니다.

#### [1] 이벤트 발생 (Trigger)
* Amazon S3 파일 업로드, API Gateway 호출 등 미리 정의된 AWS 서비스의 이벤트가 발생하여 람다 함수를 트리거합니다.

#### [2] 실행 환경 준비 (Execution Environment)
* 코드를 연산할 컴퓨팅 자원을 할당하기 위해 격리된 실행 공간(Execution Environment)을 즉시 프로비저닝합니다.
* 이 공간에는 사용자가 설정한 메모리 및 CPU 자원, Runtime 환경, 함수 소스 코드, 환경 변수, `/tmp` 임시 저장소가 포함됩니다.

#### [3] 초기화 단계 (Init Phase)
* 함수 코드 및 Lambda Layer를 다운로드하고 런타임을 초기화합니다.
* **Java 생성자나 전역 변수 등 람다 핸들러(Handler) 메서드 외부에 작성된 정적 초기화 코드**들이 이 단계에서 최초 1회 실행됩니다.

#### [4] 호출 단계 (Invoke Phase)
* 인프라 준비가 완료되면 실제 비즈니스 로직이 담긴 핸들러 메서드(`handleRequest`)를 호출하여 이벤트를 처리합니다.
* 처리가 완료된 후 람다는 자원을 즉시 반납하지 않고, 향후 연속적인 요청에 대응하기 위해 특정 대기 시간 동안 실행 환경을 유지합니다.

### 2. Cold Start vs Warm Start 메커니즘 비교

서버리스 인프라 환경에서 발생하는 초기 지연 현상과 자원 재사용에 대한 동작 특징입니다.

| 비교 항목 | Cold Start (콜드 스타트) | Warm Start (웜 스타트) |
| :--- | :--- | :--- |
| **인프라 상태** | **새로운 실행 환경을 동적으로 생성**하는 단계 | **기존에 생성되어 대기 중인 실행 환경을 재사용**하는 단계 |
| **동작 흐름** | 인프라 프로비저닝 및 Init 단계를 모두 거침 | Init 단계를 건너뛰고 즉시 Invoke 단계로 진입 |
| **응답 속도** | 환경 구축 및 초기화 시간이 추가되어 **상대적으로 지연됨** | 자원이 이미 메모리에 상주하여 **신속한 응답 속도를 보장** |
| **발생 시점** | 오랜 시간 요청이 없었거나, 급격한 트래픽 증가 시 | 최근에 동일한 함수가 실행된 이력이 존재할 시 |
| **최적화 전략** | 주기적인 가짜 헬스체크 요청을 보내는 **Warming-Up 기법** 적용 | 별도의 오버헤드 없이 최적의 연산 속도 유지 |

### 3. 본 프로젝트에서의 AWS Lambda 실무 활용 시나리오

#### [1] 미디어 파일 업로드 비동기 후처리
* 유저가 S3 버킷에 대용량 이미지를 업로드하는 시점에 S3 트리거 이벤트를 수신합니다.
* 백엔드(EC2) 서버의 자원을 소모하지 않고, 독립된 람다 환경 내에서 프로필 사진 크기를 줄이는 **이미지 리사이징(Resizing)** 및 용량을 압축하는 **WebP 포맷 변환** 작업을 완전 비동기로 처리합니다.

#### [2] 정기 예약 작업 (Batch Process)
* 24시간 가동되는 서버를 배치 전용으로 두지 않고, **매일 새벽 특정 시간**에 유휴 임시 데이터를 일괄 삭제하거나 **매주 월요일** 통계 리포트를 자동 생성하는 정기 스케줄러 로직을 실행하는 데 활용하여 고정 인프라 비용을 절감합니다.

#### [3] 무거운 비동기 이벤트 처리 (Decoupling)
* 유저가 주문이나 핵심 요청을 보냈을 때 메인 API 서버는 가벼운 DB 데이터만 적재하고 클라이언트에게 즉시 응답을 반환합니다.
* 이후 메시지 큐(SQS 등)에 적재된 이벤트를 람다가 수신하여 **이메일/슬랙 알림 발송, 외부 API 연동, 통계 데이터 집계** 등 무거운 후속 비동기 작업을 메인 서버와 분리하여 처리합니다.

### 4. 아키텍처 설계 시 주의사항: 무상태성 (Stateless)

* AWS Lambda는 이벤트 처리가 완료되고 일정 시간이 지나면 자원을 시스템에 완전히 반납합니다.
* 실행 환경이 운 좋게 재사용되어 전역 변수나 `/tmp` 임시 폴더에 저장된 데이터가 일시적으로 유지될 수는 있으나, 이 자원은 **언제든지 예고 없이 휘발(Dispose)**될 수 있습니다.
* 따라서 장기적으로 유지되어야 하는 비즈니스 상태 값이나 영속 데이터는 람다 내부 메모리에 저장하지 않고, 반드시 **외부 저장소(RDS, DynamoDB, S3 등)와 연동하여 관리**하도록 아키텍처를 설계했습니다.

| **서버리스 아키텍처와의 통합** | AWS Lambda와 완벽하게 연동되어 HTTP 요청을 람다 이벤트로 변환하고 비즈니스 로직을 실행하는 서버리스 환경을 구축합니다. | 상시 구동 서버 없이도 트래픽에 따라 인프라가 유연하게 자동 확장(Auto Scaling)되며 고도의 비용 효율성을 달성합니다. |
| **자동 확장성과 고가용성** | AWS가 관리하는 풀 매니지드(Managed) 서비스로서 높은 트래픽 부하가 발생해도 자동으로 성능을 확장하고 복구합니다. | 별도의 로드 밸런서 설계나 서버 모니터링 없이도 인프라의 안정성과 서비스 신뢰성을 최상으로 유지합니다. |

#### 주제 3: CloudTrail, CloudWatch
- CloudTrail: AWS 계정에서 발생하는 모든 API 호출과 콘솔 활동을 자동으로 기록하고 추적하는 서비스
  - 보안 감사, 컴플라이언스, 문제 해결을 위해 AWS 계정의 활동을 추적하고 분석하기 위해 사용됨
- ### AWS CloudTrail 도입 이유 및 핵심 특징
| 도입 이유 | 상세 설명 | 실무적 의의 및 기대 효과 |
| :--- | :--- | :--- |
| **보안 감사 및 위협 대응** | AWS 계정 내에서 수행된 모든 자원 변경 작업을 추적하여 누가, 언제, 어떤 작업을 했는지 명확히 확인하고 의심스러운 활동을 감지합니다. | 루트 계정 도용이나 비정상적인 리소스 생성 등의 보안 사고가 발생했을 때 최초 침투 경로와 행위를 역추적하는 강력한 감사 가시성을 제공합니다. |
| **규정 준수 (컴플라이언스)** | 금융, 헬스케어 등 엄격한 정보보호 규제가 요구되는 산업군에서 필수적인 인프라 조작 및 API 호출 로그 보관 규정을 충족합니다. | 데이터와 인프라의 모든 변경 이력을 위변조 없이 안전하게 보관하여 규제 기관의 감사 요구사항을 완벽하게 증명합니다. |
| **문제 해결 및 운영 개선** | 시스템 장애나 인프라 구성 오류 발생 시, 에러가 터지기 직전에 일어난 AWS 자원 변경 사항을 파악하여 원인을 분석합니다. | "누가 보안 그룹 설정을 바꿨는지", "어떤 인스턴스가 갑자기 삭제되었는지" 등을 실시간 기록으로 파악하여 장애 복구 속도(MTTR)를 단축시킵니다. |
| **운영 투명성 및 변경 관리** | 인프라 환경 내의 모든 리소스 생성, 수정, 삭제 활동을 투명하게 기록하여 잘못 구성된 아키텍처를 빠르게 식별합니다. | 인프라가 코드로 관리(IaC)되거나 다수의 작업자가 동시에 시스템을 제어할 때 전체적인 휴먼 에러를 방지하고 운영 환경을 최적화합니다. |

- ### Amazon CloudWatch 도입 이유 및 특징
| 도입 이유 | 상세 설명 | 실무적 의의 및 기대 효과 |
| :--- | :--- | :--- |
| **리소스 성능 모니터링 및 최적화** | AWS 인프라 자원의 성능 데이터를 실시간 수집하여 CPU 사용률, 디스크 I/O, 네트워크 트래픽 등의 메트릭을 상시 감시합니다. | 성능 저하 징후나 리소스 고갈 문제를 조기에 감지하여 시스템 다운타임을 선제적으로 방어합니다. |
| **문제 감지 및 자동화된 대응** | 사용자 정의 경고(Alarm)를 설정하여 임계값 초과 시 알림을 전송하거나, 인프라 자체를 동적으로 제어하는 트리거를 당깁니다. | 예를 들어 CPU 사용률 초과 시 자동으로 Auto Scaling 그룹을 작동시켜 EC2 인스턴스를 추가하는 등 무인 장애 복구 체계를 완성합니다. |
| **중앙화된 로그 관리 및 분석** | 분산된 여러 EC2 인스턴스의 애플리케이션 로그와 시스템 로그를 CloudWatch Logs로 중앙 수집하여 통합 관리합니다. | 서버가 스케일인(Scale-in)으로 삭제되더라도 로그를 영구 보존하며, 텍스트 검색 및 분석을 통해 에러의 원인을 신속하게 파악합니다. |
| **데이터 시각화 및 통합 뷰 제공** | 여러 AWS 리소스의 메트릭과 로그 데이터를 커스텀 대시보드(Dashboard) 한곳에 모아 시각화합니다. | 전체 인프라 아키텍처의 가동 현황과 서비스 상태를 한눈에 모니터링할 수 있는 관측 가시성을 확보하여 운영 효율을 높입니다. |
| **비용 관리 및 최적화** | 리소스 사용량 추이를 정밀하게 모니터링하여 인프라 낭비 요소를 식별하고 오버 프로비저닝을 방지합니다. | 유휴 자원을 축소하거나 적절한 스펙(Right-sizing)으로 변경할 수 있는 정량적 지표를 제공하여 인프라 비용 절감에 기여합니다. |

- ### 🔍 옵저빌리티(Observability)의 3대 핵심 요소 (3 Pillars of Observability)

| 핵심 데이터 유형 | ❓ 엔지니어링 핵심 질문 | 📝 주요 데이터 및 대표 실무 예시 |
| :--- | :--- | :--- |
| **Metrics (메트릭)** | 시스템의 **현재 상태**가 어떠한가? | - 시스템 자원 및 가동 현황 데이터<br>- 예: CPU 사용률, 메모리 점유율, 초당 요청 수(RPS), API 응답 시간, 에러율(%) |
| **Logs (로그)** | 시스템 내부에 **어떤 일**이 발생했는가? | - 특정 시점에 발생한 이벤트의 상세 텍스트 기록<br>- 예: Exception 스택 트레이스, 서버 에러 메시지, 사용자 인증 요청 로그 |
