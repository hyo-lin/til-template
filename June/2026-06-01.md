### 새로 배운 내용
#### 주제 1: ORM, JPA
- ORM: 자바의 객체와 데이터베이스 테이블을 자동으로 연결하고 변환해, 객체 지향 코드로 데이터를 조작할 수 있게 해주는 기술
  - 객체지향과 관계형 데이터베이스 간의 간극을 줄여, 설계의 일관성과 코드의 생산성을 높이기 위해서
  - 객체는 상속, 다형성 같은 개념을 자연스럽게 다루지만, 데이터베이스는 이런 개념을 직접적으로 지원하지 않음
- JPA: 자바 객체와 관계형 데이터베이스를 매핑하고, 객체 단위로 데이터를 저장조회할 수 있게 해주는 표준 ORM 인터페이스
  - JDBC를 직접 사용하지 않고도 객체를 데이터베이스에 저장하고 불러올 수 있도록 돕는 중간 계층 역할
  - 1차 캐시: JPA가 특정 식별자를 가진 엔티티 인스턴스(객체)를 잠시 보관하는 임시 메모리 저장소
  - Hibernate: JPA 표준 명세의 대표적인 구현체로, 풍부한 기능과 활발한 커뮤니티를 갖춘 오픈소스 ORM 프레임워크
- JPA 표준 자체가 Hibernate를 기반으로 만들어져 호환성과 안정성이 높음
- JDBC: 자바 애플리케이션과 데이터베이스를 연결해주는 표준 API
  - 자바 코드에서 데이터베이스에 접속하고, SQL을 실행하며, 결과를 받아오기 위해 반드시 거쳐야 하는 통로 역할

#### 주제 2: 엔티티, 영속성 컨텍스트
- 엔티티 규칙
  - 기본 생성자는 반드시 존재해야 하며, 매개변수가 없는 형태로 `public`이나 `protected`로 선언되어야 합니다.
  - 또한 클래스의 형태에도 제한이 있어서 `final` 클래스, `enum`, `interface`, 내부 클래스는 엔티티로 지정할 수 없습니다.
  - 저장되는 필드 역시 `final`로 선언할 수 없습니다.
- 기본 키 생성 전략: 엔티티의 ID 값을 자동으로 만들기 위해 숫자를 직접 넣을지, DB 시퀀스를 사용할지, 자동 증가 컬럼을 쓸지 등을 지정하는 방식
  - TABLE 전략: 별도의 키 전용 테이블을 두고 시퀀스 동작을 흉내 내는 방식
  - SEQUENCE 전략: 데이터베이스에 존재하는 시퀀스 오브젝트를 이용해 기본 키 값을 생성하는 방식
  - IDENTIFY 전략: 데이터베이스의 자동 증가 컬럼을 사용하여 기본 키를 생성
  - AUTO 전략: JPA가 데이터베이스 방언을 기준으로 적절한 키 생성 방식을 자동 매핑해 주는 방법
  - 결론적으로 MySQL 환경에서는 AUTO 전략과 IDENTITY 전략이 동일하게 동작(AUTO_INCREMENT)하지만, 다른 DB로 변경하면 동작 방식이 달라짐
- 전략마다 키가 생성되는 시점이 다르고 이것이 JPA의 동작에 직접 영향을 줌
- @Transient: 해당 필드를 데이터베이스 컬럼으로 매핑하지 않도록 지정하는 어노테이션
  - @Transient가 선언된 필드는 JPA 영속성 컨텍스트에서 관리되지 않으며, 엔티티 저장 시 데이터베이스에 기록되지 않고 조회 시에도 로드되지 않음

- 영속성 컨텍스트: JPA가 엔티티 객체를 관리하며, 동일 트랜잭션 내에서 변경 사항을 추적하고 자동으로 데이터베이스와 동기화하는 메모리 상의 저장소
- EntityManager: 엔티티의 저장, 수정, 삭제, 조회 같은 작업을 담당하며, 내부적으로 영속성 컨텍스트를 생성하고 제어

- ###  영속성 컨텍스트의 핵심 기능 및 메커니즘
| 기능 | 설명 | 동작 시점 | 효과 및 유의사항 |
| :---: | :--- | :--- | :--- |
| **1차 캐시** | 영속성 컨텍스트 내부에 존재하는 엔티티 저장소로, PK를 키로 하여 엔티티 인스턴스를 보관합니다. | 엔티티를 조회할 때 먼저 캐시에서 탐색하고, 없을 경우에만 DB를 조회한 뒤 캐시에 저장합니다. 동일 트랜잭션 내에서는 같은 엔티티를 재사용합니다. | • DB 접근 횟수를 줄여 성능을 높여 줍니다.<br>• **주의:** 트랜잭션 범위를 벗어나면 캐시는 초기화되므로 전역 캐시로 오해하면 안 됩니다. |
| **쓰기 지연<br>(Write-Behind)** | INSERT, UPDATE, DELETE SQL을 즉시 실행하지 않고 내부 큐에 모아 둡니다. | 트랜잭션 커밋 직전 플러시(Flush) 단계에서 모아둔 SQL을 한 번에 실행합니다. | • 네트워크 왕복 횟수를 줄여 처리 효율이 높아집니다.<br>• **주의:** `IDENTITY` 전략(ex: MySQL AUTO_INCREMENT)처럼 DB에 넣어야만 PK를 즉시 확보할 수 있는 경우에는 `save()` 호출 시 INSERT가 바로 실행됩니다. |
| **변경 감지<br>(Dirty Checking)** | 로딩 시점의 엔티티 상태를 스냅샷으로 저장해 두고, 현재 값과 비교하여 변경 여부를 판별합니다. | 커밋 시점의 플러시(Flush) 단계에서 변경된 필드를 찾아 필요한 UPDATE SQL을 자동으로 생성합니다. | • 개발자가 직접 `update()` 메서드를 호출하지 않아도 엔티티 값만 바꾸면 DB에 반영됩니다.<br>• **주의:** 예기치 않은 대량 변경을 막으려면 트랜잭션 범위와 수정 위치를 신중히 관리해야 합니다. |

- ### 엔티티의 생명주기 (Entity Lifecycle)

| 상태 | 설명 | 주요 메서드 및 유발 시점 | 효과 및 특징 |
| :---: | :--- | :--- | :--- |
| **비영속<br>(New / Transient)** | 영속성 컨텍스트 및 데이터베이스와 전혀 관계가 없는 순수한 객체 상태입니다. | • `new` 연산자로 엔티티 객체를 막 생성한 단계 | • 영속성 컨텍스트의 관리(1차 캐시, 변경 감지 등)를 받지 못합니다. |
| **영속<br>(Managed)** | 엔티티가 영속성 컨텍스트에 등록되어 그 통제 하에 관리되는 상태입니다. | • `em.persist(entity)` 호출<br>• `repository.save(entity)` 호출<br>• DB 조회를 통해 가져온 엔티티 | • 영속성 컨텍스트가 제공하는 모든 기능(1차 캐시, 쓰기 지연 등)이 작동합니다.<br>• 트랜잭션 커밋 시점에 DB에 반영됩니다. |
| **준영속<br>(Detached)** | 한 번 영속 상태였던 엔티티가 영속성 컨텍스트에서 분리되어 관리를 받지 못하는 상태입니다. | • `em.detach(entity)` (특정 엔티티 분리)<br>• `em.clear()` (컨텍스트 통째로 초기화)<br>• `em.close()` (컨텍스트 종료) | • 영속 상태의 혜택을 받지 못하지만, 이미 한 번 DB에 다녀왔기 때문에 **식별자(PK)를 반드시 가지고 있다**는 특징이 있습니다. |
| **삭제<br>(Removed)** | 엔티티를 영속성 컨텍스트와 데이터베이스에서 모두 삭제하기로 마킹된 상태입니다. | • `em.remove(entity)` 호출<br>• `repository.delete(entity)` 호출 | • 트랜잭션 커밋(플러시) 시점에 데이터베이스에서 실제 `DELETE` SQL이 실행되며 데이터가 날아갑니다. |

#### 주제 3: 연관관계 매핑, Proxy
- 연관관계 매핑: 엔티티 객체 간의 관계를 설정하여, 객체지향적으로 연결된 데이터 구조를 정의하고 관리할 수 있도록 해주는 매핑 구조
  - 연관관계 매핑을 활용하면 SQL 중심 코드 대신 객체지향적인 코드를 유지할 수 있고, 관계 데이터의 탐색·조회·수정을 더 직관적으로 처리
- Proxy: JPA에서 지연 로딩을 사용할 때 실제 엔티티 대신 먼저 생성되어, 데이터가 필요한 순간에 실제 조회를 지연시키는 가짜 객체
  - 연관된 엔티티를 실제로 사용할 때까지 조회를 미뤄, 초기 쿼리 수를 줄이고 성능을 최적화하기 위해서

- JPA N+1 문제와 로딩 전략 (Fetching Strategy)

- 1. EAGER (즉시 로딩) vs LAZY (지연 로딩)

| 로딩 전략 | 메커니즘                                                                    | 실무 적용 원칙 및 유의사항 |
| :---: |:------------------------------------------------------------------------| :--- |
| **LAZY<br>(지연 로딩)** | 부모 엔티티 조회 시 연관 객체는 가짜 객체인 프록시(Proxy)로 대체하고, 실제 데이터가 호출되는 시점에 쿼리를 실행합니다. | • **모든 연관관계의 기본 가드레일 (무조건 사용)**<br>• 불필요한 DB 조회를 차단하여 네트워크 및 메모리 오버헤드를 물리적으로 방지합니다. |
| **EAGER<br>(즉시 로딩)** | 부모 엔티티를 조회하는 순간, 연관된 자식 엔티티까지 **무조건, 즉시** JOIN 또는 추가 쿼리를 통해 다 긁어옵니다.    | • **실무 사용 절대 금지 (기본값 변경 필수)**<br>• `findById` 같은 단일 조회 시에는 최적화되나, JPQL 리스트 조회 시 **예측 불가능한 N+1 쿼리 폭탄을 난사**하는 주범이 됩니다. |

- 2. N+1 문제의 근본적인 원인 (Why)

1. JPQL의 독립적 작동 방식: JPQL은 연관관계 페칭 전략(`EAGER`/`LAZY`)을 고려하지 않고, 오직 작성된 엔티티 스펙만을 바라본 채 최초 명시된 생쿼리(`SELECT * FROM member`)를 먼저 생성하여 DB에 던집니다. (최초 쿼리 1번 실행)
2. `EAGER` 상태일 때: 최초 쿼리 결과로 N개의 데이터가 반환되면, JPA는 연관 객체를 '즉시' 다 채우기 위해 각 데이터의 식별자를 들고 DB를 N번 다시 찌릅니다.
   `LAZY` 상태일 때: 최초 조회 시점은 안전하지만, 비즈니스 로직 내에서 루프를 돌며 연관 객체의 실물 데이터에 접근(`member.getTeam().getName()`)하는 순간 프록시가 초기화되면서 결국 DB를 N번 추가로 찌르게 됩니다.
3. 결론: 쿼리 1번으로 끝날 작업이 결과 데이터 수(N)만큼 추가 실행되어 총 `1 + N`번의 네트워크 타격을 주며 시스템을 마비시킵니다.

- 3. 실무 해결 프로세스 (How)

- ① Fetch Join (페치 조인) 
- 적용: 일반적인 단일 타겟 조회 및 다대일(`@ManyToOne`) 리스트 조회 시 사용.
- 효과: JPQL에 `join fetch`를 명시하면 JPA 가드레일을 우회하여, 단 1번의 쿼리로 `JOIN`을 걸어 연관 자식 데이터까지 한방에 싹 영속성 컨텍스트에 채워옵니다.

- ② @BatchSize (배치 사이즈 조절)
- 적용: 일대다(`@OneToMany`) 컬렉션 관계를 **페이징 처리와 동시에 조회**해야 할 때 사용.
- 효과: `application.yml`에 전역 옵션을 설정하면, 자식 객체를 1개씩 짤짤이로 N번 조회하지 않고 설정한 크기만큼 **`IN` 쿼리**로 묶어서 대량으로 동시 조회합니다.
