| **🧩 분산 캐시<br>아키텍처 지원** | 다중 노드에 데이터를 분산 저장하고, **데이터 복제(Replication)와 샤딩(Sharding)**을 통해 높은 처리량과 내결함성을 제공합니다. | 데이터 유실 리스크를 최소화하고 scale-out 구조를 완벽하게 지원합니다. |

- Cache-Aside: 애플리케이션이 먼저 캐시를 조회하고, 캐시에 없을 때만 DB를 조회한 뒤 캐시에 저장하는 방식입니다.
- Cache hit: 캐시에 데이터가 있는 경우
- Cache miss: 캐시에 요청한 데이터가 없는 경우

- ### ⏱️ Redis TTL (Time To Live) 설계 및 캐시 만료 전략

### 1. TTL 개요
* **정의:** 캐시 데이터가 메모리에 자동으로 만료되어 삭제되기까지의 제한 시간입니다.
* **구체적 예시:**
  * **Key:** `post::1::likeCount`
  * **Value:** `10`
  * **TTL:** `300s` (300초 후 해당 캐시는 메모리에서 자동 소멸)

---

### 2. TTL 설정이 필수적인 이유 (Why we need TTL)

1. **제한적인 메모리 자원 관리 (Eviction 방지)**
  * 캐시는 RAM(인메모리) 자원을 사용하므로 저장 공간이 매우 제한적입니다. TTL이 없으면 쓰이지 않는 데이터가 메모리를 가득 채워, 정작 중요한 캐시가 밀려나거나 서버가 다운될 수 있습니다.
2. **데이터 정합성(Data Consistency) 보장**
  * 캐시 데이터는 원본 DB(RDBMS)의 복사본이므로 항상 최신 상태를 보장하지 않습니다. 만약 메인 비즈니스 로직(예: 좋아요 누르기/취소)에서 캐시를 함께 갱신하도록 설계했더라도, **중간에 트랜잭션이 실패**하거나 어드민(Admin) 페이지에서 직접 DB 데이터를 수정(예: 특정 게시글 상단 노출을 위한 좋아요 수 임의 조작)하는 경우 캐시와 DB의 데이터가 찢어지게 됩니다.
  * TTL은 이러한 예외 상황에서 **최소한 지정된 시간 뒤에는 무조건 최신 데이터로 동기화**되도록 보장하는 안전장치 역할을 합니다.

---

### 3. TTL 길이에 따른 트레이드 오프 (Trade-Off)

| 구분 | ⏱️ 너무 짧은 TTL (예: 10s) | ⏳ 너무 긴 TTL (예: 3600s) |
| :--- | :--- | :--- |
| **장점** | - **데이터 정합성이 매우 높음**<br>- 원본 DB 변경 사항이 빠르게 반영됨 | - **캐시 히트율(Cache Hit Rate) 극대화**<br>- RDBMS 부하를 획기적으로 낮춤 |
| **단점** | - **캐시 미스(Cache Miss) 빈번 발생**<br>- DB 조회가 잦아져 캐시 도입 효과 저하 | - **오래된 데이터(Stale Data) 장시간 노출**<br>- 유저 경험(UX)이 깨질 확률 증가 |


### 4. 데이터 성격에 따른 실무 TTL 수립 기준

TTL은 서비스의 비즈니스 로직과 데이터가 얼마나 자주 변하는지에 따라 유연하게 가져가야 합니다.

* **🔄 자주 바뀌는 데이터 (예: 좋아요 수, 실시간 크루 모집 현황)**
  * 👉 **짧은 TTL 권장** (또는 비즈니스 로직 단에서 Write 발생 시 캐시를 직접 삭제/갱신하는 전략 병행)
* **🔒 거의 바뀌지 않는 데이터 (예: 러닝 코스 고유 정보, 공지사항, 유저 프로필)**
  * 👉 **긴 TTL 권장** (하루~일주일 단위로 길게 잡아 캐시 효율 극대화)
* **🚨 즉시 최신 값이 강제되는 데이터 (예: 결제 정보, 비밀번호 변경)**
  * 👉 **TTL에만 의존 금지.** 데이터 변경 즉시 캐시를 강제로 삭제(`Evict`)하거나 동기화하는 로직 설계 필수.

- ## 🌐 Amazon ElastiCache 엔진 비교 및 고가용성 아키텍처 설계

### 1. ElastiCache 지원 엔진 및 특징
실무에서 캐시 저장소를 구축하면 단 하나의 목적으로만 쓰지 않고 **세션 스토어, 인기글 관리, 실시간 랭킹 등 다양한 비즈니스 목적을 동시에 수행**하게 됩니다. 따라서 단순 Key-Value 이상의 복잡한 요구사항을 해결할 수 있는 엔진을 선택해야 합니다.

| 엔진 (Engine) | 핵심 특징 | 대표 활용 사례 |
| :--- | :--- | :--- |
| **⚡ Valkey** | - 최신 Redis OSS(오픈소스) 기반 차세대 인메모리 저장소<br>- 라이선스 제약 없는 완전한 오픈소스로 비용 효율성 극대화 | 캐시 고속화, 세션 관리, 실시간 랭킹, Pub/Sub |
| **🟥 Redis OSS** | - 다양한 자료구조(Data Structures)와 확장 기능 제공<br>- 고가용성 및 복제 기능이 매우 성숙함 | 대규모 캐시, 분산 락(Distributed Lock), 실시간 채팅 |
| **🟦 Memcached** | - 단순하고 가벼운 고성능 분산 Key-Value 스토어<br>- 복잡한 기능 없이 데이터의 수평 확장성에만 집중 | 단순 조회 데이터 캐싱, 단순 K-V 스토어 |

---

### 2. Redis / Valkey가 제공하는 자료구조 
Memcached와 달리 Redis 계열은 다양한 자료구조를 지원하므로, 비즈니스 로직상 단순 키-값으로 해결되지 않는 복잡한 기능을 인메모리 단에서 효율적으로 처리할 수 있습니다.

* **📝 String:** 가장 기본적인 키-값 형태로 **로그인 세션(Session)**, **API rate limiter(처리량 제한)** 등에 사용
* **🗂️ Hash / List / Set:** 객체 구조화 데이터 저장 및 중복 없는 데이터 집합 관리
* **🏆 Sorted Set (ZSET):** 가중치(Score)를 기반으로 정렬된 상태를 유지하여 **인기 검색어**, **실시간 랭킹** 구현에 최적화
* **🔒 Distributed Lock (분산 락):** 동시성 제어가 필요한 비즈니스 로직 보호
* **📣 Pub/Sub & Stream:** 실시간 메시지 발행/구독 시스템 및 **실시간 채팅** 기능 구현

---

### 3. ElastiCache 고가용성(High Availability) 및 스케일링 구성

대규모 트래픽 환경에서 데이터 유실을 막고 안정적인 서비스를 제공하기 위해 ElastiCache는 3가지 핵심 고가용성 아키텍처를 지원합니다.

#### ① Replica (복제본) 구성
* **원리:** 쓰기 전용인 주 노드(Primary)의 데이터를 읽기 전용인 복제 노드(Replica)로 실시간 복제합니다.
* **목적:** 읽기 트래픽 분산(Read 오프로딩) 및 주 노드 장애 시 백업 역할을 수행합니다.

#### ② Multi-AZ (다중 가용구역 포지셔닝)
* **원리:** 주 노드와 복제 노드를 서로 다른 물리적 데이터 센터(AZ)에 분산 배치합니다.
* **목적:** 특정 가용구역(AZ) 전체에 장애가 발생하더라도, 정상적인 AZ의 Replica 노드가 자동으로 주 노드로 승격(Automatic Failover)되어 무중단 서비스를 유지합니다.

#### ③ Shard (샤딩을 통한 수평 확장)
* **원리:** 대용량 데이터를 하나의 서버에 다 넣지 않고, 특정 규칙(해시 슬롯)에 따라 데이터를 쪼개어 여러 노드(Shard)에 나누어 저장하는 분산 저장 방식입니다.
* **개념적 예시 (데이터 분산 메커니즘):**
  * 데이터 Key의 숫자가 `1의 배수` 구조 형태 ➔ **Shard 1**에 저장
  * 데이터 Key의 숫자가 `2의 배수` 구조 형태 ➔ **Shard 2**에 저장
  * 데이터 Key의 숫자가 `3의 배수` 구조 형태 ➔ **Shard 3**에 저장
* **목적:** 단일 노드의 메모리 한계를 극복(Scale-out)하고, 데이터가 기하급수적으로 늘어나도 데이터 처리 속도(지연 시간)를 일정하게 유지합니다.

- ### 🚨 캐시 아키텍처 운영 시 주의해야 할 3대 문제점과 해결 전략

캐시는 뛰어난 성능 향상을 제공하지만, 원본 데이터 저장소가 아니며 자원이 한정되어 있기 때문에 반드시 장애 복구 정책과 만료 전략을 함께 설계해야 합니다.

### 1. 캐시 데이터의 휘발성과 높은 의존도 위험 (Cache Dependency)
* **문제점:** Redis/Valkey 같은 인메모리 데이터 스토어는 데이터를 RAM에 저장하므로, 서버 전원이 꺼지거나 장애가 발생하면 데이터가 순간적으로 완전히 증발합니다. 간혹 비즈니스 로직상 캐시에서만 데이터를 조회하도록 **캐시 의존도가 너무 높게 설계된 시스템**은 캐시 다운 시 서비스 전체가 마비됩니다.
* **해결 전략 (복구 정책):** * 캐시 히트 실패(`Cache Miss`)가 발생하더라도 시스템이 무너지지 않도록, `finally` 구문이나 대체 로직을 통해 **언제나 최종 영구 저장소(RDBMS)를 조회하여 데이터를 안전하게 고속 복구(Cache Aside 패턴)하는 방어적 로직**을 필수로 구현해야 합니다.

---

### 2. 캐시 스탬피드 현상 (Cache Stampede)
* **문제점:** 예를 들어 매일 자정에 10,000개의 게시글이 "인기글"로 지정되어 동일한 TTL(예: 86,400초)로 캐시에 한꺼번에 등록된다고 가정해 봅시다.
  * 정확히 하루 뒤 동일한 1초 사이에 **10,000개의 캐시 키가 동시에 만료(Miss)되는 현상**이 발생합니다.
  * 이때 순간적으로 수많은 유저 요청이 원본 RDBMS로 한꺼번에 폭증(`DB Thundering Herd`)하면서 DB 서버 응답 지연 및 타임아웃(Timeout)이 발생하고, 서비스 전체의 안정성이 도미노처럼 무너지게 됩니다.

* **실무 해결 전략 (TTL 지터 기법):**
  * 캐시 키를 생성할 때 고정된 TTL을 주지 않고, **만료 시간에 의도적으로 임의의 난수(Random 값)를 더해 만료 시점을 분산**시킵니다.
  * **설정 예시:** * `기본 TTL:` 300초
    * `실제 적용 TTL:` 300초 + (0 ~ 30초 사이의 랜덤 값)
  * 이를 통해 만료 시점이 부드럽게 분산되므로 대규모 트래픽 환경에서도 DB 폭발 현상을 완벽히 방지할 수 있습니다.

### 3. 메모리 고갈 현상 (Out of Memory)
* **문제점:** 캐시는 RAM이라는 비싸고 한정된 자원을 사용합니다. 데이터가 지속적으로 쌓여 캐시 메모리가 가득 차게 되면, 더 이상 새로운 캐시 키를 생성할 수 없어 **새로운 쓰기(Write) 요청이 지속적으로 실패**하는 치명적인 에러가 발생합니다.
* **해결 전략 (Eviction 정책 설정):**
  * 메모리가 부족해질 경우 캐시 엔지니어링 단에서 시스템 사정에 맞는 **Eviction(메모리 확보를 위한 키 제거) 정책**을 무조건 수립해야 합니다.
  * **주요 Eviction 정책:**
    * **LRU (Least Recently Used):** 가장 오랫동안 참조되지 않은 키를 우선 삭제
    * **LFU (Least Frequently Used):** 참조 횟수가 가장 적은(가장 덜 사용된) 키를 우선 삭제
    * **TTL 기반 무작위 삭제:** 만료 시간이 설정된 키 중 임의로 삭제하여 가용 메모리를 상시 확보

#### 주제 2: ELB (Elastic Load Balancer)
- ELB: 여러 대의 서버로 들어오는 네트워크 트래픽을 자동으로 분산해 주는 서비스
- ### ⚖️ AWS ELB & Auto Scaling 도입 이유 및 기대 효과

대규모 트래픽 환경에서 단일 EC2 서버 구조의 한계를 극복하고, 서비스 무중단과 인프라 효율성을 극대화하기 위해 ELB(로드 밸런서)와 Auto Scaling 그룹을 연계한 고가용성 아키텍처를 구축했습니다.

| 도입 이유 | 상세 설명 | 실무적 의의 (성능, 보안 및 FinOps) |
| :--- | :--- | :--- |
| **🚦 트래픽 관리 및<br>부하 분산 (ELB)** | 대규모 사용자 요청을 여러 EC2 백엔드 인스턴스에 고르게 분산하여 특정 서버에 부하가 집중되는 현상을 방지합니다. | 서버 과부하로 인한 응답 지연을 막고 전체 애플리케이션 성능을 안정적으로 유지합니다. |
| **🛡️ 고가용성 및<br>자동 장애 조치** | 서버를 여러 가용 영역(Multi-AZ)에 분산 배포하고, 특정 서버나 AZ에 장애가 나면 **정상 서버로 트래픽을 자동 라우팅**합니다. | 단일 장애점(SPOF)을 제거하여 인프라 다운 타임과 서비스 중단을 최소화합니다. |
| **📈 확장성 및<br>비용 효율성** | 실시간 트래픽 증감에 맞춰 **EC2 인스턴스를 자동으로 추가(Scale-out)하거나 제거(Scale-in)**합니다. | 트래픽 피크 타임엔 가용성을 보장하고, 한산한 시간대엔 자원을 반납하여 운영 비용을 절감합니다. |
| **🔒 보안 강화 및<br>SSL 관리** | **SSL/TLS 인증서(HTTPS) 처리를 ELB단에서 중앙 집중식으로 수행(SSL Offloading)**하여 백엔드 부하를 줄이고, AWS WAF와 연동합니다. | 데이터 전송 구간의 보안을 강력하게 래핑하면서, 외부 공격으로부터 내부 서버망을 보호합니다. |
| **📊 모니터링 및<br>관리 용이성** | Amazon CloudWatch와 유기적으로 통합되어 실시간 트래픽 패턴, 성능 지표, 서버 헬스 체크(Health Check) 상태를 추적합니다. | 인프라 내의 장애 상황을 실시간으로 감지하고 신속하게 트래블슈팅할 수 있는 가시성을 확보합니다. |

- ### 🔄 Auto Scaling 그룹의 동적 스케일링(Dynamic Scaling) 동작 메커니즘

트래픽의 실시간 변화에 맞춰 인프라 자원을 유연하게 확장(Scale-out)하고 축소(Scale-in)하는 구체적인 시나리오입니다.

| 구분 | 📈 트래픽 증가 시 (Scale-out) | 📉 트래픽 감소 시 (Scale-in) |
| :--- | :--- | :--- |
| **동작 원리** | 미리 설정한 메트릭 임계값(예: **CPU 사용률 > 70%**, **평균 응답시간 > 1초** 등)을 초과하면, Auto Scaling 그룹이 새로운 EC2 인스턴스를 즉시 자동 생성하고 ELB(로드 밸런서)의 타겟 그룹에 등록하여 추가 트래픽을 분산 처리합니다. | 트래픽이 빠져나가 설정된 임계값 이하로 메트릭(예: **CPU 사용률 < 30%**)이 떨어지면, Auto Scaling 그룹이 더 이상 필요하지 않은 유휴 EC2 인스턴스를 안전하게 종료하고 ELB에서 제거합니다. |
| **실무 예시<br>(Scenario)** | **마케팅 프로모션**이나 **실시간 이벤트(예: 퇴근 시간대 크루 모집 폭증)**로 인해 갑자기 유저 방문자가 급증하더라도, 서버가 알아서 증설되어 **서비스 다운 없는 안정성을 유지**합니다. | **심야 시간대**나 이벤트 종료 후 트래픽이 소강상태에 접어들면, 자원을 자동으로 축소하여 불필요하게 낭비되는 **EC2 인프라 운영 비용을 획기적으로 절감(FinOps)**합니다. |

- ### 🏗️ AWS ELB (Elastic Load Balancing) 핵심 컴포넌트 구조

| 컴포넌트 명 | 핵심 개념 (Concept) | 실무적 역할 및 예시 |
| :--- | :--- | :--- |
| **⚖️ ELB** | 여러 서버에 요청을 분산하는 AWS 로드 밸런서 서비스 | 서비스 전체의 트래픽을 앞단에서 받아 안정적으로 찢어주는 총괄 수문장입니다. |
| **🌐 ALB**<br>(Application) | HTTP/HTTPS 웹 트래픽 처리에 특화된 로드 밸런서 | OSI 7계층(Application Layer)을 이해하여 URL 경로(`~/api/v1/crews`)나 HTTP 헤더를 기준으로 라우팅을 수행합니다. |
| **👂 Listener** | ELB가 외부 요청을 받아들이기 위해 대기하는 포트/프로토콜 | 외부 사용자가 들어오는 문 구멍입니다. (예: `HTTPS / 443 포트`로 들어오는 요청을 감시하고 대기함) |
| **📜 Rule** | 리스너가 받은 요청을 어디로 던질지 결정하는 조건 규칙 | "만약 URL 경로가 `/api/*`로 시작하면 백엔드 타겟 그룹으로 보내고, 그 외에는 정적 웹 페이지로 보내라" 같은 분기 처리를 담당합니다. |
| **🎯 Target Group** | 실제 요청을 받아 처리하는 백엔드 서버 인스턴스들의 묶음 | 로드 밸런서가 분산 투자할 대상 리스트입니다. Auto Scaling 그룹과 연계되어 EC2 인스턴스들이 이 그룹 내에 자동으로 묶이게 됩니다. |
| **🏥 Health Check** | 정상 서버에게만 요청을 보내기 위한 주기적인 상태 확인 | 타겟 그룹 내의 서버들이 살아있는지 주기적으로 핑(`GET /health`)을 찔러보고, 죽은 서버(`Unhealthy`)가 발견되면 트래픽 할당 대상에서 즉시 제외하여 서비스 장애를 방지합니다. |


#### 주제 3: CloudFront
- CloudFront: 전 세계에 분산된 서버 네트워크(CDN, Content Delivery Network)를 통해 사용자에게 콘텐츠를 빠르고 안전하게 전달하는 서비스
  - 지리적으로 분산된 서버인 엣지 로케이션(Edge Location) 을 통해 사용자의 요청을 처리하여 콘텐츠 로딩 속도를 향상시키고, 전송 지연시간을 최소화
- 엣지 로케이션(Edge Location): AWS CloudFront가 콘텐츠를 캐시하고 사용자에게 더 빠르게 전달하기 위해 전 세계에 분산된 데이터 센터
- ### 🌐 Amazon CloudFront (CDN) 도입 이유 및 기대 효과

전 세계(및 전국)에 분산된 엣지 로케이션을 활용하여 정적/동적 콘텐츠의 전송 속도를 극대화하고, 원본 서버(Origin)의 부하를 획기적으로 줄이기 위해 CloudFront를 아키텍처 앞단에 배치했습니다.

| 도입 이유 | 상세 설명 | 실무적 의의 (성능, 보안 및 FinOps) |
| :--- | :--- | :--- |
| **⚡ 전송 속도 최적화** | 전 세계 및 전국 각지에 분산된 **엣지 로케이션(Edge Location)**을 통해 사용자와 가장 가까운 서버에서 콘텐츠를 캐싱하여 제공합니다. | 네트워크 지연 시간(Latency)을 최소화하고, 이미지 및 정적 자원의 다운로드 속도를 획기적으로 높입니다. |
| **📉 트래픽 관리 및<br>원본 서버 보호** | 대규모 트래픽 발생 시, 원본 서버(S3, EC2)로 요청이 직접 가지 않고 **엣지 서버가 캐시된 데이터를 대신 반환**합니다. | 원본 서버에 가해지는 트래픽 부하를 대폭 줄여 대규모 사용자가 몰려도 서버 다운 타임을 방지합니다. |
| **🛡️ 강력한 보안 기능<br>중앙 집중화** | 데이터 전송 전 구간에 **SSL/TLS 암호화(HTTPS)**를 적용하며, AWS WAF 및 Shield와 연동하여 디도스(DDoS) 공격을 방어합니다. | 보안 위협으로부터 콘텐츠와 유저 데이터를 안전하게 보호하는 강력한 에지 보안 계층을 형성합니다. |
| **🔌 AWS 서비스와의<br>유기적 통합성** | **Amazon S3(정적 이미지/파일 저장소)**, EC2, API Gateway 등과 손쉽게 통합되어 정적/동적 콘텐츠 배포에 최적화된 유연성을 제공합니다. | 인프라 구성의 복잡도를 낮추고, AWS 서비스 간의 데이터 전송 효율을 극대화합니다. |
| **💰 비용 효율성<br>(FinOps)** | S3에서 외부 인터넷으로 직접 데이터를 전송(Data Transfer Out)하는 것보다 **CloudFront를 거쳐 전송하는 비용이 훨씬 저렴**합니다. | 트래픽 규모가 커질수록 기하급수적으로 증가하는 대역폭 비용을 획기적으로 절감할 수 있습니다. |

- ### 🏗️ Amazon CloudFront 구성 요소 및 CDN 아키텍처

사용자(Viewer)의 요청이 어떤 컴포넌트를 거쳐 캐싱되고, 원본 서버(Origin)와 안전하게 통신하는지 보여주는 구조입니다.

| 구성 요소 명 | 핵심 역할 (Role) | 실무적 의미 및 예시 |
| :--- | :--- | :--- |
| **📱 Viewer** | CloudFront에 콘텐츠를 요청하는 최종 사용자 또는 웹 브라우저 | 서비스에 접속하여 러닝 코스 지도 이미지나 프로필 사진을 요청하는 클라이언트입니다. |
| **📍 Edge Location** | 사용자에게 가장 가까운 위치에서 캐시된 콘텐츠를 서빙하는 전 세계 분산 서버망 | 서울, 도쿄 등 각 지역 엣지에 이미지가 캐싱되어 있다면 원본 S3까지 가지 않고 이곳에서 **0.01초 만에 초고속 응답**을 보냅니다. |
| **📦 Distribution** | CloudFront의 가장 기본적인 **배포 설정 단위** | "특정 도메인(`cdn.running-crew.com`)으로 들어오는 트래픽은 어떤 S3 원본과 연결하고 어떤 캐시 정책을 쓸 것인가?"를 정의하는 총괄 컨테이너입니다. |
| **🛣️ Cache Behavior** | URL 경로 패턴에 따라 어떤 원본으로 요청을 보내고 어떻게 캐싱할지 결정하는 **라우팅 규칙** | 예를 들어, 이미지 경로인 `/images/*`는 24시간 동안 캐싱하고, 백엔드 API 경로인 `/api/*`는 캐싱 없이 즉시 원본 EC2로 토스하도록 설정할 수 있습니다. |
| **⏱️ Cache Policy** | 캐시의 고유 키(Cache Key) 조합과 **최대/최소 TTL(만료 시간)** 등을 세부 설정하는 정책 | 앞서 정리한 TTL 기법과 캐시 히트율을 극대화하기 위해 쿠키, 헤더, 쿼리 스트링의 캐싱 반영 여부를 이 정책에서 통제합니다. |
| **🗄️ Origin** | 캐싱되지 않은 원본 콘텐츠가 실제로 저장되어 있는 최종 목적지 데이터 백엔드 | 정적 파일이 저장된 **Amazon S3 버킷**이나, 동적 데이터를 처리하는 **ALB/EC2 인스턴스**가 원본에 해당합니다. |
| **🔒 OAC**<br>(Origin Access Control) | **외부 사용자가 S3 원본 버킷에 직접 우회 접근하는 것을 완벽히 차단**하고, 오직 CloudFront를 통해서만 접근하도록 제한하는 강력한 보안 기능 | S3 버킷을 퍼블릭으로 열지 않고 완전 프라이빗하게 잠근 뒤, CloudFront의 정당한 요청만 통과시키는 **인프라 보안의 핵심 수문장**입니다. |

- ### 🔀 인프라 라우팅 비교 및 협업 설계: CloudFront vs ALB

대규모 트래픽을 감당하는 인프라를 구축할 때, 정적 자원의 초고속 캐싱을 담당하는 **CloudFront(CDN)**와 동적 비즈니스 로직의 부하 분산을 담당하는 **ALB(로드 밸런서)**의 역할 분담을 명확히 하여 아키텍처를 설계했습니다.

| 비교 구분 | 🌐 Amazon CloudFront (CDN) | ⚖️ Application Load Balancer (ALB) |
| :--- | :--- | :--- |
| **🎯 핵심 목적** | **콘텐츠 캐싱** 및 글로벌 전송 속도 가속화 | 리전 내부의 **여러 서버로 요청 분산** (부하 분산) |
| **📍 주요 위치** | 사용자와 원본(Origin) 사이의 **글로벌 엣지 로케이션** | AWS 특정 **리전(Region) 내부**의 애플리케이션 앞단 |
| **📦 대표 대상** | 이미지, CSS, JS, 비디오 영상 등 **정적 자원(Static Assets)** | EC2 인스턴스, ECS 컨테이너, **동적 API 서버** |
| **⏱️ 캐싱(Caching)** | **가장 핵심이 되는 주 메인 기능** | 캐싱 기능 없음 (요청을 패스스루하는 역할) |
| **🏥 Health Check** | 원본(Origin) 서버 장애 시 대체 페이지 대응 가능 | 타겟 서버들의 생존 상태를 **주기적으로 확인하는 것이 핵심** |
| **🏗️ 대표 구조** | `CloudFront` ➔ `Amazon S3` (정적 배포 구조) | `ALB` ➔ `EC2 / ECS` (동적 API 구조) |
