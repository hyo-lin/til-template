### 새로 배운 내용
#### 주제 1: EFS, NFS, Mount
- EFS: AWS에서 제공하는 사용자가 스토리지를 직접 설정하거나 용량을 관리하지 않아도 자동으로 확장·축소되고 운영이 자동화된 네트워크 파일 시스템
  - 여러 EC2 인스턴스에서 동시에 액세스할 수 있는 파일 스토리지를 제공하기 위해 사용됨
  - ### 📁 AWS EFS(Elastic File System) 사용 이유 및 핵심 기능
    
| 사용 이유 | 설명 |
| :--- | :--- |
| **동시 액세스 및 데이터 공유** | **여러 Amazon EC2 인스턴스가 동시에 하나의 파일 시스템에 접근**할 수 있어, 분산 애플리케이션이나 컨테이너(ECS/EKS) 환경에서 공통 데이터를 쉽게 공유하고 협업할 수 있습니다. |
| **자동 확장 및 유연성** | 저장된 데이터 양에 따라 **용량이 자동으로 확장 및 축소**됩니다. 사전에 스토리지 크기를 예측하고 프로비저닝할 필요가 없어 비용 효율적이며 리소스 관리가 단순해집니다. |
| **고가용성 및 내구성 보장** | 생성 시 데이터를 **여러 가용 영역(AZ)에 걸쳐 자동으로 복제**하여 보관하므로, 특정 인프라 영역에 장애가 발생해도 데이터 손실 위험을 최소화하고 서비스를 지속할 수 있습니다. |
| **완전 관리형 서비스 (운영 부담 감소)** | AWS가 성능 최적화, 패치, 파일 시스템 유지보수, 백업 및 복구를 모두 알아서 처리하므로 엔지니어의 **인프라 설정 및 관리 부담이 크게 감소**합니다. |
| **강력한 보안 및 서비스 통합** | 데이터 전송 중(In-transit) 및 유휴 상태(At-rest) 암호화를 기본 지원하며, **AWS IAM 및 POSIX 권한 설정**을 통해 디렉토리/파일 수준까지 세밀한 접근 제어가 가능합니다. |

- NFS(Network File System): 네트워크상에서 파일을 공유하고 액세스할 수 있게 해주는 표준 프로토콜
- 마운트(Mount): 외부 저장소나 파일 시스템을 운영체제의 디렉토리 트리에 연결하여, 해당 파일 시스템을 로컬처럼 사용할 수 있게 만드는 과정
- ### 📦 AWS 핵심 스토리지 비교 (EFS vs EBS vs S3)

AWS 인프라를 구축할 때 데이터의 성격과 액세스 방식에 따라 적절한 스토리지를 선택하는 것이 중요합니다.

| 특징 | EFS (Elastic File System) | EBS (Elastic Block Store) | S3 (Simple Storage Service) |
| :--- | :--- | :--- | :--- |
| **스토리지 유형** | 📁 **파일 스토리지** (NAS 방식) | 🗄️ **블록 스토리지** (SSD/HDD 가상 디스크) | 🪣 **객체 스토리지** (웹 저장소) |
| **데이터 액세스** | **여러 EC2 인스턴스에서 동시 접근 가능**<br>*(HTTP 접근 불가)* | **단일 EC2 인스턴스에만 연결 가능**<br>*(1:1 매핑)* | **HTTP/HTTPS 프로토콜**을 통해 전 세계 어디서나 웹 액세스 가능 |
| **확장성** | 🟢 **자동 확장** (데이터 양에 따라 자동 조절) | 🟡 **수동 확장 필요** (볼륨 크기 변경 작업 필요) | 🟢 **무제한 확장 가능** (용량 제한 없음) |
| **비용 산정** | 💰 **사용한 만큼만** 청구 | 💰 **프로비저닝(생성)한 용량**에 따라 청구<br>*(EC2를 꺼두어도 계속 청구)* | 💰 **저장된 데이터 용량 및 API 요청 수**에 따라 청구 |
| **성능 특성** | 여러 인스턴스 간 파일 공유 최적화,<br>지연 시간이 다소 높을 수 있음 | **매우 낮은 지연 시간 및 고성능 IOPS** 제공 | 높은 내구성(99.999999999%) 및 데이터 가용성 제공 |
| **주요 사용 사례** | - 공유 파일 시스템<br>- 여러 웹 서버의 공통 미디어 디렉토리 | - 데이터베이스(RDS/커스텀 DB) 저장소<br>- OS 부팅 디스크 및 고성능 워크로드 | - 정적 웹사이트 호스팅<br>- 대규모 데이터 백업 및 로그 보관 |
| **핵심 장점** | 다중 인스턴스 간 완벽한 실시간 데이터 공유 | 고성능, 빠른 입출력 속도 | 저렴한 비용, 무제한 용량, 다양한 스토리지 클래스 |
| **핵심 단점** | EBS 대비 단일 IO 성능 및 지연 시간이 떨어짐 | 여러 EC2 인스턴스에서 동시에 공유 불가 | 파일 시스템 인터페이스 없음 (수정 시 객체 전체를 덮어써야 함) |

- ### ⚙️ AWS EFS 성능 모드 및 실무 적용 시 고려 사항

EFS는 강력한 공유 파일 시스템이지만, 비용이 상대적으로 비싸고 네트워크 기반으로 동작하기 때문에 **성능 최적화(FinOps)와 보안 설정**이 필수적입니다.

### 1. 성능 및 처리량 모드 최적화 (Performance & Throughput)

#### 📊 성능 모드 (Performance Mode)
기본적으로 **General Purpose**로 시작한 뒤, CloudWatch 지표를 모니터링하며 최적화하는 것을 권장합니다.

| 구분 | 특징 | 추천 상황 |
| :--- | :--- | :--- |
| **General Purpose** | **낮은 지연 시간(Latency)** 중심의 모드 (가장 대중적) | 일반 웹 서비스, CMS, 사용자 홈 디렉터리 등 **(기본 추천)** |
| **Max I/O** | 지연 시간은 약간 늘어나지만, **높은 병렬 처리** 중심의 모드 | 아주 많은 클라이언트가 동시에 접근하는 특수 대규모 워크로드 |

#### 📈 처리량 모드 (Throughput Mode)
| 모드 | 특징 및 추천 상황 |
| :--- | :--- |
| **Elastic** | 사용량에 따라 처리량을 **자동으로 조절**합니다. **(EFS 도입 초기 강력 추천)** |
| **Bursting** | 파일 시스템의 크기가 커질수록 처리량 한도와 버스트 크레딧이 같이 늘어나는 방식입니다. |
| **Provisioned** | 데이터 용량과 무관하게 **필요한 처리량(MiB/s)을 직접 지정**하여 비용을 지불합니다. |

### 2. 수명 주기 관리 (Lifecycle Management) & 비용 최적화

클라우드 환경에서는 "접근 속도가 빠를수록 비용이 비싸다"는 법칙이 적용됩니다. (`RAM` > `SSD` > `DISK`)
오랫동안 접근하지 않는 파일은 수명 주기 관리 설정을 통해 자동으로 저렴한 스토리지 티어(Infrequent Access, Archive)로 이동시켜 비용을 극적으로 절감해야 합니다.

- ### 🚨 실무 적용 시 필수 고려 사항 (FinOps & Security)

> [!WARNING]
> **1. EFS를 모든 파일 저장소로 남용하지 마세요 (FinOps)**
> EFS는 EBS나 S3에 비해 상대적으로 비용이 많이 비쌉니다. 무조건적인 사용은 피하고, **'여러 인스턴스 간의 공유 파일 시스템'이 꼭 필요한 크리티컬한 상황**에서만 제한적으로 선택해야 합니다.

> [!CAUTION]
> **2. 데이터베이스(DB) 디렉토리용으로 EFS를 절대 사용하지 마세요**
> EFS는 네트워크 기반 파일 시스템(NFS)입니다. 높은 IOPS와 극도의 디스크 응답 속도가 필요한 `MySQL`, `PostgreSQL` 등의 데이터베이스를 EFS 위에 올리면 심각한 성능 저하가 발생합니다. RDS나 EC2에 직접 DB를 구축할 때는 반드시 **고성능 블록 스토리지인 EBS를 사용**해야 합니다.

> [!DANGER]
> **3. NFS 포트(2049)를 인터넷에 절대 개방하지 마세요**
> EFS 통신에 사용되는 **NFS Port 2049**가 외부 인터넷(0.0.0.0/0)에 노출되면 심각한 보안 해킹 타깃이 됩니다. 반드시 VPC 내부 대역이나 특정 EC2 보안 그룹(Security Group)에서만 접근할 수 있도록 인바운드 규칙을 철저히 제한해야 합니다.

> [!TIP]
> **4. 철저한 백업(Backup) 아키텍처 설계는 필수입니다**
> EFS는 파일 시스템일 뿐이므로, 데이터 유실을 방지하려면 엔지니어가 직접 백업을 설계해야 합니다. AWS에서 제공하는 완전 관리형 **AWS Backup 정책**을 유기적으로 연동하여 정기적인 EFS 파일 시스템 백업 스냅샷을 생성하도록 구성하는 것이 안전합니다.


#### 주제 2: S3, Presigned URL
- S3: (일반적으로 이미지, 로그, 백업 등 파일성 데이터와 같은) 구조화되지 않은 대규모 데이터를 객체 단위로 저장하고, 인터넷을 통해 언제든지 안전하게 업로드·다운로드할 수 있는 확장 가능한 클라우드 객체 스토리지 서비스
  - 확장성, 내구성, 가용성이 뛰어난 스토리지 솔루션을 제공해 대규모 데이터를 경제적으로 저장하고, 쉽게 접근 및 관리할 수 있게 하기 위해서
- ### 🪣 AWS S3(Simple Storage Service)의 핵심 장점 및 특징

대용량 파일, 정적 에셋, 백업 데이터 등을 관리할 때 EC2 내부 스토리지(EBS) 대신 S3를 사용해야 하는 이유입니다.

| 장점 | 핵심 내용 |
| :--- | :--- |
| **확장성 (Scalability)** | S3는 **무제한의 저장 용량을 제공**하므로, 저장할 데이터의 크기나 양에 제한이 없습니다. 반면, EC2 인스턴스의 디스크(EBS) 용량은 제한적이며 용량 부족 시 볼륨 추가 및 리사이징 등 번거로운 사후 관리가 필요합니다. |
| **내구성 및 가용성** | 데이터를 단일 장비가 아닌 **최소 3개 이상의 가용 영역(AZ)에 자동으로 분산 복제**하여 보관합니다. 이를 통해 AWS 기준 **99.999999999% (11개의 9)의 극도로 높은 데이터 내구성**을 보장합니다. |
| **데이터 관리 기능** | 파일의 과거 이력을 보관하는 **버전 관리(Versioning)**, 오래된 파일을 저렴한 스토리지로 이관하는 **수명 주기 정책(Lifecycle Policy)**, 파일 업로드 시 이벤트를 트리거하는 **이벤트 알림** 등 강력한 내장 기능을 제공합니다. |
| **유기적인 서비스 통합성** | IAM을 통한 세밀한 접근 제어는 물론, Athena(데이터 분석), SageMaker(머신러닝), CloudFront(CDN), AWS Backup 등 **다양한 AWS 에코시스템과 완벽하게 연동**되어 하이브리드 아키텍처 구축이 용이합니다. |

- ### ⚖️ AWS EFS vs S3 핵심 비교 및 활용 기준

| 구분 | EFS (Elastic File System) | S3 (Simple Storage Service) |
| :--- | :--- | :--- |
| **저장 방식** | 📁 **파일 스토리지** (계층형 디렉토리 구조) | 🪣 **객체 스토리지** (플랫한 Key-Value 구조) |
| **접근 방식** | 리눅스 파일 시스템처럼 **직접 마운트(Mount)**하여 사용 | **API 기반 접근** (SDK, CLI, REST API, HTTP/HTTPS) |
| **리눅스 명령어** | `cd`, `touch`, `chmod`, `mkdir` 등 **기존 명령어 완벽 지원** | 리눅스 명령어 직접 사용 불가 (전용 CLI나 SDK 라이브러리 필요) |
| **다중 서버 동시 공유** | 🟢 **완벽 지원** (수천 대의 EC2가 동시에 마운트하여 실시간 공유) | 🟡 **제한적** (동시 접근은 가능하나 실시간 파일 시스템 동기화 방식이 아님) |
| **외부 브라우저 접근** | 🔴 **불가** (인터넷을 통한 직접적인 웹 다운로드 주소 제공 안 됨) | 🟢 **완벽 지원** (고유 URL, CloudFront CDN 연동, Presigned URL 제공) |
| **대표 용도** | - 여러 웹 서버의 공통 미디어/소스 공유 폴더<br>- 컨테이너(ECS/EKS)의 고정 공유 볼륨<br>- CMS(워드프레스 등) 데이터 저장소 | - 대용량 이미지, 동영상 파일 저장<br>- 데이터베이스 백업, 서비스 로그 적재<br>- 정적 웹사이트 호스팅 (HTML/CSS/JS) |

- ### 🔗 AWS S3 Presigned URL 개념 및 실무 적용 가이드

**Presigned URL**은 일정 시간 동안 특정 S3 버킷의 객체에 접근(업로드/다운로드)할 수 있도록 보안 서명이 포함된 임시 URL입니다. 백엔드 서버를 거치지 않고 클라이언트가 S3와 다이렉트로 통신하게 하여 서버의 부담을 획기적으로 줄여줍니다.

### 📊 Presigned URL의 장단점 및 특징

| 구분 | 주요 내용 및 특징 | 실무적 의의 (FinOps & 아키텍처) |
| :--- | :--- | :--- |
| **💡 장점** | **백엔드 서버의 리소스 절감**<br>대용량 파일 데이터를 백엔드가 직접 수신하지 않고 클라이언트가 S3로 바로 업로드합니다. | **EC2 네트워크 비용 절감:** 서버 트래픽(대역폭) 자원을 거의 쓰지 않으므로 인프라 비용이 매우 저렴해집니다. |
| | **세밀한 권한 제어**<br>업로드 가능한 임시 시간제한, 특정 파일 경로, 접근 권한을 백엔드에서 엄격하게 제한하여 발급합니다. | 안전한 임시 통행증 역할을 하여 버킷을 퍼블릭으로 열지 않고도 안전하게 파일을 주고받을 수 있습니다. |
| **⚠️ 단점** | **클라이언트 의존적 검증 (보안 리스크)**<br>백엔드가 중간에서 파일을 가로채 검증할 수 없으므로, 파일 크기나 확장자 체크 등을 클라이언트에 맡겨야 합니다. | **"Don't Trust Client"** 원칙에 위배될 수 있으며, 클라이언트가 보내는 데이터는 위변조에 취약합니다. |
| | **결과의 불확실성 (클라이언트 자원 분산)**<br>파일 압축이나 포맷 변환을 클라이언트 브라우저 환경에 맡기면, 기기 성능에 따라 결과물이 일정하지 않습니다. | 사용자가 형변환이나 압축 없이 아주 무거운 쌩(Raw) 파일을 그대로 올릴 리스크가 존재합니다. |


#### 주제 3: RDS, Read Replica, Multi-AZ
- RDS: 클라우드에서 관계형 데이터베이스를 손쉽게 생성·운영·확장할 수 있도록 제공하는 완전관리형 서비스
  - EC2에 MySQL을 직접 설치하고 운영할 때 발생하는 백업, 패치, 모니터링, 장애 대응 등의 관리 부담을 줄여주며, 자동 백업, 손쉬운 확장, 고가용성 구성 등을 통해 운영 안정성을 확보할 수 있어서
- ### 🗄️ AWS RDS(Relational Database Service) 도입 이유 및 핵심 장점

| 도입 이유 | 설명 | 실무적 의의 (운영 및 FinOps) |
| :--- | :--- | :--- |
| **관리의 간소화** | DB 설치, OS 패치, 소프트웨어 업데이트, **일일 자동 백업 및 복구(Point-in-Time)**까지 AWS가 자동으로 처리합니다. | 인프라 유지보수 및 DBA의 운영 공수를 획기적으로 줄여줍니다. |
| **유연한 확장성<br>(Scalability)** | 클릭 몇 번으로 CPU, 메모리, 스토리지를 스케일 업/아웃할 수 있으며, **읽기 복제본(Read Replica)**을 추가해 읽기 부하를 손쉽게 분산합니다. | 트래픽 급증 시 대규모 데이터 조회 쿼리 병목을 효율적으로 해결합니다. |
| **고가용성 & 내결함성** | **다중 가용 영역(Multi-AZ) 복제**를 지원하여, 주 가용 영역에 장애가 발생하면 대기 중인 동기화 복제본으로 **자동 장애 조치(Failover)**를 수행합니다. | 서비스 중단 시간(Downtime)을 최소화하여 시스템 가용성을 극대화합니다. |
| **강력한 보안 체계** | VPC 내부망 격리, **AWS KMS를 통한 저장 데이터 암호화**, SSL/TLS 통신 암호화, IAM 기반의 세밀한 접근 권한 제어를 제공합니다. | 외부 해킹 및 데이터 유출 리스크로부터 핵심 자산을 안전하게 보호합니다. |
| **비용 효율성** | 반복적인 인프라 관리 작업을 자동화하여 엔지니어의 시간 비용을 아끼고, 사용한 리소스 스펙에 맞춰 유연한 비용 책정이 가능합니다. | 장기적인 관점에서 수동 인프라 구축 대비 총소유비용(TCO)을 절감합니다. |
| **인프라 진입 장벽 완화** | 복잡한 샤딩, 장애 복구 메커니즘, 패치 등의 작업을 AWS가 대신 수행하므로, 깊은 인프라 전문 지식 없이도 안정적인 운영이 가능합니다. | 백엔드 개발자가 핵심 비즈니스 로직과 서비스 아키텍처에 더 집중할 수 있게 합니다. |

- 스냅샷: 데이터베이스의 특정 시점 상태를 저장한 복제본으로, 백업 및 복구 목적으로 사용
- 멀티 AZ(Multi-AZ) 배포: RDS 데이터베이스를 두 개 이상의 서로 다른 가용 영역(AZ)에 자동 복제하여 운영하는 고가용성 구성 방식
  - 장애나 유지보수 시 기본 인스턴스가 중단되면 AWS가 즉시 예비 인스턴스로 자동 장애 조치(Failover)를 수행하여 다운타임을 최소화
