#### 주제 1: DevOps, Docker
- DevOps: 개발(Development)과 운영(Operations)의 협업을 통해 소프트웨어 배포 속도와 안정성을 높이는 문화 및 방법론
  - 개발-운영 간 소통 지연, 책임 분산, 수작업 등으로 발생하는 시간과 자원 낭비를 없애 배포를 빠르고 안정적으로 하기 위해서
    - 개발 영역: 기획부터 설계, 코드 작성, 테스트 및 배포 준비 단계까지의 전 과정을 수행하는 영역
    - 운영 영역: 개발된 소프트웨어를 실제 서비스 환경에 배포하여 사용자에게 제공하고, 안정적으로 운영 및 관리하는 역할
- Docker: Docker는 애플리케이션이 실행되는 데 필요한 모든 요소(코드, 라이브러리, 설정 등)를 하나로 묶어, 어떤 컴퓨터에서든 동일하게 실행되도록 도와주는 도구
  - 애플리케이션을 일관되게 실행하고 배포하기 위해 환경을 표준화하고 격리된 컨테이너를 사용해 개발, 테스트, 프로덕션 간의 차이를 없애기 위해서
- ### 🐳 Tech Deep Dive: 가상 머신(VM)과 도커 컨테이너(Docker)의 아키텍처 비교 분석

### 🏗️ 1. 구조적 차이점 및 구성 요소

### 💻 가상 머신 (VM / VPS) 구조
* **하이퍼바이저 (Hypervisor):** 물리적 하드웨어 자원을 분할하여 여러 개의 독립된 가상 머신을 실행하고 관리하는 소프트웨어 레이어입니다.
* **게스트 운영 체제 (Guest OS):** 각 가상 머신(VM) 내에서 호스트와 분리되어 독자적으로 부팅되고 실행되는 무거운 운영 체제 환경입니다.
* **애플리케이션 (Application):** 각 VM 내부 인프라 위에서 실행되는 서비스 앱입니다.

### 🐳 도커 컨테이너 (Docker Container) 구조
* **호스트 운영 체제 (Host OS):** 실제 물리 서버 또는 AWS EC2 등에서 실행되는 기본 베이스 운영 체제입니다.
* **도커 데몬 (Docker Daemon):** 컨테이너를 빌드하고, 수명 주기를 관리하며 실행하는 핵심 백그라운드 프로세스입니다.
* **컨테이너 (Container):** 게스트 OS를 탑재하지 않고, **호스트 OS의 커널(Kernel)을 직접 공유**하며 가벼운 격리 환경 안에서 종속성과 함께 실행되는 애플리케이션 단위입니다.


### 📊 2. 성능 및 지표 비교

| 비교 지표 | 💻 가상 머신 (VM / VPS) | 🐳 도커 컨테이너 (Docker) |
| :--- | :--- | :--- |
| **운영 체제 격리** | 자체 게스트 OS를 통째로 실행하므로 완벽한 하드웨어 레벨의 격리를 지원합니다. | 게스트 OS 없이 호스트 OS 커널을 공유하며, 리눅스 커널 커스텀 기술로 공간을 격리합니다. |
| **자원 효율성** | 독립적인 OS 구동을 위한 기본 메모리/디스크 오버헤드가 매우 커서 자원 소모가 심합니다. | 어플리케이션 구동에 필요한 최소 종속성만 포함하므로 극도로 가볍고 자원 효율성이 높습니다. |
| **시작 시간** | 가상 머신의 OS 전체 부팅 프로세스를 거쳐야 하므로 시작 시간이 최소 수 분 단위로 비교적 깁니다. | OS 부팅 과정이 생략되므로 프로세스 실행 속도와 다름없는 밀리초(ms) 단위로 즉시 구동됩니다. |
| **유연성 및 이식성** | 하이퍼바이저 및 특정 OS 환경에 종속적이어서 가상 머신 이미지 스냅샷의 이식성이 낮습니다. | **"한 번 빌드하면 어디서나 실행한다"**는 컨테이너 사상에 따라 클라우드, 로컬, OS 종류에 무관하게 완벽한 이식성을 제공합니다. |


#### 주제 2: Namespace, Cgroups, Dockerfile

- ### 🔥도커는 어떻게 서로 격리하는 환경을 만드냐 🔥
### 🧠 1. 도커 격리의 핵심: 리눅스 커널 (Linux Kernel)
* **커널(Kernel)이란?** 애플리케이션이 하드웨어(CPU, 메모리, 디스크, 네트워크 등)를 사용할 수 있도록 전방에서 실제로 처리해 주는 운영체제의 최하층 핵심 시스템입니다.
* **도커의 경량화 원리:** 도커 컨테이너 내부에는 **자체적인 커널이 존재하지 않습니다.** 가상 머신(VM)처럼 Guest OS 전체를 무겁게 부팅할 필요 없이, 호스트 OS의 커널을 그대로 공유하기 때문에 압도적으로 가볍고 빠르게 구동됩니다.

---

## 🧱 2. 공간을 격리하는 기술: Namespace
네임스페이스는 컨테이너마다 특정 시스템 자원들이 **오직 자신만의 독점 공간에 존재하는 것처럼 보이게 눈을 가리는 리눅스 커널 기능**입니다.

* **PID Namespace (프로세스 목록 분리)**
    * 각 컨테이너는 서로의 프로세스 존재 자체를 알 수 없습니다.
    * 예: Spring 컨테이너에서 모든 프로세스를 종료하는 명령어(`killall`)가 실행되더라도, 격리된 MySQL 컨테이너의 PID(프로세스 아이디)를 볼 수 없기 때문에 명령이 전파되지 않고 안전하게 보호됩니다.
* **Network Namespace (네트워크 분리)**
    * 컨테이너마다 독립적인 가상 IP, 포트(Port), 라우팅 테이블, 가상 네트워크 인터페이스를 별도로 부여합니다.
    * 이 덕분에 한 호스트 안에서 여러 컨테이너가 포트 충돌 없이 동일한 `80` 포트나 `8080` 포트를 동시에 사용할 수 있습니다.
* **Mount Namespace (파일시스템 분리)**
    * 각 컨테이너가 서로 완전히 다른 루트 파일시스템(` / `)을 가진 것처럼 격리하여, 서로의 파일이나 디렉토리에 접근할 수 없도록 차단합니다.

---

## 🛑 3. 자원을 통제하는 기술: Cgroups 
네임스페이스가 '공간'을 분리했다면, cgroups는 컨테이너별로 **CPU, 메모리, 디스크 I/O, 프로세스 개수 등의 하드웨어 자원을 얼마나 사용할지 한계선을 정하고 측정하는 기술**입니다.
* 특정 컨테이너 안의 코드가 무한 루프를 돌거나 메모리 누수가 발생하더라도, 설정된 제한선 이상의 자원을 먹지 못하게 커널 단에서 틀어쥡니다. 이를 통해 하나의 컨테이너가 호스트 서버 전체의 자원을 고갈시켜 시스템이 다운되는 대참사를 방지합니다.

## 📊 4. Namespace vs Cgroups 핵심 요약

| 구분 | 🧱 네임스페이스 (Namespace) | 🛑 시그룹 (Cgroups) |
| :--- | :--- | :--- |
| **핵심 질문** | **"무엇이 보이는가? (시야)"** | **"얼마나 사용할 수 있는가? (양)"** |
| **주요 목적** | 공간 및 자원의 완전한 **격리** | 하드웨어 자원의 **제어 및 제한** |
| **프로세스 목록** | 다른 컨테이너의 프로세스를 안 보이게 숨김 | 생성할 수 있는 최대 프로세스 개수 제한 |
| **네트워크** | 컨테이너별 독자적인 IP·포트·라우팅 분리 | 네트워크 대역폭(사용량) 측정 및 제어 |
| **파일시스템** | 컨테이너별 독립된 루트 파일시스템 제공 | 직접적인 파일시스템 격리는 관여 안 함 |
| **CPU · 메모리** | 논리적 공간 분리이므로 직접 제어 안 함 | CPU 점유율 및 메모리 사용량 할당·제한 |
| **대표 비유** | **각 팀에게 완전히 분리된 다른 사무실을 제공** | **각 팀이 쓸 수 있는 전기·회의실 사용 시간을 제한** |

- Dockerfile: 도커 이미지를 생성하기 위한 명령어 및 설정이 담긴 텍스트 기반의 스크립트 파일
  - 컨테이너 이미지를 코드로 정의해, 수동 설정 없이도 항상 동일한 환경을 재현하고, 빌드 과정을 표준화하기 위해
    - 각 명령어 실행 단계를 독립된 레이어(layer)로 나누어 관리하므로, 빌드 효율성과 캐싱(caching)의 이점을 얻을 수 있습니다.
    - 하단의 Base Image를 기반으로 위쪽으로 레이어(Layer A, B, C)가 쌓이면서, 자주 변경될수록 위쪽 레이어로 배치해 빌드 과정에서 캐싱(caching) 효과를 극대화하는 구조가 됩니다.
- ### 🧱 1. 도커 이미지 레이어(Layer) 적층 구조

도커 이미지는 레고 블록을 바닥부터 **아래에서 위로(Bottom-up)** 차곡차곡 쌓아 올리는 아키텍처를 가집니다.

* **베이스 이미지 (Base Image):** Dockerfile의 맨 첫 줄(`FROM`)에 명시하는 OS 및 기본 런타임 환경으로, 이미지의 가장 최하단(바닥) 레이어를 형성합니다.
* **레이어(Layer)의 누적:** Dockerfile의 명령어(`RUN`, `COPY`, `ADD` 등)가 한 줄씩 실행될 때마다, 기존 레이어 위에 새로운 변경 사항이 담긴 파일시스템 레이어가 한 층씩 위로 쌓이게 됩니다.

- ### ⚡ 2. 빌드 캐시(Build Cache)의 작동 원리와 철칙

도커 엔진은 이미지를 빌드할 때 소요 시간을 단축하기 위해 기존에 빌드했던 레이어를 재활용하는 **캐싱(Caching)** 기능을 지원합니다. 단, 캐시를 적용할 때 매우 엄격한 규칙이 존재합니다.

> ⚠️ **도커 캐시 무효화(Invalidation)의 철칙**
> 빌드 과정 중 특정 레이어에서 변경 사항이 발생하면, **그 레이어를 포함하여 그 위에 쌓이는 상위의 모든 레이어는 캐시가 깨지며(Invalidated)** 처음부터 다시 재빌드를 수행해야 합니다.
- ### 변하지 않는 무거운 환경 세팅(상단/바닥)을 먼저 실행하고, 자주 바뀌는 소스 코드 복사 및 실행(하단/꼭대기)을 맨 마지막에 배치

- Entrypoint: Docker 컨테이너가 시작될 때 어떤 명령을 실행할지 미리 정해두는 Dockerfile의 명령어
- CMD: 그 실행 대상에 어떤 기본 옵션을 줄지를 정의하는 명령어
#### 주제 3: Image, Overlayfs, Container, Registry
- Image: 애플리케이션 실행에 필요한 바이너리·설정·라이브러리 등을 미리 포함한 읽기전용(Read-only) 스냅샷
  - Thin R/W layer: 컨테이너가 실행될 때 이미지 위에 추가되는 최상위 쓰기 가능한 레이어입니다.
  - 이 레이어는 파일 전체를 담지 않고 변경된 파일이나 새로 생성된 파일의 차이(diff)만 저장합니다.
- overlayfs: 여러 개의 읽기전용 디렉토리(이미지 레이어) 위에 하나의 쓰기 가능한 디렉토리(컨테이너 레이어)를 겹쳐서, 마치 하나의 통합된 파일시스템처럼 보이게 만드는 리눅스 기술
- Container: 애플리케이션과 그 실행에 필요한 모든 종속성을 포함하여 경량화되고 독립적으로 실행되는 단위
  - 컨테이너 기반 가상화는 별도의 하이퍼바이저나 Guest OS 없이, 호스트 OS의 커널 위에 컨테이너 엔진(Container Engine) 을 설치하여 애플리케이션과 그 실행에 필요한 라이브러리 및 환경설정만을 독립적으로 패키징해 실행하는 방식
  - 즉, 컨테이너는 별도의 Guest OS를 포함하지 않고 호스트 OS의 커널을 공유하기 때문에, 가상 머신에 비해 자원 소모가 적고 더욱 가볍고 빠르게 동작
  - Thin R/W Layer: 컨테이너가 실행될 때 이미지 위에 얹어지는 **얇은 쓰기 가능 레이어**입니다. 파일 전체를 무겁게 복사하지 않고, 컨테이너 런타임 중에 변경된 파일이나 새로 생성된 파일의 차이점(diff)만 효율적으로 저장
- 하이퍼바이저: 물리 서버 위에 직접 설치되어 각 VM이 독립적인 Guest OS를 부팅·운영하도록 하는 가상화 엔진
- 컨테이너 엔진: 호스트 OS의 커널을 그대로 공유하면서 애플리케이션과 필수 라이브러리만을 격리된 패키지(컨테이너)로 실행
- Registry: 컨테이너 이미지를 저장하고 배포하기 위한 중앙 저장소
  - 컨테이너 이미지를 중앙에서 관리하여 배포의 일관성을 유지하기 위해서
  - 컨테이너 이미지를 버전별 중앙 저장소에 안전하게 보관할 수 있고, 조직 내 개발자나 배포 자동화 시스템이 언제든 동일한 이미지를 내려받아 실행할 수 있어 배포의 일관성, 자동화 및 롤백 편의성을 확보
  - Docker Hub, Amazon ECR, Google Container Registry(GCR), GitHub Container Registry등

- ### 🐳 도커(Docker) 핵심 구성 요소 정리

| 구성 요소 | 설명 |
| :--- | :--- |
| **도커파일<br>(Dockerfile)** | 도커 이미지를 생성하기 위한 청사진 역할을 하는 텍스트 문서입니다. 애플리케이션 실행에 필요한 모든 명령어, 환경 설정, 의존성 설치 방법 등을 정의합니다. |
| **도커 레지스트리<br>(Docker Registry)** | 도커 이미지를 저장하고 배포하는 중앙 저장소입니다. 도커 허브(Docker Hub)와 같은 공용 레지스트리가 있으며, 자체 사설 레지스트리를 구축하여 사용할 수도 있습니다. |
| **도커 이미지<br>(Docker Image)** | 사용자가 실행할 코드가 들어있는 불변의 바이너리 스냅샷입니다. 한 번 생성하면 수정이 불가능하며, 빌드 시 여러 단계의 레이어(Layer)로 구성되어 쌓입니다. |
| **도커 데몬<br>(Docker Daemon)** | 도커 컨테이너를 관리하는 백그라운드 프로세스(`dockerd`)입니다. 클라이언트의 API 요청을 처리하고, 컨테이너가 정상적으로 구동될 수 있도록 런타임 환경을 제공하며 이미지 빌드 및 관리를 수행합니다. |
| **도커 컨테이너<br>(Docker Container)** | 도커 이미지가 메모리 위에 상주하여 실제 코드가 격리된 환경에서 수행되는 독립적인 프로세스 인스턴스입니다. 컨테이너 종료 및 삭제 시 내부의 모든 데이터는 휘발됩니다. |

### 오늘의 회고
- 도커가 컨테이너를 격리하는 리눅스 커널의 기술인 Namespace와 Cgroups을 배웠다.
- 도커의 밑바닥 가상화 메커니즘을 이해하며, 향후 Dockerfile 작성 시 레이어 캐싱 효율을 극대화할 수 있는 명령어 배치 순서를 고려하여 실습에 적용해야겠다.
